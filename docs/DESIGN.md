# Quarterdeck: design

Version 0.20, 2026-11-07.

## 1. What it is

Quarterdeck runs a crew of coding agents as visible terminal sessions under one human's command. Each agent is an ordinary terminal program (Claude Code, Codex, Antigravity and others) in its own tmux window, where the human can read it and type into it at any time. Quarterdeck seats the agents, carries orders and reports between them, watches them, and accounts for what they spend.

It is a control plane and nothing more. It is not the agents, not the code they write, and not the way they review or land that code. Those rules are the ship's standing orders, which Quarterdeck carries to every seat but does not enforce in code.

## 2. The parts

Six parts make the ship and two keep it honest. The parts name the modules and the commands, and the laws are grouped by the part that enforces them, so the eight words, learned once, carry through the code and the rest of this document.

**Six make the ship**

| Part | What it is | Module | Commands |
|---|---|---|---|
| **Ship** | The declared organization: one file, `ship.toml`, naming the tmux sessions, the seats in each, and every seat's role, harness, pool, model and persona; one project folder holding framework, declaration and state | `ship.py` | `qd up`, `qd down`, `qd status`, `qd status --line` |
| **Harness** | An adapter for one agent program: how to launch and brief it, recognize it, find and read its record, read its screen and its usage, which controls it takes and in what form, which of its dialogs may be dismissed, and how it takes a message while it works | `harness/` | none of its own; the other parts call it |
| **Seat** | One running harness in one tmux pane under one role, and its door, the one path anything is typed through. Identity is pane id, process id and record; the persona and the window name are display | `seat.py`, `door.py` | `qd up <seat>`, `qd down <seat>`, `qd restart <seat>`, `qd fresh <seat>`, `qd stop <seat>`, `qd set`, `qd controls` |
| **Post** | The messages: orders, reports, questions, answers and acknowledgments as immutable files, delivered in full to each addressee, through its door or through its own watch, with an inbox the service renders for each seat | `post.py` | `qd post`, `qd inbox`, `qd inbox --wait` |
| **Watch** | Reading a seat: what it is doing and in which tool, whether its door is open, context used, and the last reply; and the one line every ship session shows about the whole | `watch.py` | `qd watch` |
| **Ledger** | Accounting: tokens, cost, tool calls, time, machine load and disk by pool, by seat and by order, from each harness's own record and the seat's own processes | `ledger.py` | `qd ledger` |

**Two keep it honest**

| Part | What it is | Module | Commands |
|---|---|---|---|
| **Standing orders** | What every seat reads before it acts: the laws the framework enforces, the ship's own orders, and a card for its role and for its program. The laws live here, are enforced in the six parts above, and are proven by the Drill | `standing.py` | `qd laws`, `qd brief <seat>` |
| **Drill** | Proof that the ship works: a fake harness in the shape of Claude Code or Codex, and the all-hands exercise, every seat sending to every other, the service crashing and recovering, every seat relaunched fresh and the matrix run again. On the fake harness in the tests; on real programs when asked | `drill.py`, `fakeharness.py` | `qd drill` |

One verb is for the machine the ship runs on. `qd doctor` (`doctor.py`) checks tmux and git, the program each harness needs and its version, the sign-in each pool names and when its grant expires, every seat's working directory, the runtime's fence, the service and the disk, and prints a proof line per check. With `--fix` it opens a throwaway seat on the first pool whose program runs, hands it the failures as an order, waits for its report and checks again: the programs that run the ship are the help that can mend it, where a script could only name what is wrong.

## 3. What the human sees

The Admiral, the human operator, has "Admiral's Office". The flagship's other two tmux sessions are "Ship's Bridge" for command seats and "Crew" for workers. One window per seat, named by persona. Every ship session carries one status line, refreshed by tmux on its own timer: whether the service is alive, the oldest undelivered message and its age, the seats that need a human, seats held at a limit with no eligible declared destination, delivery and watch obstructions, nearly full disks and grants nearing expiry. `qd status` fits on one screen: every seat's activity, door, current order and tokens today, then the open orders. On the Bridge and in the Crew every message is typed in full into its addressee's pane, so a pane's scrollback is the log of the seat's traffic, read by scrolling up. Everything else is a file a person can read: TOML for the ship, Markdown for inboxes and standing orders, JSON lines for messages, and one SQLite file for the Ledger.

The human rarely types `qd` at all. Their word goes to the Desk, an agent seat in the Office, and the Desk runs the ship with `qd`. So `qd` is written for an agent at the keyboard as much as for a person: one verb per act; every reading available as `--json`; every act followed by a proof line saying what was done and how it was confirmed; every refusal naming the reason and what would lift it; `qd --help` complete enough to be the Desk's manual, with the desk role card teaching the rest. What the human watches is the Desk's pane, where the commands and their proof lines appear, and the other panes, where each change lands as a typed line a person can read.

Two words the rest of this document leans on. A **turn** is everything from one input to the next idle: the program takes a message, the model works through its steps, and the program stops and waits again. A **step** is one entry in the record along the way: a reply, a tool call, a tool result. The Ledger counts by turn, summing steps. The Watch calls a seat working while a turn is open and steps keep coming.

## 4. The ship file

The example gives names to roles: Pike, the captain; Scott, the engineer; and Maeve, the desk.

```toml
[ship]
name = "enterprise"
operator = "Admiral"                 # what this ship calls its human
workspace = "~/dev/quarterdeck"      # the default working directory of every seat
tick = 1.0                           # the service's wait after each pass, in seconds: the default

[pools.claude-primary]
provider = "anthropic"
config_dir = "~/.claude"

[pools.claude-secondary]
provider = "anthropic"
config_dir = "~/.config/claude-second"

[pools.codex]
provider = "openai"
home = "~/.codex"

[pools.google]
provider = "google"
config_dir = "~/.config/agy"

[pools.anthropic-api]
provider = "anthropic"
api_key = "env:ANTHROPIC_API_KEY"     # the key is named, never written here
budget = "200 USD/month"             # optional: a wall when spent

[pools.local]
provider = "local"
endpoint = "http://127.0.0.1:8000/v1"  # a model served on this machine: no credential, no quota; a seat on it is jailed
# output = 8192                     # optional response-token allowance, separate from the context window

[sessions.bridge]
title = "Ship's Bridge"

[sessions.office]
title = "Admiral's Office"
human = true                         # the human types here; the ship never does

[sessions.crew]
title = "Crew"

[seats.pike]
session = "bridge"
role = "captain"
persona = "Pike"
harness = "claude"
pool = "claude-secondary"
model = "claude-opus-5-5"
effort = "max"

[seats.scott]
session = "bridge"
role = "engineering"
persona = "Scott"
harness = "codex"
pool = "codex"
model = "gpt-6-astra"
effort = "xhigh"

[seats.desk]
session = "office"
role = "desk"
persona = "Maeve"
harness = "claude"
pool = ["claude-secondary", "claude-primary"]   # starts on the first; at a wall tries later choices, then earlier ones
model = "claude-opus-5-5"
effort = "max"
cwd = "~/dev"                        # a seat may override the workspace
remote_control = true

[seats.worker-1]
session = "crew"
role = "worker"
harness = "codex"
pool = "codex"
model = "gpt-6-astra"
effort = "high"
up = false                           # declared, brought up on demand
fresh = "after-order"                # a clean context for every order

[seats.worker-1.settings]            # the program's own keys, passed verbatim at launch
model_auto_compact_token_limit = 200000

[seats.worker-2]
session = "crew"
role = "worker"
harness = "opencode"
pool = "local"
model = "qwen3.8-27b"
up = false
sandbox = true                       # what a seat on an endpoint pool gets anyway; written to say so, or false to lift it
```

Rules: nothing undeclared runs. Any declared seat can be up or down; `qd up` brings up every seat marked up and resumes what has a record, and `qd up <seat>` brings up one that was declared down. A seat without a persona is shown by its name. A pool is one way of paying, named for its place in the ship: a subscription, named by its credential directory; an API key, named by the environment variable or file that holds it; or an endpoint, a model served at an OpenAI-compatible URL, local or remote, with no credential and no quota wall, and a key named beside it where a remote service wants one. A provider may have any number of pools of any kind. Pools point at credentials and never contain them. A seat on an endpoint pool runs its program in a jail unless the ship says `sandbox = false`, and any seat does with `sandbox = true` (section 5). A seat's `pool` is one pool or a list in order of preference (section 6). Seats start in the ship's workspace unless they name their own. A session marked `human = true` is where the human types, and the ship never types there; its seats are reached by their watch (section 7). `remote_control = true` opens the seat's session from the operator's phone and claude.ai as well, where the program has that feature; Claude Code has it, and `qd up` refuses the key on a program that does not. A seat's `settings` are its program's own keys, passed verbatim as launch overrides; nothing is ever written into the program's configuration. `qd up` also starts the ship's one service: one plain process per ship, not a seat, which renders inboxes, delivers messages, writes attempts, applies deferred controls, fails seats over between pools, writes the heartbeat and samples the machine. It belongs to whoever ran `qd up`, outlives that shell, and is restarted by `qd up` when the status line says it is down; a ship may run it under a systemd user unit if it likes, and the framework neither requires nor installs one. `qd` works on the ship folder named by `--ship` or by `QD_SHIP` in the environment, which `qd up` puts in every seat's environment. The ship file is written in the plain form shown here, one key per line, and `qd set` edits the one line a change needs and keeps everything else, comments included; a test round-trips this example. `tick` in `[ship]` is how many seconds the service waits after each pass: 1.0 when absent, and otherwise a number from 0.05 to 5 inclusive, refused by name as `ship.tick` outside those bounds or when it is not a finite number. The service reads the ship file afresh at the start of every pass, so a new tick takes effect from the wait after that pass. A ship file that no longer loads keeps the last valid ship, its tick included. Every duty and its heartbeat run once per pass whatever the tick, and the stale age the service is judged by stays 10 s, so the longest tick keeps a running service fresh. The tick is set only in the ship file: no environment variable changes it. The test ships and the drill's generated drydock declare a short tick.

**One project folder.** The framework, every ship's declaration and every ship's state live in one folder, because the crew edits all three in the same place and sorting user-edited from crew-edited from source from state across folders is the mess to avoid. What keeps them apart is git, with three nested repositories: the project folder is the framework repository; a ship folder inside it, `ships/enterprise/`, is its own repository holding the declaration, ignored by the framework repository; and the runtime inside the ship folder, always `runtime/` beside the ship file, is a third repository with no commits, a fence and nothing more, ignored by the ship repository. Git will not enter a nested repository without a second force, so `git clean -fdx`, `git stash --all`, `git checkout .` and `git reset --hard` run in the project folder leave the declaration and the state untouched, and `git clean -fdx` run in the ship folder leaves the state untouched, each checked on git 2.53. `qd set` commits what it writes when the ship folder is a repository, so no live change sits uncommitted for a stash to take, and the ship repository's log is the ship's own history of rotations. The double force, `git clean -ffdx`, destroys everything, as `rm -rf` does; nothing short of another disk prevents that, and it is accepted. `qd up` creates the fence if it is missing and refuses a ship whose runtime git tracks. Two ships travel inside the framework repository as tracked files, the drydock on the fake harness and the default ship on real programs, so they are the ships that cannot be their own repositories, and `qd up` says so in a line when it runs one.

A harness is the terminal program; a provider is the company whose models or plans the pool uses, or the declared operator of an endpoint. A model's brand does not establish the endpoint operator. A pool is one payment/access choice. Seats name harnesses; pools name providers.

Canonical company identifiers and displays are `anthropic` (Anthropic), `openai` (OpenAI), `google` (Google), `xai` (xAI), `meta` (Meta), `zai` (Z.ai) and `openrouter` (OpenRouter). Known company spellings normalize without case; `z.ai`/`z-ai`, `x.ai`, `open-ai` and `open-router` normalize to those identifiers. Other explicit endpoint operators retain their trimmed spelling. `synthetic` is the fake program's test provider. Native provider facts live on adapters: Claude Code is Anthropic, Codex OpenAI, Antigravity Google; open harnesses OpenCode and pi have no native provider.

Subscriptions run only in their provider's native harness; a refusal names it. A native harness also accepts its own provider's key. Open harnesses take compatible endpoint pools, optionally with a key, and refuse a key without an endpoint. Native cross-provider endpoints are deferred to the Claude endpoint integration. Validation and launch preflight enforce acceptance; a refused restart or move leaves the old pane intact.

Existing native harness spellings remain input aliases. Doctor prints the exact pool declaration edit to its company spelling. Install the new reader with the old ship file first, then edit and commit the provider spellings. Before downgrading, restore the previous native spellings while the new reader is installed and validate, then downgrade. Pool names, credential roots, seat harnesses, saved selections, launch history, records and Ledger ownership do not change. There is no runtime migration or provider network call. Company spellings are not readable by the preceding code. Aliases have no removal date; new examples use companies.

Public readings use `provider_id` and `provider_name` for declared company identity, separately from `harness`, executable `program`, and paying `pool`. Pool metadata includes `native_harness`; harness metadata includes `native_provider_id`/`native_provider_name` (null for open harnesses). Status/watch/doctor and Ledger readings carry declared `pools` and `harnesses` collections. Ledger's former `pools[].provider` is replaced by `provider_id`; there is no same-name semantic switch. Usage groups/windows, launch/record harness names, native model/provider IDs and accounting pool names retain their source meaning. Status-line JSON facts and its operational-only text remain unchanged.

An optional `[cascade]` declares three ordered `seats`, a separate `orchestrator`,
`efforts` (default `low`, `medium`, `high`), `notes = "ring"` and `note_chars` (default
800, at most 4000). The seats retain their conversations between laps; the real ring
starts on three providers. The fake drydock may use one synthetic provider. An explicit
`qd cascade --re QUESTION [--efforts low,high]` from the orchestrator or operator starts
one active question, addressed to the orchestrator, once by its canonical post identity.
The question remains open until the orchestrator's ordinary answer.

The service publishes child orders as `ship` in the question's thread. Reports naturally
return to `ship`, close only their ordinary child order, and are relayed whole to the next
seat. A report begins with `## Cascade note`, a bounded note, then `## Answer` and the
full answer. No intermediate report is addressed to the orchestrator. Only the service
appends the note under seat and lap to `runtime/ring/<question>/responses.md`, with
requested and observed/unknown effort. The journal beside it saves immutable post intents
before publication and offset/hash byte-append intents before writing. Recovery finishes
only the missing append suffix or publication; it never repeats a possibly typed control.
Posts keep their existing JSON shape. A changed notes prefix holds that append and causes
an early final notice; it is not rewritten. The notes path is independent of the workspace.

The existing confirmed in-session control changes effort before the seat's next lap order.
Unavailable, busy, unconfirmed or interrupted controls leave the current effort in place
with an honest fallback in the notes and final notice; the orchestrator's card requires these
limitations in its answer. This cut adds no lifecycle transition or launch-only restart.
The shared `group_post.current_seat_failure` supplies positive owned-dead or held-limit with
no eligible destination evidence. An absent pane is unknown. A recorded failure ends a lap
only when existing canonical input matching ties its inputs to that step's order, or its
latest failed turn began at/after the order's measured native taking. Consumed queues use
their consumption time. Posted-at and attempt clocks alone prove no taking. Unknown or
unreadable evidence holds, and no reader forms are added. One immutable final service report
tells the orchestrator where the notes are, includes requested and actual/unknown effort
observations and limitations, and normally carries the last full answer. An explicit
`provider-refusal` stop category in the run journal instead withholds that full answer and
refused step input. The service names the fixed category, seat/lap, notes path and last
completed report id for a person to open. The orchestrator concludes from completed notes
only, names the stop and never automatically reads/retypes the referenced report. The
category comes only from recognized current-step failure evidence or that exact current
order's membership in the existing exclusion set; an unreadable exclusion journal holds.
Unlike the forum, which gives filed reports priority because they return only to the lead,
the cascade checks exact current-order exclusion and the existing positively associated
reader refusal before accepting a report because it would relay it onward.
One `associated_failure` helper retains the existing native match and lifecycle/launch
rechecks; the service's pre-report callback and ordinary health share that proof. The
callback promotes only the existing provider-refusal category, so dead/limit and generic
errors remain report-first and cannot mask a positive associated reader refusal. Unknown
native evidence supplies no positive refusal; an unreadable exclusion journal still holds.
An already filed report remains immutable and is named separately by `stopped_report` for
a person; it is not parsed, appended as a note, marked accepted or sent to the next seat.
No reason/body substring classifier or Message fields are added. The notice does not answer
the question. An interrupted child order stays open until its addressee reports; a late
report cannot resume the ended run. The template beside drydock carries its own orders,
cards and instructions and travels with the installed copy. There is no compiler, fleet
raising or external workspace write in this cut.

Each retained run is processed independently. Malformed, foreign, conflicting or unreadable
run evidence produces a fixed derived hold under `runtime/post/cascade-holds/`, shown by
read-only `Facts.cascade_held` even with the service down and counted on crowded status lines.
The service logs changed holds after the pass, once per unchanged signature across restarts;
successful recovery clears the derived hold. This leaves group behavior unchanged. The
holds reader observes only fixed reasons/signatures, never report/provider bodies or usage.
Untyped legacy stopped journals hold rather than guessing their stop category. Notes reads,
prefix checks and suffix appends use one checked nofollow regular-file descriptor under a
lock, with identity rechecked; an uncertain observation is retained, never a terminal
success. `cascade_runtime.py` owns this runtime evidence and no native control or probe.

## 5. Harness adapters

One class per agent program, on one interface, `Harness` in `harness/base.py`. A new adapter writes the members below; the rest is written once in the base. Every fact about a program lives in its adapter: no module outside `harness/` names a program, and a test holds the line.

A program of a frontier provider starts with the trust its maker gives a person who trusts the working folder: the folder instructions, skills, hooks and tool servers load as they would for that person. The ship adds security particular to one program only afterwards, each piece on the Admiral's word. The operator's own HOME files stay out of a seat; the declared workspace is trusted separately. The existing hands and their workspace jails are unchanged.

| `launch(seat, pool, home, brief, resume, first)` | The exact command line and environment for a launch, with or without resume: the brief carried without touching the user's files, appended to the system prompt, as a configuration override, as an instructions file or as the first message, and the first message where the program takes one on its command line |

| `quota_wall(text, at)`, with `screen_walls` | A wall the program shows on its screen, with its reset, where the record may not carry it; and whether the service reads a live seat's screen for one |
| `remote_control`, `wrap_slack`, `drill_settings()` | Smaller facts: whether a seat can also be opened from the operator's phone; the columns the program keeps clear when it wraps at a word; the settings of the synthetic drill, which only the fake supplies |

For Grok joins only, `first_timestamp` is the UUIDv7 session folder's millisecond creation time, accepted only when every native row agrees with that folder identity; unreadable, non-v7 or conflicting identity yields no time, with no row-time fallback or join flooring.

Written once in the base, over these: joining a launch to its record (the first record written after it, any ambiguity reported, never guessed); `state`, `turns` and `read` over the `reader`; `version(home=None)`, whose default keeps the program's existing `--version` invocation; `owns_launch(argv)`, which knows a saved launch by its program; and `control`, `recognize`, `confirms` and `is_headline`, which look up what the adapter declared.

JSON-lines adapters may override `JsonLinesReader.identifies(entry)` for their native envelope. The default retains the `type` in `kinds` rule. Grok uses native ACP `method` and `params.update` markers without rewriting source rows; the shared snapshot, cache and walk remain unchanged. Its inputs retain native physical line numbers for diagnostics.

`Harness.version(home: Path | None = None)` preserves its optional context contract. `Harness.private_version_home: bool = False` is the explicit opt-in; Grok declares true. The private dispatch at doctor, Seat launch and installed check calls every adapter without that flag once without arguments and creates no home, even if its version method accepts a home parameter. ## 6. Seats

A seat is one running program in one pane, under one role. `qd up <seat>` launches it with what its adapter builds: the pool's credential, the model and effort, the brief and the seat's settings, all as flags and overrides on the program's own command line, with the seat's open messages as the first message where the program takes one there. `qd up` with no seat brings up the ship and resumes every seat that has a record. `qd down <seat>` ends one. Restart and fresh are one relaunch path with one difference: `qd restart <seat>` relaunches with resume, keeping the conversation, for a control that has only a launch form or a program that has stopped answering; `qd fresh <seat>` relaunches without resume, a new conversation that begins with the brief and the open messages. Nothing is typed to clear a seat, because a typed clear cannot change a seat's pool or program, leaves a second record in its home, and cannot refresh a brief that was passed at launch. The seat's current record is the first record written after its launch, which is exact because one process writes a home; older records stay for the Ledger.

**A long first message.** Linux refuses an exec one of whose arguments passes 32 pages with its NUL (131,072 bytes here), or whose arguments and environment pass `ARG_MAX` (2,097,152 here), and a launch carries its open messages as one argument. So every start, `qd up`, `qd restart`, `qd fresh` and every start the service makes, goes through one path in `Seat._up` that bounds the first message in UTF-8 bytes. A carriage of at most 32,768 bytes, whose final command (after the adapter and any jail) keeps every word at most 65,536 bytes with its NUL and the whole at most 1 MiB or half `ARG_MAX`, is typed whole as before. Anything longer is written whole, durably, to `runtime/seats/<seat>/carried/<stamp>-<random>.txt`, a name of that launch alone that no later launch rewrites, in a private folder of the seat's own that its jail already binds; old files stay. The file begins with the complete list of open orders and questions, then holds exactly the text the launch would have typed, then an end line. The first message becomes an account: the briefed header, the file's path and size, the order to read it whole before acting, one line per open order and question (kind, sender, full id, subject cut to 200 bytes on whole characters with controls escaped and a visible `…`), and a count of the amendments and other messages only in the file. The account shrinks to fit the command; lines it cannot hold become one explicit `and N more` line. A refused message is its bodyless notice in the account and the file alike, without its subject (law: context-is-cache). These soft bounds only choose the form. A launch is refused before any window opens only when its file cannot be written, or when the kernel would surely refuse the command, as with a brief past its own limit; the reason names the word's position and the sizes, never its text. The file is no receipt: the carried messages close as `launch`, not confirmed read, and a resumed seat's consumption is read from its record alone, which holds only the account, so a message carried in a file is carried again at the next start until the record shows it.

**Controls.** `qd set <seat> model=claude-opus-5-5 effort=high` changes a seat. It writes the ship file first, and commits the write when the ship folder is a repository, so the change persists through down, up and restart; then it hands the change to the service, which applies it to the running program by the control's in-session form, a slash command typed through the door, so the change stands in the pane where the human can read it, and confirms it by the program's resulting state. A control with no in-session form is written and reported, not forced: `settings written; qd restart scott applies them`. A change of pool is a restart with resume, because the record lives in the seat's own home and only the credential changes: `pool written; qd restart pike applies it`. A change of harness is a fresh start by nature, because the conversation lives with the program: `harness written; qd fresh pike applies it`. The keys of one `qd set` are written as one edit, validated together and committed once, so a seat declared with one program switches program and pool together, `qd set pike harness=claude pool=claude-primary model=claude-opus-5-5`, which neither key could do alone. On a seat in a human session, every control goes by restart with resume at turn end, because the ship never types there; the human at that keyboard may type the slash command by hand. `qd controls <seat>` lists a seat's controls with the form each has. A slash command typed by hand in a pane changes the program and not the ship file: the ship file says what should be, the Watch says what is, and `qd status` marks any difference, whether a change is waiting for a restart or a hand changed something in the pane: `model claude-fable-5-1 (ship file: claude-opus-5-5)`. `qd set <seat> --adopt` writes what the seat is running into the file in one command. Settings the framework does not name pass through: the keys of `[seats.<name>.settings]` are the program's own, given verbatim as launch overrides, so a program's new feature is available the day it ships, with no change to the adapter.

**Fresh starts.** Compaction after compaction leaves a context made of summaries of summaries. The framework's guarantee is narrow and kept: after any restart or fresh start a seat receives its brief and every open message in full, except a message its provider refused, which it receives as a notice without the text while the sender is told. What a seat holds only in its context, it loses on a fresh start, so what must survive goes in a post, and the ship's orders say so. `qd fresh <seat>` is a fresh start on demand, and `fresh = "after-order"` in the ship file makes one each time a seat's last open order is closed and the closing turn has ended and been recorded, so every order begins on a clean context. The first report that actually closes the last order must fall within an explicitly completed turn in the active conversation; a duplicate report, an idle screen, a child session or an inferred accounting boundary is not proof. Missing or unreadable completion evidence holds the fresh start, as does an open turn or queued input. It is for workers, who take one order at a time; command seats are long-lived and keep their context, and what a human types straight into a command seat's pane, outside the post, is theirs to lose. The Drill proves the guarantee by relaunching every seat fresh between rounds.

A new conversation carries each canonical open order or question followed by what amends it, following explicit `re` links in timestamp/id order. In a root's thread, a message addressed to the seat amends it when it is an answer whose nearest message from the seat, below the root, is the seat's own question, whoever sent it; or when the root's own sender sent it, of any kind but an acknowledgment or a question, unless it is a report or answer replying directly to an order the seat gave. A question never amends: one still open and addressed to the seat is a root of its own, and one the seat has answered is settled. Open orders and questions inside a thread are roots of their own, each judged by its own sender, and stay in thread order. The rest of a thread is history: chiefly the reports and answers that closed or answered the seat's own sub-orders and the questions the seat has answered, which stay in the inbox and the store and are not carried. The rule reads the graph and the senders alone, never a body. Unread and queued messages are carried whatever their kind, so nothing a seat has not yet received is left out. Each message appears once across open threads, unread posts and queued work. The seat's own outgoing questions appear only when needed to explain an incoming answer; they are marked context only and receive no delivery attempt, receipt or claim. A report from `ship` addressed to the seat directly on an open root is also an amendment only when its exact published id and envelope metadata match that structure's saved terminal notice: the group's non-null notice in `runtime/post/groups/<root>.json`, addressed to its lead on the saved order, or the cascade's final intent in `runtime/ring/<root>/state.json`, addressed to its orchestrator on the saved question with status `done` or `stopped`. Selection checks journal format, root and role consistency, and the group's copy and failed-member metadata against immutable posts; the saved group notice is the writer's terminal marker, without a second completion rule. It never reads, compares, hashes or interprets a body to decide this exception, and never calls the structures' full body-comparing validators. The checked journal read is capped at 1 MiB before parsing; oversized evidence or JSON nesting beyond the parser limit is unknown. Missing, unreadable, malformed, inconsistent or competing structure evidence grants no exception and creates no repair or derived artifact. Every other direct ship report is history, including recovery continuations on the same structure root and reports on a root whose sender is itself `ship`; nested reports and reports to another seat get no terminal-notice exception. Unread or queued reports still arrive once through ordinary extra carriage. Other participants' bodies are not carried. Excluded bodies remain absent from both incoming and explanatory context; open roots remain open, and the existing bodyless notice names a withheld incoming message. An unreadable exclusion journal holds the launch.

Only the actual resolved native resume id permits amendment deduplication against the pinned owned record being resumed. A requested resume that resolves to a fresh conversation carries the amendments again, including those consumed in an older record. Deduplication recognizes complete canonical native inputs: full incoming envelopes, exact own-question context, the canonical briefed header and bodyless notices. Unknown or truncated surroundings and ambiguous tokenization invalidate the whole input; envelope-looking text within a body is not separate consumption. Only timestamped accepted or validly consumed input qualifies. Headers, context and notices yield no incoming ids. A launch receipt remains carriage evidence, and is never promoted to record delivery by this selection.

`fresh_after_compactions = 2` is an optional framework setting in `[seats.NAME]`. An absent field or `0` disables it; positive integers enable it, and booleans, negatives, strings and floats are refused. The current owned record supplies the count: Claude Code's root `system/compact_boundary` is a completed transcript boundary; Codex's top-level `compacted` is a persisted history checkpoint. Progress, summaries, sidechains and Codex's `context_compacted` notice do not count again. The adapter must prove the native origin and readable history. The seat retains a byte-prefix proof and the native conversation identity: a same-record resume or service restart retains the count, and only a different owned native origin following a proved fresh launch resets it. Incomplete, rewritten, missing, mixed or unsupported history is shown as unknown; the service does not guess a join from other records. Count, execution proof and activity are separate readings.

At threshold, the service saves a fixed immutable request intent before publication, once per generation. The seat posts an open self-addressed order replying to that request (`qd post order --to SELF --re REQUEST --body-file handoff.txt`), which is reserved before publication and kept out of the ending program's delivery/watch. For automatic fresh, the seat invokes `qd fresh-ready --request REQUEST --handoff HANDOFF --at-break` as its last tool act. This attests no review, signature or landing is half done and promises to finish the turn without starting another task. The command itself persists/publishes the seat's fixed ordinary report, then submits a control naming that exact report and revision. Report prose, publication alone, a timeout or an idle screen cannot arm it. The service does not close either obligation on the seat's behalf. Retry of the same revision reuses the exact immutable bytes; later work requires a new handoff and revision.

The service binds readiness to the live pane/PID, native record/conversation, exact input/tool frontier, configuration, incoming post frontier and open handoff bytes. Only that turn's recorded completion and a proved empty composer, record queue and tool set can claim fresh; unresolved queue identity, recovery, unread or unconfirmed work holds it. Work admitted before the claim invalidates readiness. Admission and claim share a recipient lock; after the claim later arrivals are held for the successor, and the lock is released before retirement/startup. The existing lifecycle carries every open message and unread input, including the handoff, with the brief. A crash leaves a durable claim; a proved new launch/record is adopted, and ambiguity is visible without another automatic attempt.

Admission locks follow the lifecycle claim, then recipient names in sorted order, then attempt publication. A report takes the addressee (its sender) and recipient locks, so addressing a closure elsewhere cannot close a reserved handoff. Explicit pending or claimed lifecycle controls hold automatic fresh; their writers release admission after atomic publication, before waiting for the service reply. The retiring delivery/watch filter is not used for successor carriage: the launch snapshots ordinary unread posts, including non-open answers/reports, as well as open work. Arrivals after that snapshot wait for normal delivery to the successor. Fixed threshold request ids remain in the journal across generations. Reports on those requests or their related self-handoffs close them normally, but cannot trigger `after-order` fresh; genuine orders, including unrelated self-orders, keep their existing eligibility.

**Provider refusals.** A crew seat whose current launch's latest turn is a provider refusal is started fresh by the service, once, without the refused message. The service acts only when the turn has ended with a known-empty queue and tool set; an open turn, queued input or a running tool waits with the door held. The refused message is the single ship message the door typed on this launch whose whole envelope is an input of the refused turn. No input, an input the door did not type (a human's text, or the launch's carried first message), an input matching several messages, or several messages in the turn are ambiguous. Once the refused message is named it is quarantined and its sender told, whether or not the fresh start may proceed: an unknown queue or tool set, or a refusal of the successor before its first normal turn, holds only the fresh start, and a fresh start by hand carries every other open message and the refused one as a notice, never its text. A refused message that cannot be named is held, shown and alarmed for the systems seat or a person; nothing is quarantined on a guess, and the status says the refused message is not identified and must be kept out by hand before any `qd fresh`.

`runtime/seats/<seat>/refusal.json` (format 1) keeps one event per refused turn, keyed by the launch's pane, process and time and the turn's end, written durably before any act: the refused message and its sender, the fixed identity and time of the sender's notice, and the stage, `claimed`, `launched` with the successor launch's time, or `held` with its reason. The sender receives a report from `ship` that refers to the refused message, says the seat's provider refused its conversation at it and that it will not be typed again, and quotes none of it; then the ordinary `qd fresh` lifecycle relaunches the seat. A claim that finds a different launch adopts it; one that finds the seat down is held; one whose relaunch fails is held with the failure as its reason, logged once and never retried by itself: the status line says to inspect, then `qd fresh <seat>`, and the systems seat or a person acts. A held claim keeps its quarantine and its notice. A launch begun by an automatic refusal fresh that is itself refused before it completes a turn normally is held for a person: the ship does not start a seat fresh twice in a row for refusals.

The refused message stays open and whole in the store; nothing closes it or calls it delivered. It is withheld from this seat for good: the launch's first message carries it as a one-line notice, its id, kind and sender, `withheld: refused by the provider · sender told`, without its subject or body (law: context-is-cache), the inbox and `qd inbox` show it the same way, no tick types it, and `qd post resend` refuses it with the reason. A reworded message is a new message. The seat may close a withheld order with an ordinary report saying it was not acted on. An unreadable refusal journal holds: a launch refuses to carry anything and the inbox withholds every body until it is inspected.

**Launch retirement.** A down, restart or fresh start retires the saved launch's window before forgetting its launch metadata. **Reaching a seat mid-turn.** A turn can run half an hour. Both first-round programs take a message typed during a turn and queue it, showing it in the pane, so a message is typed the moment it arrives, turn or no turn, and read at the turn's next stop. Two faster speeds exist where the program has the key: `qd post --now` types the message and presses the program's send-now chord, so the model reads it at its next step without losing the tool call in flight; `qd post --interrupt` presses the program's interrupt key first, which stops the turn, then delivers. `qd stop <seat>` is the interrupt alone. The adapter declares the keys, or their absence. A `qd stop`, like every request a `qd` command files for the service (a stop, a control, a resend, a relaunch, a selection), is answered alone, in name order: a refusal is its answer, written to the request's `.done`; an unexpected error keeps the request as it was under `requests/failed/`, logs the trace and answers the asker that it failed, and the request is never retried, since an act that may have half happened is never repeated unconfirmed; a rebrief, which persists its intent and posts each notice once, instead stays to be tried on the next tick, its error logged; none keeps a later request waiting.

Ordinary request publishers use the durable temporary-file/fsync/rename helper: the temporary does not match `*.json`, and the final request becomes visible only when complete. Success, refusal and unexpected-failure answers use that same helper: the client sees the complete `.done` or keeps waiting, never an empty or partial answer from an open final-name writer. Before dispatching an ordinary service request, the service durably saves its original bytes beside it as `.claimed`. Completion removes the active request durably before removing that replay guard; an explicit deferred/selection hold releases the claim without completing the request. If archival or error-reply publication fails, the claim remains, appears in status, and prevents replay even after a service restart. The raw request and trace remain for inspection; an action that may have run is not automatically repeated. Claim-creation failure happens before the action, leaves the unexecuted request pending and does not block later requests. Rebrief is the explicit exception: its existing persisted intent and deterministic notice ids make retry safe, so even a `ShipError` from an immutable notice conflict retains the original request/baseline/notices, lets later requests run, and then raises for logging. No conflicting notice is altered.

These `.claimed` files are optional runtime evidence, with no post or ledger format change. A service older than this change does not honor them: before rollback, stop the service and inspect/retire any matching active request whose outcome is uncertain; never restart older code over such a request and silently replay it. Removing a claim is an explicit recovery decision, not automatic cleanup.

**A seat's home.** Each program keeps its settings, instruction files, transcripts and logs under one home directory named by one variable: `CLAUDE_CONFIG_DIR` for Claude Code, `CODEX_HOME` for Codex, `PI_CODING_AGENT_DIR` for pi, the XDG directories for OpenCode. The user's own home for a program is the user's, and a ship seat never runs in it. Quarterdeck builds every seat a home of its own under the runtime, from files it owns: the program's settings as the ship wants them, from the framework's template or the ship's own `homes/<harness>/` folder in the program's own format, with the seat's settings laid over; trust for the workspace and the first-run flags already set, so a fresh home opens without a dialog; the program's self-update and its own memory turned off where it has the switches, since a seat keeps nothing of its own between conversations and what must survive is a post or a file of the ship's; permission for `qd post` granted through the program's own permissions; and nothing of the user's. The pool's credential is the one thing shared: an API key by the environment variable the program reads; a subscription by environment where the program takes a long-lived token there, by a link to the pool's one credential file otherwise; and never by a copy, because refresh tokens are single use and a copied credential dies at the first refresh, which has logged most of a crew out at once. The link alone is not enough either: Claude Code writes a refreshed credential by atomic rename, which turns the seat's link into a private file holding the only live refresh token and strands the pool's file and every other seat on it within seconds. So the service watches every seat's credential file on its tick: when one stops being a link, a refresh happened there, and the service copies the refreshed file over the pool's, parks the stale one beside it, and relinks the seat, before the next seat needs it; a test launches two seats on one pool, refreshes in one, and checks that the other sees it. The tick is not the only reseed: a seat going down reseeds from its own home once its program is gone and before its launch, which names the pool the refresh belongs to, is forgotten, so a restart or a check's throwaway seat keeps a refresh with no service running; and a seat's home is never built over a detached credential fresher than its pool's, which is refused and kept for the human, since it may hold the only live token. The grant itself also expires, about every four weeks, and no relink cures that, only the human's login into the pool; the service reads the credential's expiry times as metadata, never the token values, and the status line warns two days ahead: `claude-secondary · login needed by 11-13 22:24`. What an expiry means depends on the grant's kind, which each adapter declares from its measured facts. A fixed grant, such as Claude Code's, whose `refreshTokenExpiresAt` ends the grant that renews its access, warns as above. A self-renewing grant, such as Grok Build's, carries a short access expiry that the program renews on use, so it passes every few hours with no login needed and never warns: the line warns only when the renewal has visibly failed (`login needed by now (its renewal failed)`), or when the grant that renews it is readable by a named field and within two days of its end. An unknown kind (Codex, Antigravity, OpenCode and pi, for none of which a grant's renewal or end has been measured) is never counted; `qd doctor` says `grant kind unknown` in the pool's detail, and for a self-renewing grant names its current access time and whether the end of its renewing grant is known. Whether Codex rewrites its file the same way is a probe for the spike, and the same watcher applies. So a ship seat and the user's own sessions share a subscription and nothing else: not settings, not instruction files, not memory, not transcripts, not logs. What follows: the programs' logs are in the runtime; a seat's record is the only record of its launch in its home, so the join is exact by construction; the user's own directory stops filling with the crew's sessions; and the ship's program settings are files in the ship folder, read and changed like everything else of the ship's. The pane itself is not logged: a program redraws its screen many times a second, and the record already holds every word.

## 7. Post

Saving a delivery proof compares its newly merged, serialized JSON against the
current file bytes using the same locale encoding, indentation and trailing
newline as its writer. Equal bytes leave the file alone; a missing file is a
first write. Equality means only nothing to write, never durability or that an
earlier failed write was repaired or resolved. Different bytes still use
`durable.replace_file` with its original
file and directory synchronization. Other read errors and write errors propagate;
the save publishes its merged in-memory data only after equality or successful
replacement, never as an in-memory substitute for reading disk. Repeating a
delivered finish therefore does not replace an unchanged journal, while normal
receipt and attempt reconciliation still runs. This adds no reader cache or
change to the durable writer's crash-safety contract.
Errors retain their journal path in the exception trace. No repair flag or
hidden same-process state changes a following pass's disk comparison. Attempt
closure likewise skips a result/detail already present in its locked on-disk
receipt, preserving first writes, terminal rules and real receipt changes.

Brief rendering also compares the actual encoded file before rewriting it,
including when a rebrief retries after another seat remains unresolved. First
renders and changed text keep their existing write behavior. Heartbeat time and
status collection timestamps continue advancing: freshness is real changed data,
even when the displayed status text is the same.

A post proof confirms storage and says only what its caller can observe. A seat's own saved launch establishes whether the managed jail hides other seats; the current declaration alone does not describe an already running launch. A missing, malformed or unreadable caller launch leaves that view unproved. In either case the proof reads no recipient launch, host service PID or watch PID: it names service delivery, or the declared human inbox route, and says that recipient/watch state is not visible. Hidden metadata is never a down or unarmed fact. This uses the existing own-seat mount and exposes no additional path, marker or environment variable. Unrestricted callers retain the normal up/down, service and watch proofs; failed recipient selection or unreachable transport is reported as unknown. Stored messages and delivery/receipt behavior do not change.

A message is one immutable JSON file:

```json
{
  "id": "ord-20261106-2101-desk-7f3a",
  "kind": "order",
  "from": "desk",
  "to": "scott",
  "re": null,
  "subject": "Codex profile of the fake harness",
  "due": "2026-11-08T18:00:00-07:00",
  "at": "2026-11-06T21:01:12-07:00",
  "body": "Build the Codex profile of the fake harness. Report when its contract tests pass."
}
```

Five kinds: order, report, question, answer, ack. `re` names the message being answered. Only a report closes an order: a report from the order's addressee whose `re` names it. An ack claims: it names the order its sender is working on, for the Ledger, and never closes anything. `subject` is optional, one line. A message's sender is the seat that posted it, read from the identity its launch set (`QD_SEAT`) and never from a flag, so no seat speaks for another; a shell that is no seat posts as the operator, or names the sender it speaks for.

**Groups and the forum.** Optional `[groups.reviewers]` declares `members = ["reviewer-1", "reviewer-2"]` and `lead = "lead"`. Names must be distinct from seat/operator/ship addresses; members are unique declared seats and the declared lead is separate. `Ship.groups` defaults to an empty mapping, preserving existing constructors and declarations. Groups accept **orders only for now**: another kind addressed to a group is refused before any root, copy or group intent is published.

`qd post order --to reviewers` stores one ordinary request addressed to the lead, keeping the caller as its original sender. It files a separate child order from the lead to each member, with an individual id, the root request id in `re`, and the root's exact body, subject, due and speed. The service generates these declared copies on the lead's behalf; a seat still cannot select another sender through `--from`. Each reviewer reports on its own child and closes that child through the ordinary rule. The lead files one final report on the root, to the original requester; the service's notice never closes that root.

When the lead already has an ordinary open request, it uses `qd post order --to reviewers --re REQUEST --body-file brief.txt` to fan out that same root. The caller must be the declared lead, the root an open order to it, and the body byte-identical; the requester remains `ROOT.sender`, not the forwarding lead. A request binds one group invocation. An identical retry recovers its original ids even after closure; a different group, declaration snapshot or body is refused. A command without `--re` creates a new request, as ordinary post does; identical prose alone is never a deduplication key.

`group_post.py` durably saves format-1 fixed intents under `runtime/post/groups/ROOT.json` before publishing any root or child. The journal holds the original declaration snapshot and complete immutable message intents, including ids and times. Publication verifies existing files against those intents, completes partial fanout after a crash, and never replaces an existing post. The CLI and service serialize this work through the existing admission-lock machinery with a reserved group coordinator name. Membership does not silently change during recovery. No new Message JSON fields, Ledger columns or post-store formats are introduced.

After accounting and before inbox rendering, the service recovers fanouts and checks exact child closing reports. It waits until **every member has filed or positively failed**; a first failure does not discard still-working reviewers. Positive outcomes are saved under the exact child id in this root's optional `failed` mapping, with the member and an allowlisted fixed reason. They are terminal observations for this copy, not a global failed-seat flag or a claim about the seat's later state. Older journals without the field mean an empty mapping; a malformed present mapping holds that group. Later filed reports take priority over saved failures until a terminal notice intent exists. When every member is covered, the service saves one all-filed or named member-failure notice listing every report and failure. No member remains merely pending at that point. Once its notice intent is saved it is immutable and there is no second notice, even if a failed member later files. A cut before or after publication reuses the saved notice id/time/body.

Failure evidence is local: a removed declared member; a positively owned dead pane; the existing status reading that the seat is held at its limit with no eligible destination; or an existing provider-refusal journal identifying this exact child. `current_seat_failure(service, name) -> str | None` in `group_post.py` is the common observation callable without an order: it uses the existing nonblocking lifecycle lock with `automatic=True`, never disarms compaction readiness, and rechecks unchanged launch identity. An absent pane is unknown, including during lifecycle transitions. It consumes the exact `watch.limit_holds` result; an eligible destination or unknown status note prevents a wall failure. `member_failure` adds the group-specific removed-member and exact-child refusal cases. No provider program, usage, login or authenticated request is called; the helper reads the existing local pane/status evidence. This reuses existing wall semantics, including their current limitations; it does not implement the separate spent-only correction. Reused or absent panes, busy lifecycle coordination, no saved launch, unreadable evidence, missing reports or elapsed time alone establish no failure. Refusal forms not classified by the adapter stay unproved. Request-specific refusal and launch/ownership enforcement validation belongs to the separate Claude proof stage.

**Ended turns without filing.** Forum copies and cascade steps also have a record-proved ordinary outcome: `turn ended without a report`, or `turn ended on a length cap without a report` where measured. The shared observer requires the current nonhuman owned launch and pinned reader, native conversation, an explicit completed turn containing the exact canonical copy/step input, known-empty pending tools and record queue with no queue error, and a positively idle empty composer and visible queue. Input skip diagnostics, absent/untimed completion, unsupported steering, recorded errors, changed record/ownership, unresolved delivery or recovery all remain visibly unknown. A direct input must be matched at the turn start; steering requires explicit per-turn input membership. Pi preserves its measured per-turn inputs and native stop/length reason through optional `Turn` fields; older constructors/readers leave them unknown. Readers without usable input diagnostics or native conversation/direct-input association remain unknown. Only pi gains per-turn end reason and steering membership here; existing unknown Codex metadata stays unknown. No guessed end reason, pane prose, identifier substring or elapsed duration supplies proof. The generic direct-input proof does not claim steered association for readers without membership metadata.

Service owns an in-memory pass counter, last completed pass and per-order candidate signature. The first valid observation shows exactly `waiting on <seat>: turn ended, no report`; only a later pass after that entire pass completed can settle, after rechecking the full proof. Duplicate coordinator calls in one pass do not age it. Structures run before thinking recoveries, so the initial grace preserves their ordinary opportunity later in that pass. Unknown proof or renewed activity resets grace. A service restart conservatively grants grace again; no global per-tick journal is written. Derived `post/structure-waits/` files contain only fixed operational categories and observation identities, not answers or provider bodies, and never authorize settlement. Status checks active structure/order, report, launch and record generation; stale observations become unknown or disappear. Status readers neither start passes nor advance grace. They use only an existing lifecycle inode, saved record pointer and explicit saved reader bindings; they cannot join a record, infer/register ownership or create coordination state. Malformed or deeply nested metadata is visibly unknown per journal, without hiding healthy waits; overflow preserves a structure-wait count.

The observer takes existing automatic lifecycle coordination and member admission through the final report check and coordinator terminal save. Forum notice selection additionally freezes all member/lead admissions in sorted order; notice publication occurs after releasing those locks. A report admitted within grace wins. Settlement never closes the underlying copy/step/root or invents transport proof, retries, replacement orders or filed answers. A later report does not rewrite an immutable terminal notice. Cascade stops at the named seat/lap through its existing seat-stop path, retains only the last FILED full answer, and emits its existing one orchestrator notice. Existing separate stop-category precedence is unchanged.

Thinking recovery eligibility is unchanged: the supported pi client requires Qwen and the existing measured launch/configuration proof; Gemma is ineligible. Active/queued/working/unknown recovery holds. A done recovery must bind the same launch, record, native conversation, exact canonical original source input and reserved continuation input before that final completed continuation can receive its own no-report grace. The consumed original cap never becomes another recovery opportunity; unknown lineage stays visible. No live journals are converted. Rolling back requires stopping the service first. Older code ignores the optional wait files and new optional turn fields; it holds group journals containing the new failure reasons as unsupported evidence, so retain those journals and use the newer coordinator to operate them. Ordinary immutable posts and cascade terminal states keep their existing formats. In-flight grace resets on upgrade/restart and no completed outcome is undone.

Each group journal is processed independently. A malformed or unreadable journal or failed publication holds only that group; healthy groups finish in the same pass. Derived `runtime/post/group-holds/ROOT.json` records a safe fixed reason and signature, never provider bodies or usage. The service logs new or changed holds only after the pass; unchanged errors stay quiet across ticks and restarts. Successful recovery clears the derived hold. Read-only `Facts.group_held` adds an operational alert, preserved as a group-held count when status text is crowded, even when the service is down. Older code ignores these side files.

The shipped `ships/forum` template contains the full ship declaration, orders, lead/reviewer cards and a tracked `work/README.md`. `workspace = "work"` keeps the endpoint reviewer's workspace separate from the read-only ship folder; card output paths are absolute under `$QD_SHIP/runtime`. Its four reviewer examples use Claude, Codex, Grok and a local endpoint through pi; the operator sets the real pools, models and endpoint before starting it. At every start with the request still open, the lead's card requires checking for the terminal notice before acting; the direct ship report is carried as an amendment. The lead waits until every member has filed or failed, combines only the named reports, keeps dissent, adds no new analysis and reports once to the requester. Reviewers work independently and read only their own messages. Inbox and carriage retain their recipient selection. The shared post store and group journal remain readable and writable; independence is instruction-only, not a filesystem fence. Native records may show a recorded tool read, but cannot reliably prove that every possible read was observed. A proper fence would require a separate post broker with per-seat authenticated publication/reply resolution and private delivery views, plus changed jail mounts and migration/proof work; that is outside this morning cut.

`qd upgrade` installs the target's declared templates into `runtime/venv/share/quarterdeck`, found by `standing.project_dir()` in the installed copy. One upgrade includes newly introduced templates, and supported rollback targets remove stale resources as described in section 15. Older services can still read/write every ordinary post here and ignore the side journal, but cannot finish a group or issue its terminal notice. Stop group coordination and resolve outstanding reviews before rolling back; retain the journal and all posts. No live state is rewritten or deleted by this change.

Where files live, under the runtime: `qd post` writes each message atomically into `post/store/`, the one canonical copy; `post/inbox/<seat>.md` is the rendered view, open obligations first, oldest first, then what was already delivered; `post/attempts/` holds one record per delivery attempt. Messages are addressed to seats by name, whatever program a seat runs.

The post store, the delivery attempts, the pending journals, a seat's launch with its price, its record pointer and its pool selection are written durably, by one helper (`durable.py`): to a temporary beside the file, synced, renamed into place, then the folder synced. A file renamed into place before its data reaches the disk can come back empty after a power loss (delayed allocation), which emptied two posts, an ack and a launch with its record pointer on 9 November; with the syncs, a power cut at any step leaves a reader the old file or the complete new one, and a crash test cuts each step in-process to show it. Readers still refuse a partial or empty file; an empty record pointer joins no record. The syncs cost about a millisecond a post on the runtime's disk. Appended journals, rendered inboxes and other derived files are outside this guarantee.

The immutable post cache checks directory identity and modification/change times. Following [Git's racy-timestamp principle](https://git-scm.com/docs/racy-git.html), it trusts a matching stamp only when the cached listing itself began strictly more than two seconds after both directory times. A recent listing must be refreshed before certification; merely waiting cannot make it trustworthy. Old certified directories need only constant-cost metadata and clock checks. This guards identical timestamps around two atomic publications, rather than assuming nanosecond fields imply nanosecond precision.

The supported timestamp tick is two seconds: [Python documents coarse filesystem timestamps](https://docs.python.org/3.14/library/os.html#os.stat_result), and [Linux FAT uses two-second timestamp units](https://github.com/torvalds/linux/blob/master/fs/fat/misc.c). Certification uses epoch nanoseconds comparable with file times. Because [the realtime clock can move backward](https://docs.python.org/3.14/library/time.html#time.time_ns), samples bracket stat and listing; observed rollback, future stamps and failed reads leave the cache untrusted. This assumes local, coherently observed metadata with timestamp coarseness no greater than that tick. Coarser/delayed remote metadata or clock changes hidden entirely between observations are outside this proof.

Attempt files are mutable: each read scans their file identities, sizes and nanosecond modification/change times, reusing parsed attempts only while those match. This sees another process's same-path or same-size rewrite without relying on directory time. Failed scans or malformed files raise rather than return cached success or a partial empty reading. Both caches are in memory; their on-disk formats are unchanged. A reading or service phase derives its attempt results from one explicit inventory; journal reconciliation takes a fresh inventory after it may have changed receipts.

**Two ways in.** A message reaches its addressee by one of two paths, chosen by the session the seat sits in. On the Bridge and in the Crew, where the human reads but does not type, the service types the message in full into the seat's pane through the door, under a one-line header and over a one-line footer:

```
qd > order from desk · ord-7f3a · Codex profile of the fake harness
Build the Codex profile of the fake harness. Report when its contract tests pass.
qd > reply: qd post report --re ord-7f3a · inbox: post/inbox/scott.md
```

The pane is where the human reads, by scrolling up, so the whole message goes there and not a pointer to a file: a file name in a transcript tells a person nothing. Both first-round programs show a sent paste in full in their transcript, checked on 6 November 2026 on Claude Code 2.1.317 and Codex 0.166.0. Messages arriving together are typed one paste each, and each is confirmed on its own. New due messages go before previously withheld messages, in order within each group, so a failed item never becomes part of another item's payload. A pre-paste refusal can leave the door usable for the next item; a foreign draft, unknown dialog, unverified paste or uncertain submission holds the door. There is no unconditional progress through an occupied or uncertain box. A message has no length limit.

In a human session, the Office, where the human types, the ship never touches the box. A seat there runs `qd inbox --wait` in the background: it blocks until something new is addressed to that seat, prints the new messages in full in the same form, and exits, and the program hands the output to the agent as a notification. The wait registers itself in the runtime while it runs, so the service knows a watch is armed; the brief tells the seat to arm it again as the last act of every turn. If no watch is armed, the message waits and the status line says so. The watch cannot reach a seat mid-turn or stop it, which the human at that keyboard does by hand, and which is the other reason the Bridge and the Crew keep the door.

**Delivery, exactly once or visibly not.** Before typing, the service persists the exact transport, attempt files, original attempt time, pane, process, launch, reader and owned record. It writes each paste or submit phase before the side effect, and saves the verified display before submission. Recovery never repeats a paste or submit whose outcome is uncertain. An attempt without this journal cannot claim text in the box merely because it looks like the message. The service schedules one message and journals one attempt per new transport. The persisted attempts list remains readable by preceding versions and can still reconcile older multi-attempt journals.

Only an exact, fresh, timestamped input in the owned record confirms transport. Record acceptance into a queue is `queued`, not `delivered`; its timestamped consumption must be seen before it becomes delivered. Untimed or stale identical inputs prove nothing. The same matching rule serves the door, the service and `qd check`, using each adapter's input evidence. Unjournaled open, queued and blind attempts use the same receipt rule over retained records with proven readers and their original attempt times. The open-attempt confirmation window and blind-attempt retry cadence remain distinct from journal recovery. Screen echoes, padding and a disappeared box never supply that receipt. Missing or unreadable records leave uncertainty; a malformed journal is not reconstructed or resent and does not prevent another seat's intact receipts from reconciling.

The adapter declares `record_time_resolution` in seconds. Its default is zero: every existing adapter keeps the exact comparison. Grok 1.0.77 writes whole-second row timestamps and declares `1.0`; `input_receipt.confirmed` floors its local `since` comparison to that second, without rewriting the persisted attempt time or native evidence. An identical input in the previous second is still stale. The whole payload must match, including its unique message id, and the record is already owned by that launch. The Door makes one transport attempt and never retypes uncertainty. This resolution handles the native timestamp's precision; no screen, changed payload identity or retrospective phase rewrite supplies receipt evidence.

A program whose fresh brief starts a model turn declares `opening_prompt_turn`. Its check waits for a recognized ready idle door and a known ended opening turn (bounded by 180 seconds), then requires an additional ended task turn. The check journals its single paste through the same pending Proof as ordinary service delivery. A submitted queued/pending input gets up to 180 seconds for exact record consumption, never a resend.

Antigravity 1.5.5 can show a new native queue before it writes that input. `queued_input` requires a previously empty queue, one matching transport-envelope preview with complete kind/sender/short-id, the edit hint, an empty recognized box and unchanged launch, after the Door matched the whole paste. This returns `queued` with explicit record-pending detail. The journal remains `submitted` and adds optional boolean `screen_queue: true`; other work stays held. The exact receipt clears the marker and advances the existing queue/delivered phase. Queue disappearance is not acceptance. Unreadable/ambiguous evidence, original-time 600-second inspection and temporary-owner teardown retain their ordinary holds and never replay typing. Existing journal readers ignore the optional flag and still hold `submitted`. Public queue enum values are unchanged; `queued` can now describe screen-only evidence, distinguished by detail and pending phase. No Screen/State or Ledger field is added.

The Codex and Claude receipt readers skip unknown or malformed rows and continue through readable evidence on either side. Additional unrelated fields do not invalidate a known row. Codex requires its known user-message subtype; missing essential text is not an empty receipt. Known non-input metadata is ignored without being diagnosed or used as a program-format marker. Empty records remain distinct from unreadable files or wholly foreign program formats, which are reported as failures. Detailed `qd watch` gives one line of counts by bounded known kind and fixed reason. JSON gives exact totals and group counts, at most eight numbered examples, and the number omitted. Neither contains source values, and no skip history is stored. These read-only diagnostics do not change activity, obstruct the door or invalidate a proven receipt.

Claude queues preserve original enqueue times and FIFO positions. A contentless `dequeue` names no input: it is a known shape, and affected queue entries hold until actual readable input identifies them. A later matching input uses the original enqueue time, so a stale or untimed identical queue entry cannot gain freshness from a dequeue or echo. A string-content removal supplies consumption evidence, but retains an echo slot until actual input prevents that echo becoming a fresh acceptance. An unknown queue operation leaves affected state unknown; later readable input can resolve it conservatively. Identical entries with ambiguous echo history may therefore hold rather than certify a newer attempt.

Claude Code 2.1.317's native `popAllEditable` returns selected queued commands to the composer draft. Its logger writes one root `popAll` row per selected item with optional string content; `popQueuedIntoDraft` replaces the draft with the merged text. It does not deliver those commands to the model. An exact unwrapped whole-content match removes one known queued FIFO slot, retains the original acceptance/echo identity for a later actual submission, and supplies no consumed or delivered receipt. Other slots remain queued. Queued answers and reports, even though they are not open obligations themselves, remain unread and are included by restart/fresh carriage until actual receipt or the existing distinct launch-carriage proof. A later merged or edited draft is not a receipt for each former component: substring matching cannot prove delivery, so unmatched original transports remain unconfirmed.

Missing, non-string or unmatched root `popAll` content leaves identity unresolved, including repeated rows after the known slot has left the queue. The optional in-memory/JSON `State.queue_error` then gives a content-free reason; `queued` is last-observed candidate history, not a current count or membership assertion. This uncertainty persists for that record, independently of known turn/tool/completion facts; later deltas and idle screens do not establish a complete queue snapshot. A different record has its own reading. Compact/full watch and the status line expose the uncertainty (including a separate queue-unknown category on status overflow). After-order automatic fresh, pool selection and failover require a proved empty error-free queue and hold with the reason visible. Explicit live restart/fresh requires the queued collection to be known empty and a real timed completion, but a residual queue identity error alone is not a permanent veto. Explicit stop/down and the question-only recovery exception keep their existing rules. Endpoint-only recovery checks cannot see Claude queue uncertainty and are unchanged. No post, attempt, ledger or journal format changes; rolling back requires only reverting the code, with no data migration. Sidechain draft-return rows do not alter the root queue or its uncertainty. Native turn/tool completion still requires its own recorded evidence.

A matching older pending slot, left by identity-free dequeue or an unknown operation, is a possible native queue member. A pop cannot skip it to select a newer identical known slot: both receipt and state readers leave candidate/acceptance identities intact and report the pop unresolved. Echo and returned-draft slots are not native queue membership. Automatic status-line queue collection reads only nonhuman Claude records. Human-owned status alarms retain their metadata-only boundary and do not claim to observe human queue state; explicit requested watch/full readings can expose it.

An unresolved submission on an old launch stays visible without owning a different launch's empty, recognized door. If an explicit lifecycle operation carries the message into a later launch, its distinct `launch` receipt supersedes the old hold without declaring the old submission delivered. A changed launch alone proves nothing. After inspecting the box and owned record with `qd watch <seat>`, the Desk may deliberately request `qd post resend <id>`. That request can retire prior uncertainty only with an empty, recognized box; it cannot clear a draft, repair historical evidence or declare the earlier attempt delivered. Ordinary ticks never resend an unconfirmed submission.

An unresolved journal may instead acquire terminal phase `not-in-closed-record`, displayed as **not in its closed launch record**. This is an attempt reading, not proof that the program never acted. All three facts must be readable: the exact old launch is closed by ordinary lifecycle evidence (its pane is absent from the server, a later saved launch exists, or the server began after the matching launch file was written); its exact saved record has an unambiguous retained reader and readable input evidence with no skipped, unknown or incomplete input rows; and no input at or after the original attempt time matches the payload under the shared text rule. Queueing and other input dispositions still establish presence. Unknown timestamps, failed tmux queries, empty/missing/unreadable records and ambiguous reader bindings hold. Initial supported readers are Claude Code, Codex and pi; other readers hold.

The same rule reads old journal shapes, without backfill, a new baseline or a new proof artifact. Settlement preserves the original time, payload, reader, record and attempt files, changes neither native records nor message openness, and authorizes no transport or automatic fresh start. Ordinary ticks cannot replay the terminal attempt; normal open-thread carriage on an explicit later launch remains available. Repeated reconciliation is idempotent, including recovery after saving the terminal journal but before updating its attempt. Sticky `unacted` and `uncertain` results retain their separate rules. No Ledger schema changes; a version predating this terminal phase reports the unfamiliar journal as unreadable and must not be used to reconcile it.

**Attribution.** One change has one concrete order. Its implementation, test and correction orders refer to that order with `re`; reports still refer to the assigned order they close, and answers to their question. Review and merge messages remain in that same explicit reply thread. An umbrella campaign is not the anchor for its separate changes. The framework follows the links, never subjects, quoted ids, role names or an inferred parent. Historical messages without links remain independent or unassociated; semantic grouping of that history is evaluation work outside the framework.

For each recorded turn, the Ledger collects valid posts made by that seat within the turn and exact complete post envelopes consumed in its record. A consumed queue entry needs its consumption time. Acknowledgments must claim the sender's own open order; only the first actual closing report supplies closing evidence. Duplicate/foreign reports and invalid claims do not create work. Missing, conflicting, cyclic or time-inconsistent threads are unresolved. Direct evidence takes priority over fallback context: with no direct order evidence, use a valid claim active at turn start, else the sole open-order interval overlapping the turn. Tied latest claims or several competing open orders are uncertainty, not proof that each was served.

Several directly evidenced change roots in one turn are shared work. The turn's measurements are counted once under `[shared]`, with the candidate roots and evidence in the reading; no token fractions are invented and no last message wins. `-` means no association in available evidence; `[unresolved]` means an evidence gap or competing candidates. `qd ledger --by order --json` gives the basis for every turn, including fallback context. These labels describe attribution, independently of the measured/unknown usage figures.

Claude's watch route is separate from transport receipts: a recorded `qd inbox --wait` command names an output file, and a uniquely linked recorded `cat` or complete `Read` result supplies the full envelope at the read-result time. The output file itself is never opened for attribution. Arbitrary stdout, compound shell reads, conflicting/reused output origins and truncated envelopes do not prove that route. Launching a watcher or its completion notification alone does not charge a later message to that launch turn. Incoming evidence that overlaps turn intervals, or a posted message that could belong to overlapping records of the same seat, remains unresolved.

## 8. Watch

Two readings, taken together, because they answer two different questions.

**Activity**, from the record, answers "what is it doing":

- `idle`: the last turn ended and nothing is queued.
- `working`: a turn is open and steps keep coming, with the open tool call named: `working, in Bash 3m`.
- `stalled`: a turn is open and ten minutes have passed without a step, with the open tool call named: `stalled, in Bash 14m`. A seat that has never moved is idle, not stalled.
- `off`: no harness is running in the pane, with the reason: exited with a code, crashed, no pane.
- `refused` or `failed`: the last turn ended in an error the record names, with its kind, its native code where the record gives one, and its first words: `refused, provider refusal (cyber_policy): <first words>`; `failed, program error: ...`. Never `idle`.

**Door**, from the screen, answers "can the typing path deliver":

- `open`: the box is empty and nothing is in the way. Generated suggestions are turned off at launch, so text in the box always means someone typed it. A pane left scrolled is open: a paste reaches the program in copy mode and a raw pasted carriage return submits it without leaving copy mode, checked on 7 November 2026, so the person reading keeps their place. A working seat is open where its program queues.
- `obstructed`, with the reason named and what clears it: a key the adapter knows (`daybreak notice, dismissable`); time (`limit banner, resets 14:00`; `working, program does not queue`); or a human (`text in the box`, `login`, `unknown dialog`). A captured blank or recognized startup frame reads as `starting, waiting for the input box`, cleared by time: delivery holds without pressing a key. A missing footer or box on an unfamiliar nonblank screen still needs a human. Codex's captured header, complete logo and untouched placeholder before its ready footer are one such startup frame; the logo alone is not, and a residual logo does not obstruct a ready box. Startup describes the door, never overrides activity read from the record.

Text in the box that the door did not type is an obstruction and nothing more is done about it: nothing is typed, nothing is lifted, nothing is restored. The message waits in the inbox, the status line names the seat as needing a human, and the alarm's recipients are told once. This is the whole of the guarding, and why a half-written message can never be sent: the door types only into an empty box, so the human's text is never in the box when the ship's goes in.

A reading the Watch could not take is `unknown`, with what it could not see. Unknown is never dressed as a state. Error is not a state either, except a turn the record says ended in one: a seat's own failure shows as `off` with its exit or as `obstructed` with the banner, a recorded turn error as `refused` or `failed`, and the Watch's own failure is `unknown`.

```
seat    activity              door                              order      today
pike    idle                  open                              -          12.1k
scott   working, in Bash 3m   open, queues                      ord-7f3a   48.9k
una     stalled, in Bash 14m  open, queues                      ord-9c21   3.2k
laan    idle                  obstructed: login, needs a human  -          0
spock   off                   exited 1 at 21:12                 -          0
```

Titles are display, never identity. The door dismisses only a notice the adapter recognizes, types once into an empty box, checks the display, and only then submits. An unverified paste is never cleared automatically. No key goes into an unknown dialog, a menu or a human's text.

**The box check.** Terminal soft rows are joined using tmux's `capture-pane -J` wrap flags before adapter parsing. For rows drawn by the program itself, the expected transport and the adapter's text-area width establish which breaks are forced: a full row may break at any character; a word or hyphen break is allowed only when the following piece cannot fit. Interior spaces, indentation, hard newlines and punctuation remain significant. Without layout evidence a plain string must match exactly; unknown control or grapheme layouts fail closed. The adapter may also recognize the placeholder of a folded paste during initial verification, with its changing paste counter ignored. That visual check permits submission, not a delivered receipt.

Codex 0.166.0 uses textwrap 0.16.2 and unicode-linebreak 0.1.5. Beside the established ASCII and Latin letters, its box comparison knows three specific ship-authored symbols: U+00B7 and U+2192 resolve from the ambiguous class to alphabetic; U+2026 uses the distinct inseparable class. Ellipsis permits only its source-established following breaks, never an arbitrary break before it or between consecutive ellipses. A preceding space can supply a boundary, subject to the existing opening/quotation context and overflow checks. This does not classify other punctuation or establish unknown grapheme/control layouts. The pinned sources are [Codex's composer wrapper](https://github.com/openai/codex/blob/rust-v0.166.0/codex-rs/tui/src/bottom_pane/textarea/wrapping.rs), [textwrap's word separator](https://github.com/mgeisler/textwrap/blob/0.16.2/src/word_separators.rs), and [unicode-linebreak 0.1.5](https://docs.rs/crate/unicode-linebreak/0.1.5/source/src/lib.rs).

Pi 0.74.2 opts into its editor's whitespace-only word wrapping at pane width minus one. Hyphens remain inside words; overflowing whitespace can backtrack to the preceding word boundary, and an overlong word splits at the available width. This comparison establishes printable ASCII wrapping only; wrapped Unicode/grapheme/control layouts remain unverified. Short Unicode lines need no wrapping. Other adapters retain their existing break rules.

Painted right-edge ASCII padding can be indistinguishable from typed trailing spaces. Known placeholders and empty rows tolerate it; nonempty box rows stay raw for obstruction and journal ownership checks. Visual comparison may disregard row-end padding only within a known text-area bound. Text requiring trailing spaces stays unverified unless shown exactly. Even a successful visual match never replaces exact record confirmation.

**Pending input.** A submitted payload on the same pane, process and launch, still showing its exact verified display, reads as `waiting to be taken`, without a human-obstruction alert. An empty box reads as `waiting for record confirmation`, never delivered. Edited, partial, foreign, folded or unavailable pending displays require inspection, as do identity changes or an uncertain paste/submit phase. The bound is 600 seconds from the original attempt, including prior withheld attempts, inclusive at the boundary; polls, retries and service restarts cannot move it. This is an intervention policy, not a claim about normal queue delay. Expiry needs a human and appears in every session's status line; it never triggers a resend.

An unknown obstruction can be inspected with `qd watch <seat>` and captured with `qd watch <seat> --save-screen` for a scrubbed adapter fixture. When a seat needs a human, the service reports it, with the seat and reason, as a report from `ship`, and the status line continues to show it. Who is told: while a seat whose role is `systems` is up, the alarm goes to it, since it clears what a `qd` act can clear; an alarm only a person can clear, a sign-in or a delivery whose paste or submit outcome is uncertain, goes to the desk as well. Those reasons are named in one place, `PERSON_ONLY` in the service; every other reason goes to the systems seat alone. An obstructed systems seat is never told of its own door. With no systems seat up, or none declared, every alarm goes to the desk, as before. Each addressee is told once per reason: an identical reading tells no one again, a changed reason tells its addressees again, a door that clears and then shows the same reason tells again, and an addressee that becomes a recipient while a reason stands, as when the systems seat comes up, is told it then. What is told and to whom lives in the service's memory, so a restarted service may tell a standing reason once more; nothing is stored. The status line carries every alarm by itself, through tmux, whoever is told.

An unknown-screen obstruction raises that report/status alarm only after two fresh captures in the same collection show identical complete text on the same owned launch, pane and process. A changed, whole, missing or replaced second frame does not confirm the first unknown-screen alarm. These are two observations, not a guarantee about redraw duration; no timer or retained screen store is involved. Known dialogs, drafts, pending-input uncertainty and other alarms retain their timing. The first unknown reading remains closed and inspectable: suppressing its transient alarm grants no delivery or control permission.

JSON-line readers retain bounded in-process snapshots (16 records and 128 MiB of raw source bytes, with parsed state beside them). A changed or racy source is read in full and its previous complete-line prefix is byte-validated before reusing parsed rows, state or input evidence. Replacements, truncation, rewrites, unfinished final rows, failed reads and clock reversals cannot certify stale evidence; a recent equal-stamp snapshot is refreshed before it can become trusted. Public row/input lists remain independent copies. Claude and Codex identify which appended native rows can change their input evidence, including queue, consumption and skip diagnostics. Unchanged current input evidence can reuse attribution verdicts only with the same source identity, no source error, unchanged posts and no invalid ledger turns. Source validation and the entry dirty marker still run first. No record, receipt or ledger format changes.

**Following work.** When a seat starts working, the session it sits in, the Bridge or the Crew, shows that seat's window, so whoever watches the session, or a recording of it, sees the work as it begins. A start is a turn the seat's record opens after the service last read it closed (law: record-first); the record is read again only when it changes, and the service's first reading of a seat is its baseline, never a start, so a restarted service jumps nowhere. A seat in a human's session is never followed, and the switch happens only in a session this ship owns (its `QD_SHIP`), for the pane of the seat's own launch, checked in the server by its PID as the switch runs (law: identity). It is refused, and the refusal logged, while any pane of the session is in a mode, which is a human scrolling back, while any client attached to the session has had key or mouse input in the last 30 seconds, which is a human typing, and when the window would change size: tmux fits a window to the client that comes to view it, so with a client attached the seat's window must already be the size of the window shown. Nothing is typed, closed or resized; selecting a window is the whole action. A human who is watching keeps the session they chose until they leave it quiet. So that a followed window already fits, a seat's window opens at the size of the window its session shows whenever a terminal is attached to that session: tmux would otherwise size a new detached window by the most recently active terminal anywhere, which may be another session's, and the follow would then be refused. The size is set while only the window's placeholder runs, before the seat's program starts, so the program draws, and the door reads, at that size from the first; the window's own `window-size` option is unset again at once, so it is not pinned and tmux keeps sizing it as any other. With several terminals of different sizes on one session, the shown window's size is the one taken: it is the size tmux gives that session's most recent viewer, and the size the follow compares against. A session with no terminal attached, including a session's first window, or an uncertain reading, opens its windows as tmux always has. An open window is never resized.

**The status line.** Every ship session's tmux status line carries `qd status --line`, refreshed by tmux on its own timer, independent of the service and of every door: `service ok · 0 waiting · laan needs a human · worker held at limit · disk: root 94%`. The kernel-held service lock proves a live owner independently of its heartbeat: a late heartbeat reads busy, a missing or invalid heartbeat stays unknown, and a released lock reads down; `qd up` restarts a dead service. This is how a dead service never looks like a healthy idle ship, and how an alarm reaches the human without passing through the Desk's own door.

The service may atomically publish an optional `runtime/status-line.json` rendering. Plain canonical text status jobs can reuse it for at most three seconds from collection start, checked against both wall and monotonic clocks. They independently verify the live lock, heartbeat PID and age, process start identity, declaration fingerprint, framework source stamp and installed-copy handoff. A restart, busy owner, clock reversal, source/version change or missing, stale, corrupt or unreadable cache falls back to the ordinary reader; failed or refused collection discards its prior disposable rendering instead of renewing an old success. Unreadable fallback evidence is an explicit status-unknown alarm, with null facts in JSON rather than invented counts. Other JSON readings, lifecycle, receipt and usage decisions never consume this presentation file. Its versioned disposable contents are ignored by older revisions; heartbeat, record and ledger layouts are unchanged. The canonical text console path uses the verified rendering when available and otherwise collects the ordinary current facts directly, without importing unrelated command verbs or constructing their parser. Other commands retain the ordinary parser; installed-copy handoff is unchanged. The three-second presentation bound accommodates roughly two-second actor cycles and their observed scheduling gaps; owner death still invalidates a rendering immediately through the independent kernel lock check, and a late or unreadable heartbeat refuses it even within that age. This lifetime applies only to rendered text, with no change to record-source certification or receipt/lifecycle evidence.

Presentation demand comes from a fresh native tmux client listing for the declared sessions. A complete listing with no attached client skips collection; missing, malformed or unreadable client evidence collects conservatively. The service checks due presentation between duties and during its existing one-second sleep after actor work, targeting 0.7 seconds between collection starts. Actor and record duties retain their sleep-after-work cadence. A blocked duty or failed collection may still leave a miss; neither changes the three-second trust limit or renews the old rendering. The independent tmux command then reads fresh facts, including down, busy and unknown alarms. No client listing or presentation deadline authorizes a lifecycle action. Pane queries use exact pane IDs and current PID/width evidence; screen identity and capture share one fresh server command queue, with the saved launch rechecked before the frame is returned. An idle delivery duty uses that single owned frame for its obstruction reading; an actual delivery still obtains its own fresh door and lifecycle evidence. There is no pane cache.

None of this is a setting. The ship file declares a ship; it is not a settings file for the framework. If a behaviour ever needs a knob, the knob goes in the ship file under a table named for the part it tunes, because one file is the only place a ship is configured, and each such knob is a default the framework should have got right. Ship sessions keep a 50,000-line history so the scrollback holds days, not hours, and no window size is ever fixed.

`qd watch` prints the table above; `qd watch <seat>` prints the full reading.

## 9. Ledger

Record accounting has one lazy SQLite transaction per service pass, independent of how many historical launches, quota events or turns it contains. The service collects program records and screens before writing, then calls the existing record writers with `commit=False` inside `Ledger.record_pass`. That boundary commits once if rows changed; a pass with no new record information and no due usage attempt issues no DML, BEGIN or COMMIT. Standalone writers keep their commit defaults. Usage refresh runs after the record boundary: each real usage attempt owns its own transaction, so the bound is one record commit plus the number of due attempts, not the number of historical rows. Provider calls never run inside the record transaction. Usage attempt and hold persistence must retain the same independent atomic owner when adapters add their own pacing evidence.

The writer alone sets `synchronous=EXTRA` and verifies that SQLite returns 3. Journal mode, existing tables and compatibility triggers are retained; there is no WAL migration or background checkpoint. [SQLite documents](https://www.sqlite.org/pragma.html#pragma_synchronous) that rollback-journal FULL can lose the last commit on some filesystems after a power cut; EXTRA also syncs the directory when a DELETE journal is removed. The guarantee still depends on working filesystem locks and storage honoring sync. Read-only status/watch connections set no pragma and change no schema. Older readers retain the same tables; an older writer after rollback uses its own connection settings and existing invalidation triggers.

Launch imports compare a record/wal metadata fingerprint and the current saved launch/price, then compare rows before inserting or updating. Wall observations fill only previously missing evidence and supersede only still-active matching screen rows; identical observations do not rewrite their rows or observation time. Record error markers also compare values before writing. A native record change can still require parsing and comparing its complete turn history: the service invents no offsets or new incremental adapter protocol. New launch/pricing evidence forces reconciliation even when record bytes stand still. Order attribution still follows the same post graph, input evidence and overlap rules; a changed turn invalidates the same side evidence through its existing triggers.

Record fingerprints, failed-read retry state, machine meters, launch-import cache and attribution cache are staged. Only a successful transaction publishes them; an exception discards speculative progress. No persistent checkpoint can run ahead of committed rows, and a service restart rereads source history. Unchanged known-reader failures are retried at most once a minute by accounting, with duplicate errors neither rewritten nor logged every pass. Unknown/conflicting reader evidence remains visibly unresolved and is reconsidered when its record/reader/launch evidence changes; no unknown turn count becomes zero. The attribution service uses the same bounded transient retry, while its standalone replay API retains immediate retry by default. Establishing an old unknown reader and its actual turn count is a separate settlement task.

Reader-registry membership is shared by `bindings()`, `register()` and attribution replay through a context local to exactly one `Service.account()` invocation, including its existing seat join calls. The read-only consumer accessor `registry_events(folder)` uses the same coherent registry observation as indexed membership; attribution still enumerates every seat folder, including retired seats. An unchanged registry is parsed once in that pass; exact full-row membership is indexed by record, with extra fields and unknown reader evidence preserved. Each reuse checks device, inode, size and nanosecond modification/change times. An observed change forces a fresh parse; a read whose before/after metadata differs is returned under the ordinary reader rules but is not cached. Metadata failures also bypass the cache and keep the ordinary reader/error path. This observes coherent local metadata changes, not edits hidden entirely between checks or changes to a result already constructed by `records()`.

An already registered row needs only read access. A missing row discards that registry's cached membership, then uses the existing write-mode open and exclusive lock, freshly rereads under the lock and appends only if the exact row remains absent. A competing process that appended the row first therefore causes no duplicate append. A later lookup rereads after any write attempt, including a failed one. Changed registries and new-row rechecks can require additional parses; the once-per-pass bound applies to unchanged registries with no new rows. No lock spans record reading or accounting. The context resets in `finally` on success or failure, and nested invocations restore their enclosing context; no cache is retained on a service or seat. Public `events()` and callers outside an account context remain uncached. Repeated parsing of `record-launches.jsonl` is outside this registry bound and remains unchanged. Registry/launch formats, reader selection, provenance and the database transaction/cache-publication boundaries are unchanged.

Pools: utilization for each window the provider exposes (five hours, seven days), reset times, burn (1.0 means on pace to use the whole quota by reset), a wall when a window is spent, and a stale flag when the reading is older than the provider's cache floor. A spent window stays a wall until its own reset: a failed, rejected or hour-old read keeps it, marked last known, and only a newer valid reading with room or the window's own reset ends a wall, so the door, failover and detailed status retain it through a missing read. A wall is a fact to route around, not an alarm. Claude Code's usage endpoint is shared by every caller on the login, the crew's seats and the Admiral's own sessions alike, so a Claude pool is read at most every five minutes, while a seat runs on it or once before a move to it. A failed read keeps what came back as the reading's error (the HTTP status with any Retry-After, a timeout, a network error, bad JSON; never the token, another header or the body) and is logged as a `usage` event in the service log; a refusal with Retry-After holds the pool that long, at least the interval and at most an hour, and the hold is logged too. A state that makes no provider call (a record reader with no snapshot, a missing credential or token) is logged only when its reason changes, and again after a good read, so the log keeps how often the provider refused without repeating a steady state. The read pacing survives a service restart: the first read after it waits out the interval from the pool's stored attempt time; the Retry-After hold is kept in memory only. An API key pool has no windows. Its row is spend where cost is established, with unpriced turns counted separately; no price catalogue is carried. A `budget` in the pool's declaration makes a wall of measured spend, without treating unknown spend as zero.

Claude consumes general and model allowances from the one usage response it already fetched. General `five_hour` and `seven_day` objects retain their `utilization`/`resets_at` mapping to ungrouped 5h and 7d windows. Named model windows such as `seven_day_sonnet` map to `sonnet / 7d` with group `sonnet`. Fable, Sonnet, Opus and Haiku are distinct canonical families. A Fable row supplies no Sonnet constraint; shared cap charging is unproved and is never inferred from similar names or a historical field spelling. An exact model name in a native named window or list display name establishes that row's own scope. A null optional named window is absent. In `limits[]`, a model row has nested `scope.model.display_name`, numeric `percent` in [0,100], string `severity`, ISO `resets_at` and boolean `is_active`. An inactive flag does not cancel a wall. Critical, exceeded and error severity explicitly prove a wall independently of the fraction. The actual fraction remains unchanged.

Installed Claude Code 2.1.317 classifies `kind=weekly_scoped` rows as Current week and constructs them with `group=weekly`; its schema explicitly says kind classifies the server meter, while group only controls rendering. That exact kind proves 7d and takes precedence over reset inference, even if no reset matches or several do. Other native kind enums and durations remain unproved; group alone never establishes a period. If kind supplies no proved period, the fallback requires exactly one general window whose reset is within an inclusive absolute two seconds of the model reset. The bound covers the ordinary-read offsets of 0.15 ms and about 1.0002 s, while rejecting a difference just beyond two seconds. Unknown provided enums/types are diagnosed; a unique reset inference is identified by this policy, never by guessing their meaning. With no match or several matches the stable name is `<family> / unknown period`; the known fraction/reset and explicit wall remain, while availability is unknown. An unrecognized model scope uses group `unknown`, not a guessed family. A known family with malformed measurements stays unknown. Only entries producing no window, including a null non-model scope, contribute to `unmapped limits: N; key/type shapes: ...` in the latest reading detail. Retained explicit-unknown windows, malformed mapped fields, uncertain periods and unrecognized kind/group values are described separately as `limits diagnostics: N; key/type shapes: ...`; a malformed list container has its own diagnostic. Only top-level kind/group scalar strings consisting of 1–32 ASCII letters, digits, hyphens or underscores can appear as `{type: str, word: ...}` in a diagnostic. Empty, longer, non-ASCII, punctuation, whitespace or non-string values remain types only. Every other field and all nested values remain key/type-only, with no account, token, header or body scalar values. Malformed list containers are visible too. A confirmed null scope creates no model window. No live capture or extra provider request is used; the first ordinary scheduled read after signed installation is compared with the retained reader's same-minute projection.

The stored change is `pools.exhausted TEXT NOT NULL DEFAULT ''`, exposed as `reading.exhausted` in JSON. It stores versioned evidence bound to the pool/window, group, blocking flag, fraction, reset and reading time; JSON exposes the validated boolean. Numeric evidence normalizes both signed zero forms to the SQLite REAL representation, so critical -0.0 remains an explicit wall without changing its zero fraction. The writer migrates it normally; a read-only older book projects false without writing. If an older writer replaces any bound part of the measurement, its leftover evidence no longer proves a wall after re-upgrade, and the reading is unknown rather than proved room until a newer native observation. `Window.exhausted` carries the explicit native severity wall and ordinary percentages/resets still apply. The existing row error records unknown period and the existing `usage_reads.error` carries safe unmapped-entry diagnostics. No account/body/header scalar data is retained; diagnostic scalar values are confined to the kind/group word allowlist. Missing windows and failed/stale observations retain prior complete spent evidence, including an explicit wall, until reset or a newer good reading of that window. Older code ignores the added evidence, so downgrading loses severity-only walls below 100% while that old code runs; native percentages and other stored columns remain readable. A newly proved period can replace the installed unknown-period identity without leaving automatic room blocked forever. The adapter declares the prior name and a two-second reset-continuity bound in internal Window.replaces metadata. During the ordinary cache write, exactly one accepted, fresh, newer, uncertainty-free replacement must match the old complete row’s model group, bucket, blocking flag and reset within that bound. The old name must be absent from the new observation; failed/stale readings, malformed or ambiguous replacements, different identities/resets and old observations preserve it. Only the exact matching current-cache row is retired, with its obsolete missing-row diagnostic; no source, record or historical accounting data is removed. This restores primary-like known room and preserves secondary-like critical spend on upgrade from 34abc0b. There is no stored schema or status/ledger JSON field change.

Routing, door walls and held-seat status apply the same adapter-owned family scope. General windows apply to every model. Automatic destination selection requires current relevant windows, including reported matching-family rows; an unknown other family cannot block it. An absent family row imposes no additional constraint on a legacy general-only body. A known matching row with missing, malformed or stale measurement is unknown and cannot prove automatic room. Explicit selection may still move on unknown usage, but refuses a proved matching or general wall. Source scope uses the running model from record-first evidence, never an unconfirmed declared model. Destination scope uses its own resolved choice. Unknown running family cannot prove a scoped wall; an unknown destination family with scoped rows cannot prove room. Detailed status/ledger and JSON line facts retain each model window and reset; session text remains held-seat alerts only.

Every subscription adapter that reads usage names its headline windows: Claude selects 5h, falling back to 7d when a good read carries no five-hour figure, since the provider reports none for some accounts: the headline then says the provider reports no 5h window rather than unknown, 5h returns when a good read carries it again, and a failed read still reads as unknown; Google selects its 7d Gemini window; Codex selects both 5h and 7d, with an absent expected window explicitly unknown. Status and watch show those cached windows even without a live seat; unsupported adapters, key pools and endpoint pools gain no invented subscription reading. The text status line carries operational alerts. It names an up seat held at its current limit only when none of its declared destinations has proved room in the recorded evidence. Routing and status use the same cached eligibility predicate and later-then-earlier candidate ordering. Lifecycle guards can defer a move with an eligible destination without creating a held alert. The service keeps its ordinary paced foreground read before a move and re-evaluates that predicate after recording the result. Status commands make no provider request, so an unread destination supplies no proved room until the service reads it. An unreadable ledger makes held-seat evidence unknown. Detailed status, ledger and JSON line facts retain walls, windows, reading dates, age and failure reasons. The line uses the existing 160-character presentation budget for alert names, then counts every affected operational category and points to qd status. The all-category count fallback can exceed that budget. Grant-expiry alerts retain their dates.

Codex 0.166.0 supplies subscription observations in `event_msg` / `token_count` / `rate_limits` in its own record. The `codex` limit id identifies the allowance, not an account. `window_minutes` identifies 300-minute and 10080-minute windows regardless of primary/secondary slot; `used_percent` is provider-reported utilization, and `resets_at` is UTC Unix seconds. The event timestamp dates the observation, never the service's read time. Each minute the service selects the newest eligible snapshot across current joined Codex records whose saved launch names the pool, excluding entries before that launch. It does not scan historical or personal sessions, query credentials, or assemble windows from different snapshots. A newer partial/failed snapshot goes through the existing retention errors rather than selecting an older complete one. An older observation cannot replace a newer retained tuple; an observation at or before the latest failed attempt cannot clear that failure. Missing, unreadable, untimed, future or conflicting evidence cannot certify a current measurement. A restart without a post-launch snapshot therefore leaves dated retained values or unknown; repeated reads do not renew their age. A current supplied blocking window can establish a wall before a request fails, but an absent expected sibling cannot establish a fully known/open destination for automatic failover. Binding relies on the saved paying pool: these record events do not identify the account. No store or schema is added.

An endpoint pool may state `[pools.<name>.price]` with `currency = "USD"`, `unit = "million_tokens"` and all four numeric rates: `input`, `output`, `cache_read`, `cache_write`. Rates must be finite and nonnegative; booleans, incomplete declarations and other units/currencies are refused with the pool name. Zero explicitly states a zero price. Omission means unknown. Adapters map these rates into their program's supported model configuration; unknown rates are omitted, never written as null or zero. Pool rates override selected-model template rates so the ship declaration remains the price authority. The effective rates and model are saved with the actual launch and owned-record launch journal. Only an explicit matching step model and an unambiguous turn interval can use them; edits to current pool settings never price earlier turns.

Pi and OpenCode default omitted model rates to zero internally, so a zero cost in their records alone does not prove free usage. Their readers retain that recorded value separately and require stated launch evidence to establish zero cost. Measured nonzero step costs remain usable even beside unresolved siblings. Each endpoint step retains its recorded amount, tokens and explicit model; the display model is never price evidence. Known step amounts form a partial numeric turn cost, while `unpriced_steps` marks missing/invalid costs or uncertified zeros. Rollups count every such turn as unpriced even when a supported partial amount is present. A late source refresh can resolve or introduce uncertainty; preserving historical cost never overrides new step evidence. The Ledger keeps `recorded_cost` and `cost_basis` in a separate `turn_costs` table without rewriting historical numeric values. An old zero with no basis remains uncertified, neither declared free nor called fabricated; an owned-record refresh can establish its meaning only with available source/launch evidence. Missing old records or missing launch evidence cannot be repaired by today's pool settings. Historical nonzero record costs are retained on a later incomplete read. Rollups expose `cost` and `unpriced` independently in JSON: all unpriced is null, genuine measured zero is zero, and a partial numeric text total carries `+`.

Compatibility: the preceding service keeps the original 22-column `turns` and four-column `record_launches` layouts, so its reads and writes still work after the new service. `turn_costs` and `launch_prices` hold the added evidence. Ingestion names the stored turn and tool columns for both reads and writes; source-row names do not change the tuple-based public queries or the on-disk layouts. Insert/update triggers invalidate cost evidence when an older writer refreshes a turn; the next owned-source read can establish it again. Raw evidence is retained while invalid; it cannot certify current cost. Old numeric nonzero costs without side evidence remain recorded costs, while old zeros without evidence remain uncertified. Older readings cannot display these new uncertainty semantics.

`launch.json` and endpoint `model.json` retain their preceding keys. Adjacent `launch-price.json` and `model-price.json` bind price evidence to the file's publication (inode, size, modification/change times and content digest); a rewrite by the previous version, or a missing/malformed side file, leaves price unknown. Copying those files to different inodes also fails closed; the durable owned-record launch journal preserves previously established historical prices. Pool price declarations and extra fields in the record launch journal are ignored safely by the preceding version; generated program price fields use the programs' existing supported configuration.

Turns: a row per ended turn, from the record. Tokens in as many classes as the provider bills, four for Anthropic: read cached, read uncached, cache written, written; cost where the program states it; the tool calls made, by tool, each with its duration and whether it failed; the turn's duration; and the turns of any subagents the seat spawned, charged to the seat. The three headline measures, read cached, read uncached and written, stay the display; the rest is a column away.

What a record did not hold is counted and marked, never guessed and never hidden. A token class a provider never reports is zero within an actual measurement; an absent, malformed or unrecognized whole measurement is unmeasured. Explicit measured zero is complete. The common validation lives beside `Tokens`; each adapter identifies its format's measurement presence, including proto3's present message with omitted zero scalars. Measured sibling steps remain in the total, with missing steps counted. A step whose usage the record does not hold, a turn whose duration the record did not state, a tool call without a verdict, a record that would not read: each is counted where it belongs, and every figure built on such turns carries a trailing `+`, meaning at least this much; the tables say so in a line. The book has one writer, the service. `qd status`, `qd watch` and `qd ledger` open it read-only, so a reading never writes, and a newer `qd` never moves the schema under an older service.

Machine: the service samples each seat's process tree every tick and charges the turn with the CPU seconds it used, its peak memory, the most processes it had running at once, and the bytes it wrote to disk, read from the processes' own I/O counters. Tokens say what a seat cost the provider; this says what it cost the machine, which is the shared thing on a box where five seats running a test suite at once have frozen the desktop, and where disk has filled more than once with nobody able to say which seat was writing. The status line shows the free space on every filesystem the ship writes to, the runtime's, the workspace's and the system's temporary space, and when one runs low it names the seat that wrote most in the last hour, so the question "who is filling the disk" has an answer before the disk is full.

Seats and orders: the same rows, rolled up by seat and by the order each turn was charged to.

Order attribution is cached in `turn_attribution`, keyed by record and turn, beside the unchanged 22-column turn and five-column tool layouts. The legacy `order_id` remains for preceding readers/writers; replay never updates turn rows, cost evidence, tools, usage or launch provenance merely to change attribution. The side row records verified message ids/times, the seat/turn bounds they belonged to, verdict, roots and evidence routes. Every insert/update, from either version, leaves attribution pending until full service replay; ingestion never certifies the narrower evidence in `turn.input`. Existing side evidence is preserved while invalidated, and a new key without a verdict also forces replay even when source fingerprints and posts are unchanged. New readings display pending/legacy until service replay; the preceding version ignores the side table and retains its older attribution behavior.

The service revisits every stored turn on startup, changed post evidence, changed source evidence or invalidated verdicts, including retired seats and records whose files have not changed. Saved reader bindings choose the adapter; unknown bindings are never guessed from record content. Missing records do not delete measurements or established provenance. Previously verified incoming evidence may be retained only for unchanged seat and turn bounds, and is marked retained, not a fresh source read. Changed bounds require fresh evidence. Reconciliation is idempotent. Status, watch and ledger readings open the book read-only, never migrate it or run replay.

Replay checks source fingerprints, complete post values and pending verdicts before rebuilding the thread graph. An unchanged successful pass skips that construction; a failed source read is retried, and only a completed replay advances the remembered post snapshot. New turn keys and measurement-only refreshes still force full reconciliation through the existing invalidation triggers.

Attribution replay excludes source paths outside its runtime before any fingerprint, stat or read. A legacy reader/path/launch binding without a saved fingerprint supplies no authority to read that external source. Those stored turns remain counted and unassociated with the reason `legacy binding outside the runtime, no saved fingerprint`, including when outgoing posts or claims could otherwise provide a fallback. This attribution-only boundary leaves ordinary harness accounting and receipt paths as they were.

`qd ledger` prints the pools; `qd ledger --by seat` and `--by order` print the rollups, with tokens, cost, tool calls, minutes, machine load and bytes written side by side. The Ledger is one SQLite file in the runtime; ingestion is idempotent, so a turn read twice is counted once.

## 10. Standing orders

Three tiers of document, each in its own file, each growing at its own pace, none allowed to become another:

- **Laws**, `laws.md`: what the framework itself guarantees, enforced in code and tests. One page, few by construction. They change rarely.
- **Ship's orders**, the ship's own `orders.md`: how this crew behaves. The ship changes them at will. The framework carries them to every seat and does not read them.
- **Cards**, `roles/<role>.md` and `harnesses/<name>.md`: facts a seat needs about its role (accountable for, may change, call when, never) and about its own program. They change with the crew and with program versions. The generic role cards are captain, desk, engineering, worker and hand; the hand is a worker on a small model served locally, told how to work an order step by step, to verify before it reports, and to ask rather than guess.

A seat's boot read is the laws, its ship's orders, its role card, its harness card and its inbox. Target: under 3,000 words, against about 21,000 today. `qd brief <seat>` prints exactly what that seat reads at boot, so a human can read what the agent read.

**Ours, and exposed.** The brief is Quarterdeck's own instruction set, independent of whatever `CLAUDE.md` or `AGENTS.md` a user keeps, and every word of it comes from a file the user can edit. The framework's `standing-orders/` folder holds `laws.md` and the generic cards. A ship's folder holds its `ship.toml` and `orders.md`, and may hold any card under the same path, `roles/<role>.md` or `harnesses/<name>.md`, which then replaces the framework's for that ship, and `homes/<harness>/`, the program's own settings files as this ship wants them, in the program's own format. To change what every seat reads, edit `orders.md`; what one role reads, its role card; what one program is told about itself, its harness card. The laws are the framework's, and the one part a ship does not override. Nothing is hidden in code: `qd brief <seat> --sources` prints which file each part of the brief came from, and names any instruction file a program will still load from elsewhere, for the programs that have no switch to stop it. Changing them is editing a file: the Desk, carrying the operator's word, edits `orders.md` or a card as it would any other file, and who may do so is a matter for the ship's orders, not the framework. An edit is an event like any other: the service re-renders the briefs it touches and tells each affected seat with an ordinary message from `ship`, `qd > ship's orders changed · read brief/scott.md`, and a seat coming up or starting fresh reads the new brief by itself.

The service's brief stamp hashes the text produced by the ordinary brief renderer for each resolved seat. It therefore follows ship name, operator and folder, seat name, role and display name, selected program and its human-tool policy, session ownership, and the laws, orders and selected cards, including fallback text. Moving a seat between crew and human sessions, or changing its session's human flag, refreshes the file on the next service pass without a card edit. Unchanged text does not rewrite the file or post a notice, including card timestamp changes and edits to unrelated ship settings. An unresolved selection keeps its existing hold and cannot acknowledge a complete pass. Each stamp pass reads and renders each resolved brief once in memory and reuses that exact text for publication; edits arriving later remain visible on the next pass. A seat resolved only after the stamp also waits for that next pass. This adds no timer or store. Pending upgrade rebrief requests retain publication ownership and their durable notice baseline.

**Each ship, its own orders.** A ship carries the orders and the cards for its own crew: a ship of three reads three cards about its three roles, and a ship of twelve reads its own. The framework's `standing-orders/` folder holds the generic cards a ship starts from and keeps or replaces card by card. The default ship's orders say how its crew lands code: the captain reviews a change once, reproducing what it doubts, and the desk lands it when the review is clear and the suite is green.

**The operator's word becomes the ship's.** The operator speaks briefly, often from a phone, and may be wrong in a detail; a quotation of what they said is not a rule. The desk asks until the intent, its scope and its implications are clear, then writes the rule in its own words, clean and unambiguous, in the file that owns it: the ship's orders for how the crew behaves, a role card for one role, the ship file for one seat. A change to the framework goes to the captain as an order, and a dispensation for the matter at hand is an order that names its scope and its end. Nothing durable lives in a seat's memory or context, and a seat's home runs its program with its own memory off, so the ship's files are the only place a rule can be and the only place anyone need look for one.

**How the brief reaches a seat, and nothing else does.** Every program loads instruction files of its own. Claude Code reads every `CLAUDE.md` from the working directory up to the root and combines them, root-most first, with the one in its home; checked on 7 November 2026 with three nested folders, all three were loaded. Codex reads `AGENTS.md` the same way, and the others have their equivalents. A ship's seats use the ship's instructions and nothing else. Claude Code is launched with `--setting-sources user`, which the same probe showed loads no instruction file from the working directory or its parents, and its home is ours; Codex is launched with its own switch for the same, pinned in the spike; where a program has no such switch, the brief states the precedence in one sentence: where these orders and a file the program loaded disagree about the ship, the orders win. The brief tells a seat where the workspace's own notes live, and reading them is the seat's work like reading any other file. Quarterdeck never writes a user's instruction files and never relies on them: the brief is complete on its own, and the fake harness, which loads no instruction files at all, is fully briefed by it. The brief is rendered to `brief/<seat>.md` in the runtime and reaches the seat by the channel its adapter declares: a file appended to the program's system prompt where the program takes one on its command line, which costs no turn; a configuration override where that is the program's way; or as the first message otherwise. In every case the seat's open messages follow, under a header saying the seat was briefed and with what: `qd > briefed as scott, engineering · 2 orders open`. The consequence worth wanting: ship doctrine that lives in a person's instruction files today, because there was nowhere else to put it, moves into the ship's orders, and those files go back to being about the person and the machine.

What keeps the laws few is not a number but a test of admission: a law exists only if the framework enforces it in code and tests. A rule nothing enforces is an order, not a law. A framework of a few thousand lines holds only so many such guarantees, so the page stays short by construction. If it ever needed a second page, the framework would have grown, and that is the thing to look at, not the page. The other habits: a law's statement is one or two sentences, its reason one sentence beside it, its history in git; laws have ids, not numbers, so retiring one never renumbers the rest; and the laws are grouped by the part that enforces them, so a reader who knows the parts knows where each law lives.

The connection to code is a comment and a command. Wherever code carries a law, the line is tagged with the law's id:

```python
# src/quarterdeck/door.py
def deliver(seat, text):
    clear_known(seat)                                # law: one-door
    paste(seat, text)
    shown = screen(seat).box
    if not matches(harness(seat).box(text), shown):  # law: one-door
        return Withheld(seat, text, shown)
    submit(seat)
    return confirm(seat, text)                       # law: one-door
```

The same tag goes on the tests that prove it, and the test tagged with a law tries to break it and fails to. `qd laws` finds every tag and prints each law with the lines that carry it:

```
one-door   Everything typed into a seat goes through one path, in one process: it clears what it ...
           src/quarterdeck/door.py:158, 176, 190   tests/integration/test_door.py:40
```

A test fails when a law has no carrier, or a tag names a law that does not exist. Reading the law, you can jump to the code that enforces it. Reading the code, you know why a check is there.

## 11. The laws, second draft

**Ship**

- `ship-file` `qd` reads its configuration from the ship file alone; the ship file is the only configuration a ship has.
- `nothing-leaks` Nothing from the runtime enters a repository: no ids, records, credentials or usage.
- `one-folder` The `qd` program writes only inside its project folder: a ship's declaration, which it commits, and a ship's runtime, which git never tracks. The user's instruction files, program configuration and code are read, never written. The one exception is a pool's credential file: when a seat's program refreshes its token, the service puts the refreshed file in the pool's place, so the pool and every seat on it stay signed in.

**Harness**

- `one-record` A seat is joined to one record, the first written after its launch. An ambiguous join is reported, never guessed.

**Seat**

- `identity` A seat's identity is its pane id, process id and record. Names and titles are display.
- `one-door` Everything typed into a seat goes through one path, in one process: it clears what it knows how to clear, refuses what it does not, types once into an empty box, checks the box as the program shows it, submits, and confirms by the record. It never types into a session the human owns. Never resend what you cannot confirm.
- `context-is-cache` After any restart or fresh start a seat receives its brief and every open message in full, except a message its provider refused, which it receives as a notice without the text while the sender is told; so a seat may be relaunched at any time and the ship loses nothing it sent. Where the open messages are too long for a seat's first message, that message gives a short account of each and names a file that holds them in full, which the seat is told to read whole before it acts.

**Watch**

- `record-first` Read a seat from its record first and its screen second. A reading that could not see something says so, and never reports a default as a fact.
- `nothing-waits-silently` Every withheld or blind delivery, every seat needing a human, every seat held at a limit with no eligible declared destination, a filling disk, a grant about to expire and a dead service show in the status line of every ship session. Tmux refreshes the line independently of the service. Its text contains operational alerts only. Detailed qd status and qd ledger show provider allowances.

**Post**

- `post-is-files` Messages are immutable files addressed to seats by name, whatever program a seat runs. The service renders inboxes and delivers each message once, in full, through the seat's door or its watch.
- `open-until-closed` An order stays open until its addressee reports on it. Acknowledgments claim; they never close and never wake.
- `events-not-clocks` No seat is asked to poll. The service wakes seats on arrivals and retries withheld deliveries on one tick.
- `can-post` Every seat can run `qd post` from its launch: the adapter grants it through the program's own permissions and sandbox, and `qd check` proves it by posting once.

**Ledger**

- `every-turn-accounted` Every turn is accounted, by pool, by seat and by order, from the harness's own record, or counted unattributed and reported.

Retired from the first draft: "stalled means it moved and then stopped" is the Watch's definition of stalled; "walls are normal" is advice on conduct and belongs in a ship's orders; "the framework carries no law about code" is the scope statement in section 1, and nothing in code enforces it, so it is not a law. Restated after the review of 6 November: `ship-file` promised a runtime derived from the file and a file never edited by hand, neither of which code can enforce; `context-is-cache` promised what agents put in their posts; `events-not-clocks` forbade the clocks the Watch runs and the ticks the service needs, since the standard library has no file watcher; `every-turn-accounted` denied the unattributed turns section 7 admits. Two added: `nothing-waits-silently` and `can-post`. Declined: a wall law, because a wall is a fact to route around and the status line then showed it; a human-first law, because `one-door` already never types into a person's text. Renamed on 7 November: `exact-join` became `one-record`, because the word exact read as a demand for exact program versions, and versions are best effort by design; the law was always about the record.

The flagship ship's orders begin: the Admiral's word reaches the bridge through the Desk; the Captain turns it into orders; no change reaches the ship's code until independent agents have reviewed it, it has passed its tests, and the First Officer has signed it.

## 12. Tests

Four layers:

1. **Unit.** Pure logic: the ship file and its line editor, message records, inbox rendering, the typed form, attribution, the Ledger's arithmetic, the status line from a fixture state.
2. **Contract.** Each adapter against recorded screens and transcripts, one directory per proven version, with a check that every proven version has a fixture set; `qd check <harness>` is its live counterpart, and narrower: it proves that the installed program launches, takes a paste its record confirms, does one task and is read, and leaves every comparison with recorded files to this layer. Every interruption the adapter knows has a screen in the set, every control has the state that confirms it, the box's folding of a paste is recorded with its counter, and the claude set includes a subagent transcript.
3. **Integration.** The Drill on a real tmux server with `qd-fakeharness --as claude` or `--as codex`, a small program in the shape of one of those two: it shows a box that folds a long paste, a dialog, a program that queues while working and one that does not; it accepts a message, works for a while through steps, writes the record in the shape it takes, and replies. The other programs are proven by their contract fixtures and by `qd check`, not by the drill. Every seat sends to every other seat and the Watch confirms each delivery; the service is killed mid-delivery and recovers with no message lost or doubled; every seat is relaunched fresh and the matrix runs again; the Office seat is reached by its watch and never typed into.

   The crash check requires the public fresh delivery receipt, one delivered attempt, and one acceptance in the record. A dequeue and its later input echo may both describe consumption of the same enqueue; these count once by their original acceptance time, provided consumption is timed and valid. Separate direct acceptances and distinct enqueue times count separately. Queued, untimed or stale evidence cannot satisfy delivery. The simulator's independent submission count must also be one: input evidence alone cannot distinguish separate identical enqueues sharing a timestamp, and a live drill lacks that simulator counter.

   Private suite fixtures and the standalone fake drill allocate a fresh mode-700 namespace outside tmux's shared socket directory and use its exact `-S` endpoint. `TMUX_TMPDIR` supplies an existing transport root when set; fallback is the framework project’s ignored `work/`, never an arbitrary caller directory. Paths, including a replacement suffix, must fit the native socket limit. The namespace creator creates its mode-600 lock/header; bound children and observers open only that existing validated regular lock, use `-N` to avoid bootstrapping a server, and gain no cleanup authority from `QD_TMUX_SOCKET`. Opening uses `O_NONBLOCK`/`O_NOFOLLOW` and checks the actual opened inode, so unfamiliar special files refuse without blocking or being repaired. Public generic observer commands accept only the known query/buffer/key transport queues; other commands, including mixed shutdown/unknown queues, refuse before dispatch. Required session, pane and status operations build fixed commands through the private validated dispatcher, preserving their target/session-token guards; whole-server shutdown remains creator-only. Named `-L` bindings and the ordinary/default server retain their existing behavior. Older framework revisions do not understand this new absolute private binding; a kept private drill needs the matching code or its printed native `tmux -S … -N` command, while existing ship declarations and record/ledger formats remain unchanged.

   A creator-started private server uses `exit-empty off`, so bound CLI/service observers can continue between sessions; its creator ends the server lifetime. A genuine last-session exit with that native option enabled still requires the same proved-dead endpoint removal before creator restart. Suite setup explicitly starts the creator before testing CLI observer launches. A session fixture also isolates intentional named/default no-server probes with a fresh short `TMUX_TMPDIR`. With the outer variable unset, the anchor is the fixed short `<project>/.testruns/s`, the project being the parent of the Git common directory, so the checkout, every linked worktree and every run checkout of `tests/testrun.py` share it; the folder is private, ignores itself and must be proven ignored by Git, and a link or a foreign or shared directory in its place refuses. It budgets the real nested isolation layout and native UID/PID/replacement names before allocation and keeps a margin of 12 bytes below the native limit on the deepest socket the suite generates; an irreducibly long project anchor refuses honestly rather than using shared or arbitrary temporary directories. It restores the caller’s environment and removes only its exact empty native UID directory and root with `rmdir`. Outer test containers retain their original directory descriptor through setup/teardown and compare identity before empty-only removal, including setup failure; replacement, nonempty or uncertain containers remain with a reason. Socket namespaces stay outside pytest and drill data trees that may be removed recursively.

   Creation, managed replacement and cleanup serialize through this namespace lock. Only known native query and buffer/key transport queues share the namespace stability lock, with a single nonblocking acquisition; server/session/window lifecycle commands, options and any generic or mixed queue outside that set take it exclusively and cannot bypass `-N` on a bound observer. Exclusive acquisition has one two-second budget (`EXCLUSIVE_WAIT`), then refuses with ownership uncertainty. A holder holds the lock for one tmux client command, which a loaded machine can take well over a quarter second to run, so the first budget of 250ms failed ordinary lifecycle and cleanup steps under a parallel suite; two seconds outlasts a slow command and still bounds a stuck one. Close takes at most two such acquisitions (four seconds aggregate), plus its existing bounded two-second shutdown check; lock expiry is not retried. Suspended holders therefore cannot indefinitely block status or confer cleanup permission. Private lock/ownership uncertainty propagates through pane/server reads instead of becoming a missing pane or server; status retains its independent service alarm, and lifecycle callers hold. Synthetic polling retries only that uncertainty within its existing deadline. The busy-actor fixture pauses between native namespace operations; separate held-lock cases exercise actual lease contention. Waiters revalidate the directory and actual held lock after acquisition. Creator evidence is separate for directory, server birth nonce/PID/start and the socket inode retained by descriptor. Cleanup stops only the proved server through an in-server identity condition, then requires ended-process and refused-connection evidence (a process whose `/proc` entry is gone, or reaped between opening and reading it, which the kernel answers with ESRCH, has ended; any other read error still refuses) plus the same socket identity before unlinking the exact endpoint under the held lock. Any observed replacement, live or uncertain endpoint is retained with a reason; a refusal alone is not ownership proof. Only the exact owned lock is removed when no peer or unfamiliar entry remains, followed by `rmdir`; socket roots are never recursively swept. This guarantee covers framework-managed operations following the lock protocol. A same-UID process mutating the namespace without taking that lock is outside it; ordinary POSIX unlink cannot atomically guard against such a swap.

   Ordinary successful completion removes private leftovers; failed or interrupted cleanup with known ownership takes the same path. Unprovable startup/cleanup or uncatchable process death can leave an explicitly held project-private namespace, never authorize adoption or a sweep. Drill data is retained if private shutdown is held, so recursive data cleanup cannot erase a live/foreign peer. `--keep` preserves the server, namespace and drill data, prints the quoted absolute endpoint/session command, and restores the caller’s previous transport environment. A kept namespace remains until its creator explicitly closes it; transport-only observers cannot reclaim it.

4. **Live drill.** Opt-in, real programs on throwaway seats, the same matrix plus one duty per role from its card and one task per seat that the drill can check without reading prose: write a named file with given contents, run a given command and report its output, post a report with given words. The drill verifies each by the filesystem and the post store, not by the reply, and emits a pass table. It spends real tokens and runs only when asked.

Two tests guard the repository itself: no runtime content, seat id or credential pattern in any tracked file, and every `runtime/` ignored; every law carried somewhere, every law tag real, and every law's test attempting its violation. File size is guidance, about 400 lines, split by concept and never compressed to fit a number.

Hosted CI gives only its pytest step a fresh private `TMUX_TMPDIR`, created by `mktemp -d` with owner-only permissions as `$RUNNER_TEMP/qs.XXXXXXXX`. This keeps socket length independent of the checkout path. The session fixture still budgets the effective anchor in filesystem bytes, with the same 107-byte limit and 12-byte margin; an overly long runner temporary path still refuses. The step retains a directory descriptor, compares device/inode identity and rejects a link before empty-only `rmdir` on exit. A failed test command keeps its nonzero status even if cleanup fails; cleanup failure after success fails the step and reports the retained path. No recursive removal or peer cleanup is allowed. Uncatchable process death may leave this invocation's directory for the disposable runner to retire. The separate fake-harness drill and the unset-variable project fallback are unchanged.

## 15. Working on the framework from a ship

Upgrade refuses links at `runtime/venv`, `venv/share` or `share/quarterdeck` before any mutation; after pip succeeds, resource-phase failures retain target code with a failed `resources` proof record, through the same handler as later installed-command failures.

**Target resources.** The explicit per-file `[tool.setuptools.data-files]` declaration in the target commit's `pyproject.toml` is the one authority for packaged laws, cards and templates. Wheel and source distributions use those same source files; there is no second resource tree or recursive ship inventory. Even an unchanged incumbent with an older literal copy list already pip-installs the target, so that original call bootstraps new templates after one upgrade across this fix. The first declaration retains every root the supported old incumbents copy: their subsequent old copy step rewrites target-identical files and does not remove newly packaged roots. This covers the historical standing-orders/drydock incumbent and the later forum/cascade incumbents; it cannot change an old caller's behavior if a future target removes a root that caller requires.

Updated upgrade code reads the archived target's declaration before installation, then replaces the managed `share/quarterdeck` tree with exactly those files after pip, including on rollback. It first builds the complete replacement in a temporary sibling. Read and diagnostic commands never synchronize or repair resources. For targets before the declaration, `resources.py` reads at most 1 MiB and 20,000 AST nodes of the target's installer without importing or executing it. It recognizes one direct literal copy tuple with the historical remove/copy statements and optional simple absent-template skip, then inventories only those declared roots. There is no inferred historical root catalog. Missing, dynamic, ambiguous or otherwise unsupported legacy shapes do not prevent emergency rollback: after pip, the explicitly authorized baseline fallback copies only the target's `standing-orders` and `ships/drydock` roots, each only if present, and runs ordinary installed laws proof. Other share contents are left as pip left them; one output line warns that extra templates may remain. This named fallback is separate from the authoritative packaging declaration. Only when the target has no standing orders at all does proof use `--help` instead, with an explicit laws/cards-unavailable line that does not promise usable seat briefs. Ordinary service restart, re-brief and seat lifecycle keep their existing behavior after successful proof.

Installation direction is read-only report wording: a target named as the prior record's previous installation or a strict Git ancestor is rollback, a verified descendant is forward, and the same commit is unchanged. Missing/corrupt installed evidence, an unresolved previous Git object or divergent commits mean unknown; an existing environment without usable metadata is never called an initial install. Unknown direction does not block an explicit target. Before creation or pip, upgrade records whether the environment already exists. A failed post-install proof retains every preexisting environment, regardless of direction, and writes the actual target commit/ref/time/previous with optional `proof = "failed"` and `proof_command` fields before raising an error. It neither queues a re-brief, repoints status lines nor starts the service; the service remains down and its existing alarm applies. Only an environment absent before a genuinely first install may be removed after failed proof. The current read-only doctor marks the failed-proof record as a failure. Older target readers ignore these optional fields and cannot report the newer failed-proof marker.

This also supplies the resource packaging mechanism for ordinary installs. Fresh installed laws/fake-drill acceptance and the installed-package omission inventory remain separate acceptance work; this upgrade change does not establish those proofs.

The most common work a ship does is work on Quarterdeck itself, so the loop has to be short and safe. Three facts shape it. The checkout a running ship uses is live: the seats run its `qd` on every post, so a half-edited file there breaks every seat at once. The service runs the code it loaded at its start, so a change to the service's own modules reaches it only by a restart, which the seats do not notice. And a worktree on a temporary filesystem loses uncommitted work at a reboot.

So: work on the framework happens in worktrees under `work/`, inside the project folder and ignored by its repository, never in the checkout itself; each worktree gets its own venv and its own test run, one suite at a time. A change is reviewed at its tip, once, by the captain, who reproduces what it doubts and writes down what it only suspects; its commit is its record, and no manifest or backup stands beside it. The desk lands it: a fast-forward of the checkout the ship runs, then the service restarted by `qd up`, which leaves the seats as they are; a seat picks up the new `qd` at its next command and a new adapter at its next restart. A landing may not move the schema under a running service, which is why the service alone writes the Ledger and every reading opens it read-only.

**The test tool.** `python3 -I tests/testrun.py` is the one way a seat runs the suite and cleans up after a change. It is the repository's own tool, standard library only, shipped with the tests and imported by nothing in `src/`; the framework neither depends on it nor installs it. Everything it makes lives under the project's ignored `.testruns/`, whose project is the parent of the Git common directory, the same from every worktree.

- `run [targets] [--target PATH] [-n N] [--timeout S] [--wait S]` tests the committed HEAD of the worktree Git resolves from `--target` or the current directory, never from where the tool's own file lives, so a worktree older than the tool is run by the main checkout's copy with `--target`. A worktree with uncommitted changes refuses; a WIP commit makes the result name exactly what ran. The run holds the project's one exclusive slot (a busy slot refuses at once, naming its holder, or waits as long as `--wait` says), checks the commit out detached in its own scratch, makes a venv on the ordinary `python3` with the system's read-only test tools and, by one plain `.pth` path line resolved from that interpreter before HOME is replaced, its user site (where `pip --user` tools such as pytest-xdist live; the line adds the directory only, so no `.pth` file or finder inside it is processed; the tools' bytecode there must already be current, the user site's bytecode folders are stamped before and after, and a change holds the run's cleanup), installs the checkout editable with no index, proves every package imports from that checkout, compiles the run's own code and makes its package folders read-only before any reader starts, and runs pytest in its own session with an evidence plugin of public hooks. HOME, the XDG folders, TMPDIR, pip's cache and the build all lie in the scratch; PATH is the caller's own; variables that would redirect Python, pip, pytest or git are removed and only their names recorded. Every interpreter of the run, pytest's, its xdist workers' and any child a test starts, runs with `PYTHONNOUSERSITE=1`, recorded among the fixed settings, so none processes a user site's `.pth` files or startup hooks and the user site is seen only through that path line, its base carried for a run started inside a run under the tool's own `TESTRUNS_USERBASE`, never as `PYTHONUSERBASE`.
- Every ending, pass, failure, error, timeout, interruption or a runner that died and was recovered, leaves exactly `results/<run>/result.json`, `report.md` and `failures/NNN.txt`, one complete file per failing test, and removes everything else it made, its Git admin entry included. The result names the target's commit and tree, the runner's own files by hash, the exact command, tool versions and safe settings, the exits of the wrapper, pytest, a signal and the cleanup as separate numbers, and the source manifests before and after. Each run folder carries a random owner token written when it is made, so a folder recreated in its place, even one that reuses the inode number, is refused at removal. Counts are stated only when every expected item, the xdist workers' collection included, reached a terminal report and the session finished in agreement; otherwise they are unknown, and what is known, a collection error or a failure, stays. A run stopped before pytest's collection completed states no expected count either: what it would have run is unknown, not empty, and its report says whether it stopped in setup or during collection. pytest reports a collection it was interrupted in as if finished, so the evidence plugin marks one that completed, errors included; an unmarked collection is partial, and the tests it names that never reached a terminal report are kept as at least these. Every recorded process counts, each xdist worker the controller knows of or whose recorder started, and each must have marked its own collection. Evidence of the plugin's first version, which has no mark, is read as before only when every process reports that version, and the report says so; versions that differ or are missing leave the collection unverified. The report holds the complete console. Nothing is retried.
- `clean --change BRANCH [--drop --reason TEXT]` retires a change the tool registered at its first run: its worktree by an unforced `git worktree remove` and its branch, once the branch is merged into main, or by a drop recorded first with its reason and bound to the branch's tip. It refuses main, an unregistered change, a worktree replaced since registration, in use by one of this user's processes, or holding anything Git reports, ignored files included, since the tool recorded none of them; results, reports and failures stay. A journal makes an interrupted clean resumable.
- `keep RUN --reason TEXT` keeps one run's scratch past its end and its change's clean, recorded with its reason.
- A run recovers only its own change's abandoned runs, after printing their scope, and only once its lock is free and its own process groups are empty; another change's leftovers are reported and left. The forced removal of a run's Git admin entry reaches only that run's own checkout: a recorded state naming any other checkout path, or an admin entry not directly under the project's `.git/worktrees`, holds the cleanup and removes nothing. Control state and results are versioned JSON, written atomically; a newer format refuses.

Pytest run directly follows the same folder: `tests/conftest.py` puts its temporary products under `.testruns/t`, where pytest keeps only its last three sessions (`tmp_path_retention_count = 3`, pytest's default policy, which removes nothing during a test's own teardown), and the cache provider is off.

The shared test-only `tests/testrunner/resources.py` policy lowers both soft and hard `RLIMIT_AS` to 8 GiB per pytest process, or a tighter inherited limit. The tool establishes it before executing pytest, even for an older target without the shared conftest; direct pytest establishes it in the shared configuration hook, before collection. Controllers, xdist workers and their forked, executed or spawned children inherit the hard bound even if their environment is cleared. `--memory-mib` on the tool, or `TESTRUNS_MEMORY_MIB` for direct pytest, may request a smaller positive integer limit, never a larger one. The tool records its declaration, pytest prints the effective limit and a test raising `MemoryError` names the bound. This is an address-space limit on one runaway process, not an aggregate resident-memory allowance. The ordinary plugin set includes Zarr's pytest plugin, which imports NumPy/OpenBLAS: on the 32-core test machine its thread-buffer reservations produce about 4.4 GiB of legitimate virtual address space with about 80 MiB resident at startup. The 8 GiB bound leaves room for that reservation while limiting one process to less than a tenth of the machine's 89 GiB. No production program configures these limits; the suite's service and program processes are synthetic.

The tool's `--timeout` is finite and positive (3600 seconds by default), covers preflight, setup and pytest with one monotonic deadline, and uses a main-thread alarm to interrupt synchronous setup too. An interrupted step's own session gets the existing bounded stop grace: at most three 15-second signal waits and two 5-second survivor waits. Finalization, including evidence and cleanup, has a separate 60-second budget. The stated maximum is the requested setup/test timeout plus 120 seconds of termination, finalization and emergency grace; normal test failure exits 1 and a setup/test timeout exits 3. If it expires, the tool makes no cleanup retry: the first result, report, failures and remaining scratch stay, an additional `emergency.json` is attempted within five seconds, and the command exits 7 with an explicit finalization-timeout notice and the evidence path. That notice takes precedence over a first result whose cleanup was still pending. Signal handlers and earlier timers are restored in `finally`. Authors running pytest directly supply an external wall bound as well, for example `env -u TMUX timeout --kill-after=15s 1200s prlimit --as=8589934592 .venv/bin/python -m pytest -n 2`, with their own basetemp and fresh short private socket anchor.

**The installed copy.** `qd upgrade` makes the ship its own copy of the framework: the commit named, the checkout's HEAD by default, is archived from the repository and installed into `runtime/venv`; the commit is written to `runtime/installed.json` beside the one it replaced; the service is restarted on it, the seats untouched; and the status lines of the ship's sessions are pointed at it. From then on every `qd` typed against the ship, from whichever checkout, hands off to the installed copy before it does anything, so the service, the seats and the status lines run one code, and main can move without the ship moving. `qd upgrade` with the previous commit rolls back, and removing `runtime/venv` returns the ship to the checkout; `qd doctor` says which the ship runs. So the loop is: a branch in `work/`, tests there, one review by the captain, a fast-forward by the desk, and `qd upgrade` when the ship should follow. Still owed: a worker's fresh start on a worktree of its own.

After staging the archive, upgrade stops the old service before replacing live code or cards, so its mtime watcher cannot post notices for unchanged replacement files. It captures each existing rendered brief's hash and a fingerprint of the complete saved launch before rendering anything itself, including any card event handled just before stop. After installation it puts a re-brief request in the existing `runtime/requests` spool, then starts the installed service. Only that installed and running revision may process it. The service renders current briefs for all seats and posts a notice only when content differs from the saved baseline and the same captured launch is still running. Down or replaced launches get the current brief at their normal launch. The baseline is the previous brief supplied or offered to that launch, not evidence that the program read it; an already held notice keeps its ordinary delivery evidence. A running launch with a missing baseline holds the request rather than guessing.

An incomplete same-commit request keeps its token and known offered baseline across retries. Before rendering or posting, it journals one notice intent per seat in that same request: the planned content hash, notice identity/time and previous offered notice identity. Only the matching immutable post advances the offered baseline; a failed post does not. Changed content gets a new identity linked to that previous offer, including returns to earlier text, while unchanged retries remain quiet. The exact planned text is rendered, and the source stamp is captured at the start of the pass so later edits stay visible. While this request is pending it owns card publication; ordinary re-briefing resumes after completion. The transient intent disappears with the request, without a general delivery/read tracking store.

Completed requests use the existing `.done` answer; a new upgrade operation compares current content again, including when returning to an older commit. Unchanged content spends no seat turn, even on a different commit. The proof names content changes and notices posted in that pass, or says no brief changed; posting is separate from record-confirmed delivery and never claims the agent read the file. Already posted/held notices retain their normal delivery evidence. With the service down, the request waits for `qd up`.

This adds one request kind, with hashes and launch snapshots in the existing spool, and no new store or `installed.json` fields. Ordinary service restarts do not create requests. A superseded target cannot announce its old revision using new brief text, and an older service's unknown-kind answer is reported as incomplete. Older versions still read the unchanged briefs, posts and installation metadata, but lack this re-brief operation. The upgrade command must run from the updated checkout, whose upgrade path deliberately bypasses installed-copy handoff.
