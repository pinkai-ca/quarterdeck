# Quarterdeck design: Watch

A page of [the design](../DESIGN.md).

## 8. Watch

Watch answers two questions independently: what the record says a seat is doing, and whether its screen lets the door deliver. It reads the record first and screen second. A missing observation is unknown with a reason, never a default reported as fact. Titles and personas are display; pane, process and record establish identity.

The delivery pass names unreadable alarm evidence for the affected seat, including when a human-owned seat is down. The seat's hold survives status overflow and clears after a successful reading. Version 1 unconfirmed-delivery alarm journals can lack a saved body. The next matching standing observation supplies the words for new reports while retaining saved report identities and existing posts.

Status and doctor share a read-only diagnosis of a leftover `service.delivery` pointer when the service is down. It names a displaced or unreadable journal, a saved identity mismatch or an unknown service owner stamp with fixed words. Active deliveries and evidence normal startup can resolve stay quiet. The reading keeps the pointer, journal and receipt bytes unchanged.

### Activity and door

| Activity | Evidence |
| --- | --- |
| idle | Last turn ended, nothing queued. A never-active seat is not stalled. |
| working | Open turn with steps still arriving; name its open tool and elapsed time. |
| stalled | Open turn with ten minutes since the last step; keep the tool named. |
| off | No running program in the owned pane, with the observed exit/crash/missing-pane reason. |
| refused/failed | Ended turn with a reader-recognized failure kind/code; never relabel it idle. |
| unknown | The reader could not establish activity, including an unreadable saved record pointer. |

The door is open only with a known empty box and no obstruction, including a working program that can queue. Obstruction names what clears it: a known dismissible notice, time for startup/limits/nonqueueing work, or a person for a draft/login/unknown dialog. A recognized blank/startup frame reads `starting, waiting for the input box` without a key; missing UI on an unfamiliar nonblank screen still needs a person. Startup never overrides recorded activity.

Text the door did not type is left untouched. It waits in the inbox and raises the seat's human-attention alert; it is not lifted, restored or sent. A scrolled pane can remain open where the measured transport preserves scrollback. The [door](door.md) owns paste verification, pending input, uncertainty bounds, layout and waking rules. [Harnesses](harnesses.md) owns version-specific control dialogs and native screen grammars.

`qd watch` prints the crew table; `qd watch <seat>` gives the full reading. `--save-screen` captures a scrubbed fixture for investigation. Screen-only queued evidence is not a receipt. An unreadable/empty saved pointer reports its join reason; a seat that has not yet obtained a record keeps its initial idle reading.

### Operational notices from ship-local tools

A tool may publish one short status line in `runtime/notices/<tool>.json`. The tool chooses a stable name of up to 48 lowercase ASCII letters, digits, underscores or hyphens, starting with a letter. It atomically replaces its file and unlinks it promptly when the condition clears. The directory and files belong to the ship's effective user and must prevent group and other writes. The reader accepts a real directory and regular files opened without following symbolic links.

The file holds one UTF-8 JSON object of at most 2,048 bytes with exactly these fields.

| Field | Value |
| --- | --- |
| `format` | Integer `1` |
| `text` | One printable line, at most 128 UTF-8 bytes, with no surrounding whitespace or tmux directives, escapes or aliases. Ordinary hashes and issue numbers such as `#123` are literal. |
| `pid` | The live writer's positive Linux process ID |
| `process_start` | The decimal start time from field 22 of the writer's Linux proc stat, as a string |
| `wall_ns` | Positive integer Unix time in nanoseconds when the writer observed the condition |
| `monotonic_ns` | Positive integer monotonic time in nanoseconds from the same observation |
| `expires_ns` | Positive integer Unix expiry time in nanoseconds |

Expiry must follow observation by at most 120 seconds. Both clocks must place the notice within that lifetime with at most one second of disagreement. The writer must still have the same process start and belong to the ship's effective user. The reader skips invalid entries and treats a missing, unreadable or overfull directory as empty. It examines at most 64 directory entries. The status line sorts notice text by file name and displays the text without a file or tool label. Notices share the space left after the required alerts in the first 160 display columns. If the notice text is too wide, the line shows a notice count when there is room for it. A cached status line is reused only while its notice text still matches the current reading.

### Sign-in failures and recovery

Claude Code 2.1.317's measured root API-error authentication_failed envelope becomes `sign-in failed in the program`; native turn duration remains completion evidence. Quoted login prose, screen text and unsupported forms do not classify it. A standalone recognized error can be displayed without inventing an input/turn. Automatic human-session status uses service-published metadata, never conversation bytes.

A live crew seat with a valid pool and just one latest sign-in-failed ended turn can take its next waiting message normally within fifteen minutes. The program rereads changed sign-in files for new requests; the failed input stays in conversation. A repeated failure, expired/unknown sign-in or expiry without a message holds the door again. `sign_in_failures` preserves each affected seat's fixed reading even on status overflow.

After credential reseeding, guarded resume requires local valid sign-in, saved paying pool and stable credential generation. First attempt needs a generation modified after launch; later attempts need a different generation from the last attempt. At most three saved attempts, sixty seconds apart within fifteen minutes of the first, live under `post/auth-relaunch/`. Reservations precede lifecycle work; held/failed requests consume the attempt and never bypass identity/idle checks. Safe logs name the held check or error kind without exception text.

A valid pool may wait up to fifteen minutes for renewal, displaying `sign-in: waiting for the renewed pass`; expired/unknown credentials call a person immediately. Window expiry or a proved new failure after the third attempt needs attention. An attempt whose relaunch did not start, held by a lifecycle check or raising, is a failure, not a wait: the status names it, `sign-in resume held by <check>: <reason>` or `sign-in resume raised <error kind>`, and a person is called at once; a relaunch that started still waits for the renewed pass. An old failure visible while resume starts remains waiting in that window. Only adapter-proved successful completion after the last attempt ends the episode, not merely an open turn. Claude's successful fact requires a root non-API-error assistant response closed by native duration; unknown or interrupted responses cannot clear it. Human-session seats receive alarms, never automatic recovery. Older readers lacking this failure kind lose its presentation on rollback.

### Model observations

Running model is read from the owned record first, then an adapter-proved screen identity. Comparison uses the effective pool/seat choice and that adapter's identity rule; default selection invents no expected ID. Only a matching pending model control suppresses its own temporary difference. Unknown observations neither create a difference alarm nor clear a previously proved one.

A proved difference produces fixed report intents for up systems recipients, with saved deduplication. With none up, the status line retains the seat/difference even when crowded. Journals hold canonical model names and operational intents, not native captures. Visible startup model/effort refusals remain separate from declared and observed values; they neither rewrite the declaration nor change the model automatically.

### Alarms

Every session independently shows withheld/blind delivery, human attention, held limits without eligible destination, disk pressure, grant expiry and service failure. The line carries operational alerts; detailed status/ledger carry provider allowance figures.

An unknown-screen alarm needs two fresh identical complete captures in one collection, with unchanged launch/pane/process. A changed or missing second frame leaves the first reading closed and inspectable without confirming the alarm. This suppresses transient redraw notifications, not obstruction or transport checks. Known dialogs, drafts and pending uncertainty keep their own timing.

The service reports seat/reason from ship to up systems seats. Person-only cases, including sign-in and uncertain paste/submit, also reach the desk. `PERSON_ONLY` is the shared reason set. An obstructed systems seat is not told of its own door. Without an available systems seat all alarms go to desk. Each addressee is notified once per unchanged reason; clearing/reappearing or a new recipient creates a fresh notice. This deduplication is process-local, so restart may notify again. The independent status line always retains the alarm.

### Following work

When a record moves from closed to open after the service baseline, a nonhuman session can select that seat's window. Restart's first reading is a baseline, never a start. Selection checks the ship's session ownership and the launch pane/process. It refuses if any pane is in a mode, an attached client typed or used a mouse within thirty seconds, or selection would resize the target. Nothing is typed, closed or resized.

New seat windows copy the shown window's size while their placeholder runs when that session has a viewer, then unset the temporary size option. This lets later follow preserve size without pinning windows. With no viewer or uncertain sizing, normal tmux sizing applies. Existing windows are never resized. Human sessions are never followed.

### Independent status presentation

Tmux runs `qd status --line` on its own timer, independent of service and doors. Kernel service-lock ownership proves liveness: late heartbeat means busy, missing/invalid heartbeat unknown, released lock down. The heartbeat comes from a thread of its own and proves only that the process is alive; the main loop also stamps `heartbeat/service.pass` as it begins each pass, each duty, the drain and the status work between duties, the pass's end, and its rest. A stamp older than 30 seconds (`servicectl.BUSY_SECONDS`, above the routine status work) reads `busy <age> in <duty>`, and one older than five minutes (`servicectl.LOOP_STUCK_SECONDS`, five times the longest duty the service has logged) adds `main loop stuck, nothing is delivered`; no stamp from the beating process reads `busy (main loop not yet seen)`. A stuck loop never reads ok. Up restarts a dead service. A blocked desk door cannot hide a service alarm.

An atomic stop barrier under `runtime/locks` retains all observed identities before they are signalled. A stop run again while the barrier records the live service's own owner (an earlier stop interrupted, or one running beside it) gives that owner SIGTERM and its grace as a first stop does; only what the earlier stop recorded outside the owner's tree and scope is ended at once, and the line names it.

An owner proven gone, whose lock is already free, before its scope is bound has an empty scope, not an unreadable one.

A stop confirms the owner's exit by pid and start as well as the released lock. An owner that releases its lock but outlives the exit grace has its whole tree ended by the write-bound kill, which observes new children before each round's signals.

Before confirming a stop, it reads the service's private systemd cgroup again, including its child cgroups. If that cgroup cannot be read, it uses only the private session or process group bound while the owner was alive. A member that ends between the cgroup's listing and its own reading (its `/proc` file gone, or reaped between the file's open and its read, which answers ESRCH) is skipped as ended; only a cgroup that cannot itself be read falls back, and a membership that changes mid-read in any other way stays uncertain.

A newly discovered process enters the barrier before the same tree kill runs; an incomplete reading or an unconfirmed exit refuses the stop.

A tmux server in that scope (a process named `tmux: server`, which a seat's relaunch from the service may start there) and every process under it are never ended: the proof line names it as left running with its panes, and the stop is judged on the rest. A tmux server a barrier recorded, and everything under it, is never waited for, since no stop ends one: the proof line names it as left running.

The service's scope is started with `--collect`, so systemd removes its folder once it is empty: a cgroup read whole earlier in this stop whose folder is gone once its owner is proved gone is an empty scope, and the line says `service cgroup ended with it`; a folder never read in this stop still falls back.

The proof line names the cgroup's re-read and any fallback, with the error that caused it, and it names any forced end.

A start, including copy recovery, refuses while any recorded exit is unconfirmed or the barrier is unreadable, and names that hold in status. Once every identity is proved gone, the next start or recovery clears the barrier itself. Cached status cannot hide a standing barrier.

An unreadable barrier holds a stop as it holds a start, and its refusal names the file, why, and what settles it: `qd service --settle-barrier`, run by a systems seat or the operator, is the way. It reads, under the stop guard's lock: (a) the service's lock is free; (b) no live process of the user sits in a scope named for this ship's service (`qd-service-<ship>-*.scope`), a tmux server there and everything under one left out as a stop leaves them; (c) no live process of the user outside the ship's own tmux server's tree, and outside the act's own process and its ancestors, carries `QD_SHIP` naming this ship. Another process's environment is read only for that test, and no value is printed, logged or kept; before reading one the act makes itself non-dumpable with no core, for the rest of its life, and refuses where it cannot.

When all three hold the file is moved, unchanged and never followed, into `runtime/evidence/stop-barrier/`, and the move is logged; no jail is shown this folder. Otherwise it refuses, naming the condition, the pids, their process names and their cgroups. A barrier that reads cleanly is not its to move. A process whose environment the user cannot read is skipped by (c) and named by pid and process name in the logged line and the output, unless it sits in any service's scope (`qd-service-*`), where it refuses. Its limit: a child that cleared its own environment, or made itself unreadable, and left the scope escapes (b) and (c).

A leftover `runtime/service.delivery` the next service cannot resolve holds every start. `qd service --settle-delivery`, a systems seat or the operator and never a jail, settles only that case. It calls the barrier act's proofs that no scoped service and no `QD_SHIP` carrier runs, and adds that no process of this user holds the lock, by stat of its descriptors, including a lock inode replaced under a live holder. A descriptor directory this user cannot read is named, unless that process sits in a service scope or the kernel's lock table shows its flock on the lock inode. It holds the service lock without writing it. It moves only that pointer, unchanged, into `runtime/evidence/delivery-boundary/`. The journal is not edited. A mark in `runtime/trusted/delivery-boundary.jsonl`, written before the move, names the evidence file the pointer will occupy and makes the next service hold the named journal as outcome uncertain and never type it again. A settling line is honoured while the pointer is absent or that evidence file exists. When the pointer does not parse, the line names every pending journal still in flight (pasting, submitting, submitted or queued), every attempt with no result or a blind one, and every human-wake reservation that is not ended, not cancelled, and not delivered, and holds them; a cancelled wake is resolved and is not held, and so is a delivered wake whose turn has not ended; if they cannot all be named the act refuses and moves nothing. A human wake still in flight is held by the episode recorded on the line, its wake token, so a later episode of that seat is not held. A mark that exists but cannot be read holds those same live journals and that is logged once, rather than releasing them. A prepared journal that was never pasted is not cancelled. The settling line and the trusted folder that holds it are forced to disk before the pointer is renamed. A pointer a start would resolve is refused. Its limit is the barrier's: a process that cleared its environment, left the scope and closed the lock is not seen.

The service atomically publishes `runtime/status-line.json` for text status-line jobs, dating collection start (`wall`/`monotonic`) and the publication write (`written`) separately. The optional collection-age cache retains its three-second wall/monotonic bounds and owner/declaration/framework checks. Outside that cache, a publication from the current service with an ok lead reads plain through `ship.status_refresh + STALE_SECONDS` after its write: forty seconds at the default thirty-second refresh, including a ten-second collection allowance. Its collection-start timestamp remains unchanged. Older or unverified publications, and a busy service, retain their operational alerts under an explicit `status stale` marker and write age through three times the refresh interval (ninety seconds by default). Beyond that bound the command collects current facts itself and adds `publication <age>s old, collected here` to the lead. A down service is independently named `SERVICE DOWN` and also takes the collector. Missing, corrupt or undated publications, or an unknowable write age, take the collector too, so reuse can never be unbounded. The collector keeps its existing error/unknown handling. Slow collections still publish; failed collection discards old rendering. Receipt, lifecycle, usage and JSON readings still collect their own facts and never consume this file.

Presentation demand uses a fresh client listing for declared sessions. A positive no-viewer listing skips collection; unknown demand still permits it. Between duties the service checks cheap status-input hints at most every 0.7 seconds, measured from completion. Hints cover post arrivals, attempts, journal folders, seat metadata and current record/WAL fingerprints, plus the service lead and accounting alarm. They schedule presentation only and never authorize an action. A change under `runtime/post` alone (the post's own traffic: store, attempts, journals, drops) is published at once by a post refresh: the post facts and every seat's post steps (its undelivered messages, its recorded-error hold, its detached journals, a person's unarmed watch) are read again over the slow facts kept from the last full collection, together with the service lead and the accounting alarm, and with the door read again for a seat whose own pending or drop folder changed. The seats' lines are then rebuilt in the full collection's own order, so a post refresh gives exactly the facts a full collection would; a withheld or blind delivery shows within one post refresh. Any other change collects in full, at most once every five seconds (`FULL_STATUS_INTERVAL`), and stays owed until then. Where a seat's last reading stopped at a post step, the refresh declines and the service collects in full at once. Unchanged inputs get a full reading thirty seconds after the previous collection finishes; native screens, clock-based alarms and disk space are read again on that cadence too. The `[ship] status_refresh` setting changes this interval, from five through three hundred seconds inclusive; the default is thirty. Slow collections always leave at least one check interval before the next collection; they do not return already overdue. A change during collection remains owed, and failed collection does not renew the last rendering. The service rests after a pass until a post/request arrival or its ship tick, without collecting status inside that rest. Missing directory notifications retain the tick fallback. Withheld deliveries still get a pass after one tick, independently of presentation demand. The independent tmux command retains its current owner checks and down/busy/unknown facts. No hint, client or deadline grants lifecycle authority.

**A collection profiled.** `qd profile-status` asks the service to profile its next full status collection, from a systems or engineering seat of the crew, never one in a person's session: the caller is the seat its launch named (`QD_SEAT`), and its role and session are read from the ship file, by the command first and by the service again (`status_profile.authority`, as `acts.authority` reads a screen act's). It is a request like the others; the service takes one at a time, and refuses a second while one is in hand, naming the first and its file. Its answer names the file at once, and that collection runs at once, whether or not anyone is watching the status line. The file, `runtime/status-profiles/<UTC time>.json`, a folder no jail is shown, holds only the code's function keys (module, function, line), call counts and times: it is built from pstats' own keys and numbers alone, never from the repr of anything, so no argument, value, record's content or path reaches it. A module is named by its place in the package or the standard library, folders included (`quarterdeck/harness/json_record.py`, `stdlib/json/decoder.py`), so no two files merge; any other file is named by a fixed word, and a function name outside a narrow alphabet is replaced. Each function's callers are kept the same way, code locations with their call counts and times, the eight most frequent. The 300 costliest functions are kept, within 256 KiB, and the five newest files. The service's other threads (its heartbeat, its credential watch, its write-bound walk) appear in the rows, since cProfile on Python 3.12 and later is built on `sys.monitoring`, which records every thread; the tool cannot exclude them, and the file says so. Its CPU figure is the collecting thread's own (`time.thread_time`). The profile slows the collection it measures, so that minute's timing line reads high. A request in hand when the service restarts is dropped, and its file never appears.

Within one read-only presentation scope, post-store instances share immutable messages/replies and per-seat projections; attempt readers share one complete inventory; human-wake presentation uses that same view. Import/forward metadata and their directory inventories are observed once per scope, including absence, and refreshed in the next scope. Service alarm presentation seeds the view with its existing readers so their ordinary validated parse caches can be reused. Native readers may share stable state/turn results. Reuse requires the existing two-second metadata certification, file/WAL identity and no source error. Changed, recent or unreadable evidence takes the ordinary reader. No observed snapshot survives its reading or wraps an action. Human-wake delivery reuses validated reader objects across its metadata, candidate and alarm readings, but each metadata/status reading gets a new snapshot and reruns the ordinary store and attempt checks; ownership, watch-generation, native-state, box and receipt checks are unchanged. Certified measured zero token totals avoid unnecessary history reading only with matching reader/launch/source/framework evidence, never by registering ownership or writing Ledger state.

Across passes, two of a seat's trusted readings are kept while the files they come from stand as read (`trusted_cache`): its launch (`launch.json` read once, the price binding taken over those same bytes, with `launch-price.json`), and the read-only answer to which program owns its record (`record_owner.lookup_reader`, from the reader registry, the launches journal, the record pin, the launch and its unconfirmed-move hold, and the home's `conversations.owned`, stamped with and without following a link). A value is kept only where no stamp moved during its read and every file was older than the post's two-second tick when the read began; anything young, changed or unreadable is read afresh, each caller gets its own copy of a launch, and nothing is kept across a restart. Publishing a binding never goes through it. No record reader imports it, so no reader stamp moves.

JSON-line reader snapshots keep no text and no lines in the service: only each record's running reader and input state, its counts, last rows and skipped lines, and a proof of its complete-line prefix (its byte length and a sha256 over it). They are bounded by their count, 96 entries (four times the seats and the people's records), so the records the seats read never push each other out; record bytes are kept only as a safety ceiling of 768 MiB, since an entry keeps no text and its resident cost per byte of record runs from 0.02 (Codex) to 1.94 (Claude). A sweep of many records, the seat-token fallback reading every record a seat ever owned, reads in passing (`json_record.passing`): it admits nothing, so it never pushes the working set out. The service writes the cache's count and bytes in the minute's `service-timing` line (`parse_cache`). A changed record whose old prefix is proved decodes only its new lines, which feed the kept readers and are checked against each kept input result, which a relevant new line drops; a prefix that is not proved parses whole. Each reader's compaction history is kept the same way, fed only the rows an append adds, and a history it refused stays refused until the record is rewritten. A caller that needs every line (an input reader after a relevant line, a new reader or history) parses that reading whole, once. The accounting child keeps text and lines as before, bounded to sixteen records and 128 MiB (`keep_rows`), since a job reads one record through several readers in turn. Changed/racy sources validate their complete-line prefix before reuse. Replacement, truncation, rewrite, partial final row, read failure and clock reversal cannot certify stale input evidence. Public lists are independent copies; record changes that affect queues/consumption/skip diagnostics invalidate attribution reuse.

The service's status publisher retains parsed delivery journals between collections. Each new collection opens the journal directory through the no-follow walk, lists its current names, and checks each regular file's device, inode, size, mtime and ctime. Only matching identities reuse parsed data; new or changed files take the guarded reader and validation again, and vanished names leave the cache. A read enters the cache only when both file times precede the collection's start by strictly more than the post cache's two-second timestamp tick; recent files are returned but read again next time, even if their stamp has since aged. Receipt existence is checked anew even for an unchanged journal. A directory replacement discards its earlier entries. Within one collection, journal inventories share the presentation's observation; returned proofs contain independent data. This cache applies only while publishing status: delivery, reconciliation, receipt confirmation and retirement retain their ordinary fresh journal reads. Native records and screens still supply the current alarm reading. A post refresh reuses the last full collection's slow facts, as above; nothing else is cached across collections.

The recorded-error scans (`turn_failure.current`, which the sign-in scan reads as well, and a program's queue error) read each seat's JSON-lines record from where they last stopped (`record_follow`). One entry per seat keeps the program's own reader, fed every complete line so far, with the record's device and inode, the offset after its last complete line and the 64 bytes before that offset; a later reading feeds the reader only the lines appended since. The entry starts over whenever it cannot prove the record only grew: a new device or inode, a size below the offset, a changed tail, or a new launch or record pointer for the seat. A record that ends mid-line, bytes that are not UTF-8, or a program whose records are not JSON lines (OpenCode's database, whose records are small) take the whole reading as before, so the state given is always the whole reading's. The shared record snapshot cache, which holds fewer records than a crew has, is untouched.

### Program use and check outcomes

Detailed status lists each declared/retained harness with `working_now` true/false/null and `last_turn_ended` UTC/null. A positive working seat establishes true. False requires all relevant current seats known inactive; unknown/missing/currently absent evidence stays null. The reader uses exact saved joins without joining or registering. Last-use time needs one unambiguous ledger launch interval/harness; crossing/conflicting/missing intervals yield no time. Null never proves never-used. Routine status text includes no program-use subjects, bodies or seat activity summaries.

`runtime/proven/check-outcomes/<harness>.json` retains bounded latest_attempt and definitive events, with sequence, outcome, UTC completion time, known installed version and safe fixed step/reason. Unknown events keep their original untimed format for older readers and publishers. The same publish lock protects the optional `<harness>.unknown.json` beside the outcome. It records the UTC observation time and any newer safe classification, bound to the outcome file's identity and exact bytes. Missing or mismatched metadata leaves the unknown untimed. The status scheduler watches the parent directory for both atomic writes. Beginning a check keeps prior definitive evidence. A completed same-program pass clears its alarms. Short publication locks order completions by sequence even if clocks move and are released before paid work.

Malformed outcome evidence appears as one unknown reading for its program. The next observation for that program replaces the malformed file whole under its publication lock. An unreadable file stays evidence unavailable. Account questions use the native interruption descriptor and publish a fixed reason. Failure and unknown alarms show the program and a safe reason on every line, including overflow, with time when recorded. These files are runtime evidence with no configuration authority.

Ship sessions retain 50,000 scrollback lines. Framework behavior is configured only through a declared ship-file field when needed; presentation caches and operational observations are never configuration.

The service log adds at most one `service-timing` summary per minute, after a duty or rest returns. It gives completed measurement counts, wall/CPU totals and maxima for every pass step, the between-duty `drain_drops`, `drain_accounting` and `drain_requests` calls, status collections, passes and sleep. Step names come from the code's methods and new names are carried automatically without a separate list edit. A carried name must be a Python identifier naming a Service method or one of the fixed pass, sleep, status, status_post, status_checks and drain labels; anything else is counted under `other` without retaining its name. The status count and cost cover actual full collection calls, including failed or refused calls, and status_post counts post refreshes apart; cheap scheduling checks have a separate numeric `status_checks` count and do not enter the collection timing. Pass time includes its duties, so those figures are not additive. A long duty belongs to the window in which it returns; summaries are observations, never scheduling or delivery evidence. The summary carries only numbers and duty names supplied by code, never runtime identities.

### JSON status served by the service

Every successful whole status collection also publishes its complete JSON reading
atomically at `runtime/status/status-reading.json`, outside every jail. It retains
all feed fields, its collection start time, the declaration and code identities,
and the owning service's process identity. `qd --json status` can serve it for less
than 60 seconds, while the same service holds its lock and has a fresh heartbeat.
Missing, partial, unreadable or older publications, uncertain ownership, changed
code/declaration or a stopped service use the ordinary cold reading. JSON adds a
`reading` object naming the mode, time and the served/cold label. This publication
is presentation only and supplies no delivery or lifecycle evidence.

Each JSON call atomically updates `runtime/status/status-demand.json`. A command
unable to write that stamp uses the cold reader. With clients attached, the
existing status schedule is unchanged. Without them, the service performs only
its periodic whole collections while a call has arrived within five minutes;
post traffic alone adds no headless collection. Demand aging and reading aging
are independent, and both require chronological wall/monotonic observations.
