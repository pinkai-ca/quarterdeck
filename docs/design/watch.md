# Quarterdeck design: Watch

A page of [the design](../DESIGN.md).

## 8. Watch

**Recorded sign-in failure.** Claude Code 2.1.317's measured assistant API-error envelope (`isApiErrorMessage = true`, `error = "authentication_failed"`, assistant text content and `stop_sequence`) becomes the generic `sign-in failed in the program` failure kind. Its following `system/turn_duration` remains completion evidence; no screen, quoted login text, child error or unmeasured adapter form grants that classification. A later native turn clears the current ended-turn reading. A standalone measured error is visible without manufacturing an input or completed turn. Watch and status name this failure even without an open order. Automatic status uses the existing service-published failure metadata for human sessions, never their conversation bytes.

The next delivery comes first. While the pool's sign-in reads valid, a live crew seat whose latest ended turn alone failed at sign-in, within 15 minutes of that failure, takes its next waiting message through the door as usual: the failure does not hold its deliveries, and status names it as waiting, not as needing attention. Claude Code 2.1.317 reads its sign-in file again for a new request: its handler for a refused request drops its cached sign-in and reads the store again, a changed file is adopted by its modification time before a request, and while its sign-in notice shows it checks for a newer sign-in on a timer. The failed turn's own input stays in the conversation it sends. A second sign-in failure in a row, an expired or unknown pool sign-in, or the 15 minutes passing with no message holds the door again. After credential reseeding, the service may then request a resume through its existing guarded relaunch path for a live crew seat with this failure. The saved launch names its pool; the adapter's local metadata must prove a currently valid sign-in and a stable file generation. The first attempt needs a file modification strictly later than launch. Further attempts need a generation different from the last attempt's, rather than a modification later than the resumed launch. Each episode permits at most three attempts, at least 60 seconds apart, within 15 minutes of its first attempt. Attempts are consumed durably under `runtime/post/auth-relaunch/` before lifecycle work and survive service restart. The additive `attempts` list keeps each consumed time, pool and generation; the top-level fields describe the latest attempt, and the old one-attempt form still reads. A resume the lifecycle path holds is logged with the check that held it, the recovery hold or the idle proof's dimension and reason; an error in the recovery itself is logged with the step it failed at and the error's kind, never its text.

Only a pool that still reads valid may wait: an unchanged file, renewal not yet newer or cooldown displays `sign-in: waiting for the renewed pass` without calling a person. Before a first eligible attempt, a valid pool gets a bounded 15-minute wait. A pool that reads expired or unknown calls a person immediately, before the first attempt or between attempts. Once the time window expires, or a failure after the third attempt proves that its next turn failed too, status and the systems alarm say needs attention. The old failure still visible as that final resume starts is waited on within the same window. A later open turn does not end the episode: only adapter-proved successful completion after the last attempt does. A held or failed lifecycle request consumes its attempt, without bypassing lifecycle checks. Human-session seats remain named and alarmed and receive no automatic recovery. Credential contents, delivery checks, receipts, provider pacing and lifecycle policy are unchanged.

Status facts add `sign_in_failures`, retaining each affected seat's fixed operational reading even when the status line compresses its other categories. This prevents a generic overflow count from hiding which program needs its sign-in repaired.

The generic failure-kind value and status-facts list are additive. Existing native records and turn/accounting formats remain intact. A previous reader does not recognize the new kind in the service's operational failure cache; rolling back therefore also loses this sign-in-failure reading until upgraded again. No other adapter's authentication form is claimed measured by this change.

Turns also carry optional adapter-owned `successful` evidence, defaulting to unknown. Claude proves it only for a root, non-API-error assistant text response closed by native turn duration. An interruption, inferred bound, no response or another API-error envelope cannot clear a consumed authentication episode. Only this positive completion fact, after the attempt, permits a new episode; accounting and receipt rules do not use it. Other adapters retain unknown until their own evidence is implemented.

Two readings, taken together, because they answer two different questions.

**Activity**, from the record, answers "what is it doing":

- `idle`: the last turn ended and nothing is queued.
- `working`: a turn is open and steps keep coming, with the open tool call named: `working, in Bash 3m`.
- `stalled`: a turn is open and ten minutes have passed without a step, with the open tool call named: `stalled, in Bash 14m`. A seat that has never moved is idle, not stalled.
- `off`: no harness is running in the pane, with the reason: exited with a code, crashed, no pane.
- `refused` or `failed`: the last turn ended in an error the record names, with its kind, its native code where the record gives one, and its first words: `refused, provider refusal (cyber_policy): <first words>`; `failed, program error: ...`. Never `idle`.

**Door**, from the screen, answers "can the typing path deliver":

- `open`: the box is empty and nothing is in the way. Generated suggestions are turned off at launch, so text in the box always means someone typed it. A pane left scrolled is open: a paste reaches the program in copy mode and a raw pasted carriage return submits it without leaving copy mode, checked on 7 November 2026, so the person reading keeps their place. A working seat is open where its program queues.
- `obstructed`, with the reason named and what clears it: a key the adapter knows (`daybreak notice, dismissable`); time (`limit banner, resets 14:00`; `working, program does not queue`); or a human (`text in the box`, `login`, `unknown dialog`). A captured blank or recognized startup frame reads as `starting, waiting for the input box`, cleared by time: delivery holds without pressing a key. A missing footer or box on an unfamiliar nonblank screen still needs a human. Codex's captured header, complete logo and untouched placeholder before its ready footer are one such startup frame; the logo alone is not, and a residual logo does not obstruct a ready box. Startup describes the door, never overrides activity read from the record.

Text in the box that the door did not type is an obstruction and nothing more is done about it: nothing is typed, nothing is lifted, nothing is restored. The message waits in the inbox, the status line names the seat as needing a human, and the alarm's recipients are told once. This is the whole of the guarding, and why a half-written message can never be sent: the door types only into an empty box, so the human's text is never in the box when the ship's goes in.

A reading the Watch could not take is `unknown`, with what it could not see. An unreadable or empty saved record pointer is `unknown`, with its join reason; a seat with no record yet keeps its initial `idle` reading. Unknown is never dressed as a state. Error is not a state either, except a turn the record says ended in one: a seat's own failure shows as `off` with its exit or as `obstructed` with the banner, a recorded turn error as `refused` or `failed`, and the Watch's own failure is `unknown`.

seat    activity              door                              order      today
pike    idle                  open                              -          12.1k
scott   working, in Bash 3m   open, queues                      ord-7f3a   48.9k
una     stalled, in Bash 14m  open, queues                      ord-9c21   3.2k
laan    idle                  obstructed: login, needs a human  -          0

Titles are display, never identity. The door dismisses only a notice the adapter recognizes, types once into an empty box, checks the display, and only then submits. An unverified paste is never cleared automatically. No key goes into an unknown dialog, a menu or a human's text.

A control-owned question is an obstruction to ordinary delivery. Only the pending request that submitted
the control may answer it, using an adapter-declared option matched to the requested value by its text.
An answer also needs the adapter's proved selection and focus conditions. The same request owner retains its consumed
claim and bounded continuation/deadline metadata; a later tick observes or answers, never types the
command again. Unknown continuation or transport holds without replay. Record confirmation closes a
model change; expiry names it unconfirmed. Where the program asked and the ship sent the value-matched
yes, the proof says both explicitly. The existing effort validation and declared control modes remain.
Claude Code 2.1.317's measured answer is Enter on the selected Yes option, whose text exactly matches
the requested model's current display. Positive focus requires the hidden composer, terminal cursor
flag 0 and the highlighted selected Yes marker/text in that same current frame. A typed capture keeps
cursor visibility beside styled text, bracketed by matching pane/process/geometry readings. The digit
accelerator was not measured and is not sent; neither are cursor movement or effort-dialog keys.
A malformed control-frame identity remains unknown and grants no key; its named `TmuxFormatError`
is retained in the request's held reason or final unconfirmed answer, without retaining the raw row.
The expected option display comes from the current seat/account context, never a global name alias
table. Confirmation uses the successful local-command record result bound to the pending request's
command envelope and requested model. A current model observation that may predate that request is
insufficient; absent request-specific binding remains unknown. The first question is retained by
digest only; changed or incomplete focus evidence holds by name.

A switch-model question without a matching pending qd control, including one produced by a person's
own `/model` command, stays a named obstruction. Ordinary delivery does not dismiss it with Enter.
The control owner or a person must resolve it. The synthetic Claude-shaped program now writes the
same linked caveat/command/result triple for `/model`, with its exact requested argument; its adapter
requires this new record evidence and its existing screen confirmation together. This synthetic
contract uses literal model identities and gives no catalog or gesture authority to a native adapter.
When that synthetic command is the seat's first input, no startup record is manufactured. Its empty
prefix is bound to the current launch until the ordinary one-record join finds that launch's first
record. The request owner then persists the joined path and file identity before confirming its
command triple. A pre-launch or excluded record cannot supply it. This initially unjoined synthetic
continuation can observe a result but never grants a dialog key; real Claude controls still require
their existing owned record before transport.

The service resumes that continuation before its generic consumed-claim hold, only when the original
payload and claim still agree. It keeps the original thirty-second deadline and one command reservation;
other requests continue on each pass. A failed or uncertain answer gesture is reserved before the key,
so a later pass can only observe its result or expire. A current matching continuation suppresses its
model difference through the same request owner's read-only query, including in the status reader.
The current Claude answer reader admits only the measured 2.1.317 frame at 120 by 40, with its two
option rows, indexed foreground styles, hidden cursor and absent composer. Other versions, geometry,
styles or wrapped/partial frame disagreement remain unknown. The expected display is one fresh exact
catalog row in the seat's own home, with no model-picker override or bundled-name fallback. This is
an option precondition, not native identity. The record result must follow the saved complete-row byte
boundary in the same unchanged-prefix record, with the caveat, exact command and successful output
linked in one prompt by their parent chain. No old result, timestamp ordering or display-only model
reading can supply that request-specific proof. A suffix beyond the bounded reader remains unknown.

An observed model is read from the current owned record first and an adapter-proved screen reading
second. Comparison uses the effective selected pool/seat declaration and the adapter's exact model
identity rule, with no generic prefix or punctuation aliases. Program-default model selection has no
invented expected model. Only a current matching pending model control suppresses a proved difference.
The service prepares a fixed operational report intent for each up systems recipient before publishing
it and keeps its identity for deduplication across restarts. With no systems recipient up, the status
line retains the seat and difference, including on overflow. The journal holds canonical model names
and operational report intents, never raw native records or captures.

**The box check.** Terminal soft rows are joined using tmux's `capture-pane -J` wrap flags before adapter parsing. For rows drawn by the program itself, the expected transport and the adapter's text-area width establish which breaks are forced: a full row may break at any character; a word or hyphen break is allowed only when the following piece cannot fit. Interior spaces, indentation, hard newlines and punctuation remain significant. Without layout evidence a plain string must match exactly; unknown control or grapheme layouts fail closed. The adapter may also recognize the placeholder of a folded paste during initial verification, with its changing paste counter ignored. That visual check permits submission, not a delivered receipt.

Codex 0.166.0 uses textwrap 0.16.2 and unicode-linebreak 0.1.5. Beside the established ASCII and Latin letters, its box comparison knows three specific ship-authored symbols: U+00B7 and U+2192 resolve from the ambiguous class to alphabetic; U+2026 uses the distinct inseparable class. Ellipsis permits only its source-established following breaks, never an arbitrary break before it or between consecutive ellipses. A preceding space can supply a boundary, subject to the existing opening/quotation context and overflow checks. This does not classify other punctuation or establish unknown grapheme/control layouts. The pinned sources are [Codex's composer wrapper](https://github.com/openai/codex/blob/rust-v0.166.0/codex-rs/tui/src/bottom_pane/textarea/wrapping.rs), [textwrap's word separator](https://github.com/mgeisler/textwrap/blob/0.16.2/src/word_separators.rs), and [unicode-linebreak 0.1.5](https://docs.rs/crate/unicode-linebreak/0.1.5/source/src/lib.rs).

Pi 0.74.2 opts into its editor's whitespace-only word wrapping at pane width minus one. Hyphens remain inside words; overflowing whitespace can backtrack to the preceding word boundary, and an overlong word splits at the available width. This comparison establishes printable ASCII wrapping only; wrapped Unicode/grapheme/control layouts remain unverified. Short Unicode lines need no wrapping. Other adapters retain their existing break rules.

Painted right-edge ASCII padding can be indistinguishable from typed trailing spaces. Known placeholders and empty rows tolerate it; nonempty box rows stay raw for obstruction and journal ownership checks. Visual comparison may disregard row-end padding only within a known text-area bound. Text requiring trailing spaces stays unverified unless shown exactly. Even a successful visual match never replaces exact record confirmation.

**Pending input.** A submitted payload on the same pane, process and launch, still showing its exact verified display, reads as `waiting to be taken`, without a human-obstruction alert. An empty box reads as `waiting for record confirmation`, never delivered. Edited, partial, foreign, folded or unavailable pending displays require inspection, as do identity changes or an uncertain paste/submit phase. The bound is 600 seconds from the original attempt, including prior withheld attempts, inclusive at the boundary; polls, retries and service restarts cannot move it. This is an intervention policy, not a claim about normal queue delay. Expiry needs a human and appears in every session's status line; it never triggers a resend.

An unknown obstruction can be inspected with `qd watch <seat>` and captured with `qd watch <seat> --save-screen` for a scrubbed adapter fixture. When a seat needs a human, the service reports it, with the seat and reason, as a report from `ship`, and the status line continues to show it. Who is told: while a seat whose role is `systems` is up, the alarm goes to it, since it clears what a `qd` act can clear; an alarm only a person can clear, a sign-in or a delivery whose paste or submit outcome is uncertain, goes to the desk as well. Those reasons are named in one place, `PERSON_ONLY` in the service; every other reason goes to the systems seat alone. An obstructed systems seat is never told of its own door. With no systems seat up, or none declared, every alarm goes to the desk, as before. Each addressee is told once per reason: an identical reading tells no one again, a changed reason tells its addressees again, a door that clears and then shows the same reason tells again, and an addressee that becomes a recipient while a reason stands, as when the systems seat comes up, is told it then. What is told and to whom lives in the service's memory, so a restarted service may tell a standing reason once more; nothing is stored. The status line carries every alarm by itself, through tmux, whoever is told.

An unknown-screen obstruction raises that report/status alarm only after two fresh captures in the same collection show identical complete text on the same owned launch, pane and process. A changed, whole, missing or replaced second frame does not confirm the first unknown-screen alarm. These are two observations, not a guarantee about redraw duration; no timer or retained screen store is involved. Known dialogs, drafts, pending-input uncertainty and other alarms retain their timing. The first unknown reading remains closed and inspectable: suppressing its transient alarm grants no delivery or control permission.

JSON-line readers retain bounded in-process snapshots (16 records and 128 MiB of raw source bytes, with parsed state beside them). A changed or racy source is read in full and its previous complete-line prefix is byte-validated before reusing parsed rows, state or input evidence. Replacements, truncation, rewrites, unfinished final rows, failed reads and clock reversals cannot certify stale evidence; a recent equal-stamp snapshot is refreshed before it can become trusted. Public row/input lists remain independent copies. Claude and Codex identify which appended native rows can change their input evidence, including queue, consumption and skip diagnostics. Unchanged current input evidence can reuse attribution verdicts only with the same source identity, no source error, unchanged posts and no invalid ledger turns. Source validation and the entry dirty marker still run first. No record, receipt or ledger format changes.

**Following work.** When a seat starts working, the session it sits in, the Bridge or the Crew, shows that seat's window, so whoever watches the session, or a recording of it, sees the work as it begins. A start is a turn the seat's record opens after the service last read it closed (law: record-first); the record is read again only when it changes, and the service's first reading of a seat is its baseline, never a start, so a restarted service jumps nowhere. A seat in a human's session is never followed, and the switch happens only in a session this ship owns (its `QD_SHIP`), for the pane of the seat's own launch, checked in the server by its PID as the switch runs (law: identity). It is refused, and the refusal logged, while any pane of the session is in a mode, which is a human scrolling back, while any client attached to the session has had key or mouse input in the last 30 seconds, which is a human typing, and when the window would change size: tmux fits a window to the client that comes to view it, so with a client attached the seat's window must already be the size of the window shown. Nothing is typed, closed or resized; selecting a window is the whole action. A human who is watching keeps the session they chose until they leave it quiet. So that a followed window already fits, a seat's window opens at the size of the window its session shows whenever a terminal is attached to that session: tmux would otherwise size a new detached window by the most recently active terminal anywhere, which may be another session's, and the follow would then be refused. The size is set while only the window's placeholder runs, before the seat's program starts, so the program draws, and the door reads, at that size from the first; the window's own `window-size` option is unset again at once, so it is not pinned and tmux keeps sizing it as any other. With several terminals of different sizes on one session, the shown window's size is the one taken: it is the size tmux gives that session's most recent viewer, and the size the follow compares against. A session with no terminal attached, including a session's first window, or an uncertain reading, opens its windows as tmux always has. An open window is never resized.

**The status line.** Every ship session's tmux status line carries `qd status --line`, refreshed by tmux on its own timer, independent of the service and of every door: `service ok · 0 waiting · laan needs a human · worker held at limit · disk: root 94%`. The kernel-held service lock proves a live owner independently of its heartbeat: a late heartbeat reads busy, a missing or invalid heartbeat stays unknown, and a released lock reads down; `qd up` restarts a dead service. This is how a dead service never looks like a healthy idle ship, and how an alarm reaches the human without passing through the Desk's own door.

The service may atomically publish an optional `runtime/status-line.json` rendering. Plain canonical text status jobs can reuse it for at most three seconds from collection start, checked against both wall and monotonic clocks. They independently verify the live lock, heartbeat PID and age, process start identity, declaration fingerprint, framework source stamp and installed-copy handoff. A restart, busy owner, clock reversal, source/version change or missing, stale, corrupt or unreadable cache falls back to the ordinary reader; failed or refused collection discards its prior disposable rendering instead of renewing an old success. Unreadable fallback evidence is an explicit status-unknown alarm, with null facts in JSON rather than invented counts. Other JSON readings, lifecycle, receipt and usage decisions never consume this presentation file. Its versioned disposable contents are ignored by older revisions; heartbeat, record and ledger layouts are unchanged. The canonical text console path uses the verified rendering when available and otherwise collects the ordinary current facts directly, without importing unrelated command verbs or constructing their parser. Other commands retain the ordinary parser; installed-copy handoff is unchanged. The three-second presentation bound accommodates roughly two-second actor cycles and their observed scheduling gaps; owner death still invalidates a rendering immediately through the independent kernel lock check, and a late or unreadable heartbeat refuses it even within that age. This lifetime applies only to rendered text, with no change to record-source certification or receipt/lifecycle evidence.

Presentation demand comes from a fresh native tmux client listing for the declared sessions. A complete listing with no attached client skips collection; missing, malformed or unreadable client evidence collects conservatively. The service checks due presentation between duties and during its existing one-second sleep after actor work, targeting 0.7 seconds between collection starts. Actor and record duties retain their sleep-after-work cadence. A blocked duty or failed collection may still leave a miss; neither changes the three-second trust limit or renews the old rendering. The independent tmux command then reads fresh facts, including down, busy and unknown alarms. No client listing or presentation deadline authorizes a lifecycle action. Pane queries use exact pane IDs and current PID/width evidence; screen identity and capture share one fresh server command queue, with the saved launch rechecked before the frame is returned. An idle delivery duty uses that single owned frame for its obstruction reading; an actual delivery still obtains its own fresh door and lifecycle evidence. There is no pane cache.

None of this is a setting. The ship file declares a ship; it is not a settings file for the framework. If a behaviour ever needs a knob, the knob goes in the ship file under a table named for the part it tunes, because one file is the only place a ship is configured, and each such knob is a default the framework should have got right. Ship sessions keep a 50,000-line history so the scrollback holds days, not hours, and no window size is ever fixed.

`qd watch` prints the table above; `qd watch <seat>` prints the full reading.

The detailed status reading adds `programs`, one entry per explicitly declared harness choice or retained known launch harness: `harness`, `working_now` (JSON true, false or null), and `last_turn_ended` (UTC ISO or null). A positive working seat establishes true even beside unknown seats. False requires every relevant current seat to be known inactive; mixed idle/unknown, no known state and no current seats remain null. A never-launched seat does not establish inactivity. Current activity reads the saved launch and its exact journaled join, then the record; it neither joins a record nor registers a reader. No screen default supplies a false state. The latest ended time comes only from ledger turns with one established harness launch interval; it is independent of the current seat preference. Missing harness evidence, missing times, conflicting launches and turns crossing a launch boundary establish no time. A null is not proof that the program has never run. Program last-use detail is absent from the routine status line, and contains no seat, order, subject or body.

`qd check` keeps bounded format-1 outcome evidence beside the existing proven marks, at `runtime/proven/check-outcomes/<harness>.json`. The common reader serves status text, JSON and every session's line. Each document holds `latest_attempt` and `definitive`; events carry a publication sequence, outcome, UTC completion time, installed version when known, safe step and fixed reason code. Beginning a check records an unknown completion, retaining the prior definitive event. Interrupted or unclassified completion has no invented step or completion time and cannot clear a definitive failure. A completed same-program pass clears it; another program's pass does not. The per-program lock covers only atomic durable publication, never the paid operation. Publication sequence under that lock orders overlapping completions even if the clock moves; timestamps are observations, not ordering authority. Reads are bounded and do not create files. Malformed/unreadable evidence is visibly unknown and is not overwritten by a check. A failed assertion's raw detail, native dialog text, exception, paths, record and task text never enter the outcome file. Recognized account-holder prompts name the question through fixed reason codes; an unrecognized dialog supplies no invented question identity. This change adds no native recognizer or answer to such a question.

A definitive failure appears as `<program> failed its check at <time>: <safe reason>` on every session until a later completed pass. Those named check alarms survive the status line's overflow form, which may exceed its usual presentation budget. Unknown latest attempts are shown in detail; unreadable outcome evidence has its own unknown line. Successful proven marks keep their existing names and content. Older installations ignore outcome files and cannot display the new alarm; absent older evidence means unknown, never an inferred pass or failure. Rolling back loses this alarm presentation while retaining the evidence and prior proven marks. These files are runtime evidence only, with no configuration authority. Scheduling and publication feeds remain separate work.

Detailed status and operational facts use one read-only presentation scope. Separate post-store instances share one immutable message/reply snapshot within that scope. Stable native state/turn results share a reading-local cache with the existing two-second metadata certification window, file identity and WAL fingerprint; changed, recent, missing or unreadable evidence uses the ordinary reader. No presentation cache survives the reading or wraps an action. A measured zero for today's tokens reuses successful accounting certificates only when every owned source, reader, launch evidence and framework stamp still matches; otherwise history retains its ordinary reading path. Status certificate checks do not register ownership or write the Ledger.
