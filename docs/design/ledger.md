# Quarterdeck design: Ledger

A page of [the design](../DESIGN.md).

## 9. Ledger

Production passes keep operational duties in their declared order, including authentication and push reminders, before the accounting and usage-refresh pair at the end of the pass. Messages are delivered before accounting. A low-priority child reads native records one at a time and prepares bounded write groups against a private in-memory model; it never writes the operational ledger or calls providers. The service alone applies ready groups within a two-second cooperative slice and commits before returning. Whole-record checkpoints allow later slices or a restarted service to resume. Attribution releases a record's incoming text before reading the next. Launch/reader-journal changes invalidate ready plans for the affected identities. Live quota observations and provider reads stay in the service, so a known spent pool can fail over after the slice without waiting for the backlog. Historical figures and key spend are explicitly last-known during catch-up; watch token totals are unknown and never fall back to parsing all records. Independently fresh provider windows retain their own freshness rules. The service keeps its heartbeat alive independently during long steps and refreshes it inside long apply loops. Catch-up detail is shown by `qd status` and `qd ledger`; the operational line retains its bounded accounting-failure alarm. Only a declared budget that depends on recorded spend waits for unfinished history; unbudgeted pools keep their existing eligibility rules.

Record accounting has one lazy SQLite transaction per service pass, independent of how many historical launches, quota events or turns it contains. The service collects program records and screens before writing, then calls the existing record writers with `commit=False` inside `Ledger.record_pass`. That boundary commits once if rows changed; a pass with no new record information and no due usage attempt issues no DML, BEGIN or COMMIT. Standalone writers keep their commit defaults. Usage refresh runs after the record boundary: each real usage attempt owns its own transaction, so the bound is one record commit plus the number of due attempts, not the number of historical rows. Provider calls never run inside the record transaction. Usage attempt and hold persistence must retain the same independent atomic owner when adapters add their own pacing evidence.

The writer alone sets `synchronous=EXTRA` and verifies that SQLite returns 3. Journal mode, existing tables and compatibility triggers are retained; there is no WAL migration or background checkpoint. [SQLite documents](https://www.sqlite.org/pragma.html#pragma_synchronous) that rollback-journal FULL can lose the last commit on some filesystems after a power cut; EXTRA also syncs the directory when a DELETE journal is removed. The guarantee still depends on working filesystem locks and storage honoring sync. Read-only status/watch connections set no pragma and change no schema. Older readers retain the same tables; an older writer after rollback uses its own connection settings and existing invalidation triggers.

Launch imports compare a record/wal metadata fingerprint and the current saved launch/price, then compare rows before inserting or updating. Wall observations fill only previously missing evidence and supersede only still-active matching screen rows; identical observations do not rewrite their rows or observation time. Record error markers also compare values before writing. A native record change can still require parsing and comparing its complete turn history: the service invents no offsets or new incremental adapter protocol. New launch/pricing evidence forces reconciliation even when record bytes stand still. Order attribution still follows the same post graph, input evidence and overlap rules; a changed turn invalidates the same side evidence through its existing triggers.

Record fingerprints, failed-read retry state, machine meters, launch-import cache and attribution cache are staged. Only a successful transaction publishes them; an exception discards speculative progress. Successful, complete, stable reads with accounted turns also save their accounting evidence in `record_accounting` in that same transaction. A restart skips reading unchanged turns when the saved reader, seat, record/WAL metadata, launch/price evidence and harness reader source hash agree. The metadata includes size and nanosecond modification time, inode, device and change time. Missing or malformed checkpoints, changed evidence, empty records, incomplete state and failed reads retain ordinary accounting. A record growing during its read gets no durable checkpoint. Turn, cost and launch-table writes invalidate the checkpoint, including writes by an older program. Changed records still read their complete turn history; unchanged turns write nothing. No checkpoint can run ahead of committed rows. Unchanged known-reader failures are retried at most once a minute by accounting, with duplicate errors neither rewritten nor logged every pass. The attribution service uses the same bounded transient retry, while its standalone replay API retains immediate retry by default; its separate post/source reconciliation still visits stored turns when its evidence changes.

`reader_stamp.py` explicitly lists each harness adapter, its native record reader and the shared code used to interpret records. Its key hashes relative module names and file bytes, together with the Python version; installation paths and metadata are absent. A module in a reader set invalidates that set's records; a shared reader module invalidates each affected harness. The synthetic adapter includes the native formats it delegates to. Unrelated package changes and a new installation directory preserve checkpoints. Missing or unreadable module files grant no reuse. The separate attribution set names `attribution_cache.py`, `order_attribution.py`, `input_receipt.py`, `post.py` and harness selection; changing these refreshes verdict certificates without forcing turn readings. Both streaming and ordinary replay use these same keys. Status rendering freshness and the catch-up epoch retain their full-package stamp. Reader sets are collected once per pass or status check, never once per record.

A record whose reader cannot be established, because no evidence names one or the evidence names several, is settled once (law: every-turn-accounted). The service never parses it: no program can be trusted to read it, and the file name is no evidence. A record present and empty, with no write-ahead log, holds no turn whatever program wrote it: it is accounted as nothing, carries no note and adds no `+`. Any other such record is noted in the book's `records` row with its reason and its settlement, a digest of the reader name its ownership gives (none), the record's own fingerprint (presence, inode, size, times, and those of its write-ahead log) and the reason. The note stands in `qd ledger` and the seat's figures carry its `+`, so no unknown turn count becomes zero; the service logs it once, marked settled, and while the settlement in the book matches it neither reads nor logs it again, across passes and service restarts. A new attempt comes only with new evidence for that record: changed bytes, a different reason, or a reader its ownership now names. Changes to the rest of the seat's registry or to launch prices are not evidence for it. When a reader is established the record is read and ingested in the same pass and its note is deleted; nothing was ingested while it stood, and ingest counts a turn once, so nothing is lost or counted twice. A note written by an older service has no settlement and is settled once after the upgrade. Ownership evidence that cannot itself be read is transient: it is retried once a minute like any failed read, logged once while it stands, and never settled.

Program provenance adds `launch_harnesses(record, at, seat, pool, harness)` beside the unchanged four-column `record_launches`. Normal service accounting imports only explicitly known harness metadata already present in the proven launch journal or saved current launch. Missing evidence is not filled from filenames, a pool's provider or today's preference. Contradictions or explicitly unsupported names at one launch remain unknown; no unsupported name is promoted to a program identity. Replacement/update/deletion triggers on the existing table invalidate the side evidence even when an older writer performs the operation. Import uses the existing `commit=False` record-pass transaction, compares before writing, and advances its source cache only after that transaction commits. Reading an old book without the side table projects unknown history without migrating it; older positional writers remain compatible. Rollback ignores the added evidence, and re-upgrade can reestablish it only from retained explicit source metadata through ordinary accounting. No live database backfill or native record rewrite is part of a status reading.


Reader-registry membership is shared by `bindings()`, `register()` and attribution replay through a context local to exactly one `Service.account()` invocation, including its existing seat join calls. The read-only consumer accessor `registry_events(folder)` uses the same coherent registry observation as indexed membership; attribution still enumerates every seat folder, including retired seats. An unchanged registry is parsed once in that pass; exact full-row membership is indexed by record, with extra fields and unknown reader evidence preserved. Each reuse checks device, inode, size and nanosecond modification/change times. An observed change forces a fresh parse; a read whose before/after metadata differs is returned under the ordinary reader rules but is not cached. Metadata failures also bypass the cache and keep the ordinary reader/error path. This observes coherent local metadata changes, not edits hidden entirely between checks or changes to a result already constructed by `records()`.

An already registered row needs only read access. A missing row discards that registry's cached membership, then uses the existing write-mode open and exclusive lock, freshly rereads under the lock and appends only if the exact row remains absent. A competing process that appended the row first therefore causes no duplicate append. A later lookup rereads after any write attempt, including a failed one. Changed registries and new-row rechecks can require additional parses; the once-per-pass bound applies to unchanged registries with no new rows. No lock spans record reading or accounting. The context resets in `finally` on success or failure, and nested invocations restore their enclosing context; no cache is retained on a service or seat. Public `events()` and callers outside an account context remain uncached. Repeated parsing of `record-launches.jsonl` is outside this registry bound and remains unchanged. Registry/launch formats, reader selection, provenance and the database transaction/cache-publication boundaries are unchanged.

Accounting preparation and record-transaction failures form one consecutive streak, including mixed causes. Three failed passes raise `accounting failing since <time>: <cause>` in every session's status line and in detailed `qd status`; the compact overflow rendering retains that alarm's time and cause. The first successful record pass, including an unchanged pass with no DML, clears it before any later usage refresh. Only the onset and recovery are logged for that streak. Causes are fixed, allowlisted database/file/evidence categories, never exception text, record content or supplied class names. Per-record incomplete-source notes retain their existing handling; post-commit logging, human-turn publication and usage failures retain their separate error visibility and are not called rolled-back record accounting.

`accounting_health.py` owns the bounded in-memory streak and the disposable `runtime/accounting-health.json` display snapshot. Only the service publishes it, atomically beside its heartbeat, with the current PID and process-start identity, observation time, checked flag, failure count, first-failure time, current fixed cause and per-cause counts. A new process starts unchecked; the snapshot grants no accounting or transport authority. Independent readers require the observed live service lock, a fresh matching heartbeat, the same process start, a fresh observation and a valid exact snapshot shape. Missing, stale, unreadable or differently owned evidence says `accounting health unknown`, never healthy or an old alarm belonging to the current service. The status line says that only while the service runs: when it is down or stale its own state already says so, and no unknown accounting is added to the line. Read commands never repair it. Snapshot-publication failure invalidates the previous rendering and has its own once-only failure/recovery log events; freshness bounds remain independently checked. Publication runs at most once per tick alongside the heartbeat, plus immediate accounting outcome updates. The existing disposable status-line cache includes this accounting fact. When an accounting pass changes what the line shows of accounting (unknown, nothing, or the alarm), the service republishes the line at its next status check rather than at the next interval, so a line published earlier in the tick never stands against the new evidence. Every cached reuse compares it with a fresh process-bound health reading: a missing field, a different fact or unknown health evidence falls back to normal status, preserving the existing framework stamp and formatting/budget path. This adds no Ledger schema or heartbeat-format change and no declaration setting.

The standalone usage owner covers `UsageCache.record` and the final `Quotas.usage_read` pacing INSERT as one intended write. Its narrow DML callback verifies ownership before staging anything. Ledger-owned `usage_read(commit=False)` requires that same usage owner to be actively staging and refuses during a record pass; it cannot create a usage write under a record transaction. Incomplete DML rolls back; after every intended statement succeeds, the owner marks the commit pending and attempts COMMIT outside that rollback handler. A failed intended COMMIT retains its transaction and owner for retry. At the start of each accounting pass, before any record is read, and again before staging another usage attempt or entering `record_pass`, the Ledger completes only that marked writer's intended commit, then proceeds normally; so no record is read while that transaction stands. A repeated failure remains countable by the accounting alarm. An active/nested record pass, an unclassified partial transaction, or a pending commit with no retained transaction is refused rather than silently committed or discarded. The existing lazy record boundary and its cache-after-commit publication are unchanged. Direct standalone `Quotas` callers retain their execute-and-commit default; Ledger-owned quota attempts use the tracked owner.

Service writer inventory: live-seat refresh, declared background refresh and destination eligibility all converge through `quota.record_read` and `Ledger.record_usage`; none owns a second independent Ledger write path. Before credential or provider work, `quota.read_usage` calls the same `Ledger.prepare_usage` ownership check. A prior failed commit must settle before another provider attempt, so a second call cannot be made and then lose its pacing write to the earlier obstruction. Record-derived usage has no provider call and joins the same tracked write. Provenance imports, record markers, turn/cost ingestion, recorded/screen quota events and attribution replay all use `commit=False` inside the record pass. Their standalone defaults remain available to other callers but are not service outside writers. Ledger initialization/migration completes its own startup commit before a service pass exists; read-only watch/status/door/ledger connections never stage service writes. The future Muse usage path also joins cache, pacing attempt and persisted retry hold. Its separate branch's enclosing database contexts would roll back a failed intended commit or bypass this callback: later composition must reconcile both contexts into the single usage owner, marking completion only after cache, attempt and hold DML, with incomplete-DML rollback distinct from retained commit failure. Muse is not composed or claimed compatible by this change.

Pools: utilization for each window the provider exposes (five hours, seven days), reset times, burn (1.0 means on pace to use the whole quota by reset), a wall when a window is spent, and a stale flag when the reading is older than the provider's cache floor. A seat leaves a subscription only when it is spent for it: a window is spent only when the provider reports it used in full (used >= 1.0), or when the provider has refused the seat's work at that limit, as the seat's record shows it. A provider's mark that a limit is near, a severity or any other warning, never makes a wall and moves no seat, so that no allowance is left unused; the reading keeps it as a warning, shown beside the fraction. A spent window stays a wall until its own reset: a failed, rejected or hour-old read keeps it, marked last known, and only a newer valid reading with room or the window's own reset ends a wall, so the door, failover and detailed status retain it through a missing read. A wall is a fact to route around, not an alarm. Claude Code's usage endpoint is shared by every caller on the login, the crew's seats and the Admiral's own sessions alike, so a Claude pool is read at most every five minutes, while a seat runs on it or once before a move to it. A failed read keeps what came back as the reading's error (the HTTP status with any Retry-After, a timeout, a network error, bad JSON; never the token, another header or the body) and is logged as a `usage` event in the service log; a refusal with Retry-After holds the pool that long, at least the interval and at most an hour, and the hold is logged too. A state that makes no provider call (a record reader with no snapshot, a missing credential or token) is logged only when its reason changes, and again after a good read, so the log keeps how often the provider refused without repeating a steady state. The read pacing survives a service restart: the first read after it waits out the interval from the pool's stored attempt time; the Retry-After hold is kept in memory only. An API key pool has no windows. Its row is spend where cost is established, with unpriced turns counted separately; no price catalogue is carried. A `budget` in the pool's declaration makes a wall of measured spend, without treating unknown spend as zero.

Claude consumes general and model allowances from the one usage response it already fetched. General `five_hour` and `seven_day` objects retain their `utilization`/`resets_at` mapping to ungrouped 5h and 7d windows. Named model windows such as `seven_day_sonnet` map to `sonnet / 7d` with group `sonnet`. Fable, Sonnet, Opus and Haiku are distinct canonical families. A Fable row supplies no Sonnet constraint; shared cap charging is unproved and is never inferred from similar names or a historical field spelling. An exact model name in a native named window or list display name establishes that row's own scope. A null optional named window is absent. In `limits[]`, a model row has nested `scope.model.display_name`, numeric `percent` in [0,100], string `severity`, ISO `resets_at` and boolean `is_active`. An inactive flag does not cancel a full meter. Critical, exceeded and error severity are the provider's warning that the limit is near or reached: they are kept as the reading's warning and never prove a wall, whatever the fraction. The actual fraction remains unchanged. A named window and its list entry for one family and period are one allowance read twice. They are one reading when their fraction, error and uncertainty agree and their resets lie within the same inclusive two seconds that period inference allows, which covers the about 1.0002 s by which two serializations of one cap differ; the reading keeps the later reset, so a wall never ends early, and carries a warning when either does. Two that cannot be reconciled conflict, and the conflict is named in the diagnostics (`conflicting model allowance representations for <window>: ...`). A conflict keeps whole the error-free representation spent in full, used at or above 1.0, with its own fraction, reset and warning, the later one when both are, so a merge never drops a wall; a severity counts for nothing there. A conflict with no spent representation reads as unknown room. No reading is assembled from fields of two that disagree.

Installed Claude Code 2.1.317 classifies `kind=weekly_scoped` rows as Current week and constructs them with `group=weekly`; its schema explicitly says kind classifies the server meter, while group only controls rendering. That exact kind proves 7d and takes precedence over reset inference, even if no reset matches or several do. Other native kind enums and durations remain unproved; group alone never establishes a period. If kind supplies no proved period, the fallback requires exactly one general window whose reset is within an inclusive absolute two seconds of the model reset. The bound covers the ordinary-read offsets of 0.15 ms and about 1.0002 s, while rejecting a difference just beyond two seconds. Unknown provided enums/types are diagnosed; a unique reset inference is identified by this policy, never by guessing their meaning. With no match or several matches the stable name is `<family> / unknown period`; the known fraction/reset and warning remain, while availability is unknown; only a full fraction proves that meter spent. An unrecognized model scope uses group `unknown`, not a guessed family. A known family with malformed measurements stays unknown. Only entries producing no window, including a null non-model scope, contribute to `unmapped limits: N; key/type shapes: ...` in the latest reading detail. Retained explicit-unknown windows, malformed mapped fields, uncertain periods and unrecognized kind/group values are described separately as `limits diagnostics: N; key/type shapes: ...`; a malformed list container has its own diagnostic. Only top-level kind/group scalar strings consisting of 1–32 ASCII letters, digits, hyphens or underscores can appear as `{type: str, word: ...}` in a diagnostic. Empty, longer, non-ASCII, punctuation, whitespace or non-string values remain types only. Every other field and all nested values remain key/type-only, with no account, token, header or body scalar values. Malformed list containers are visible too. A confirmed null scope creates no model window. No live capture or extra provider request is used; the first ordinary scheduled read after signed installation is compared with the retained reader's same-minute projection.

The warning is stored in `pools.exhausted TEXT NOT NULL DEFAULT ''`, a column an earlier writer named when it read the same severity as a wall, and exposed as `reading.warning` in JSON. It stores versioned evidence bound to the pool/window, group, blocking flag, fraction, reset and reading time; JSON exposes the validated boolean. Numeric evidence normalizes both signed zero forms to the SQLite REAL representation. The writer migrates it normally; a read-only older book projects false without writing. If an older writer replaces any bound part of the measurement, its leftover evidence is simply no warning, and the reading stands on its own fraction. Evidence an earlier writer left from a severity alone is read the same way: a warning, never a wall, so an upgrade moves no seat back and rewrites nothing. The existing row error records unknown period and the existing `usage_reads.error` carries safe unmapped-entry diagnostics. No account/body/header scalar data is retained; diagnostic scalar values are confined to the kind/group word allowlist. Missing windows and failed/stale observations retain prior complete spent evidence until reset or a newer good reading of that window. A newly proved period can replace the installed unknown-period identity without leaving automatic room blocked forever. The adapter declares the prior name and a two-second reset-continuity bound in internal Window.replaces metadata. During the ordinary cache write, exactly one accepted, fresh, newer, uncertainty-free replacement must match the old complete row’s model group, bucket, blocking flag and reset within that bound. The old name must be absent from the new observation; failed/stale readings, malformed or ambiguous replacements, different identities/resets and old observations preserve it. Only the exact matching current-cache row is retired, with its obsolete missing-row diagnostic; no source, record or historical accounting data is removed. This restores known room when the newly identified window reports room, and keeps a window used in full spent.

A refusal at a limit is read from the seat's own record, by each adapter that can tell it, and kept in `wall_events` with its pool, reason, reset and the model group it applies to (`group_name`, added to an older book by the writer; a read-only opening reads none). It is a wall for that pool until its own reset, scoped as a model window is: a refusal at a model group's limit walls a seat whose running model is proved to be of that group, and one with no group walls every model. The forms read, from installed source and the shape of recorded rows:

| Harness | Refused at a limit | Unknown, so no wall |
| --- | --- | --- |
| Claude Code 2.1.317 | a synthetic assistant row with `isApiErrorMessage` true, `error` `rate_limit`, `apiError` `usage_limit_reached` and `apiErrorParams.rate_limit_info` with `status` `rejected`, an integer `resetsAt` after the row's time and a `rateLimitType` of `five_hour` (5h), `seven_day` (7d), `seven_day_sonnet` (sonnet / 7d) or `seven_day_opus` (opus / 7d) | a plain `rate_limit` row, a model that needs usage credits, an overage or other `rateLimitType`, a missing or past reset |
| Antigravity 1.5.x | its `Individual quota reached` error, in the record or on the screen, with the reset it states | any other error |
| Codex 0.166.0 | none read: its `usage_limit_exceeded` error names no window or reset, so its meter decides | every turn error |
| Grok 1.0.77 | none read: a `rate_limited` retry names no window or reset and the program retries it, so its meter decides | every retry and turn error |

Key and endpoint pools are unchanged: a key pool is walled by measured spend at its declared budget, an endpoint never.

What becomes of the turn in progress at a limit. The provider refuses the turn and the program records the error and ends it; nothing is moved while it is open, since a move needs the idle proof above. For a crew seat, a ship message typed into the refused turn is settled by the turn-error rules where the adapter reads a turn failure; Claude's usage-limit row is not one, so the message's receipt stands, as its input is in the record. Nothing is lost for an order or a question: it stays open in the store, and the move's launch carries every open root whole, resumed or fresh. A move within the same program resumes the conversation, which keeps the typed message, unanswered, in its history; a move to another program starts fresh with the brief and the open and unread messages, and a closed message that only the old conversation held is not carried. For a seat the Admiral owns the same move applies. His own typed words are not posts: a resumed conversation keeps them in its history, unanswered, and he sees them there; a fresh start does not carry them, and they stay only in the old record. No paid probe has measured whether a program replays a refused turn by itself; none is assumed.

Routing, door walls and held-seat status apply the same adapter-owned family scope. General windows apply to every model. Automatic destination selection requires current relevant windows, including reported matching-family rows; an unknown other family cannot block it. An absent family row imposes no additional constraint on a legacy general-only body. A known matching row with missing, malformed or stale measurement is unknown and cannot prove automatic room. Explicit selection may still move on unknown usage, but refuses a proved matching or general wall. Source scope uses the running model from record-first evidence, never an unconfirmed declared model. Destination scope uses its own resolved choice. Unknown running family cannot prove a scoped wall; an unknown destination family with scoped rows cannot prove room. Detailed status/ledger and JSON line facts retain each model window and reset; session text remains held-seat alerts only.

Google window applicability uses explicit adapter-owned model/group relations, model identity equalities and all-model declarations only. The source-stage tables are empty: real membership remains unknown until the program or its sign-in explicitly supplies it. Neither a missing group nor a missing model proves an all-model cap. All returned buckets can constrain their proved members; unknown scope proves no group wall and no automatic destination room. Native refusal events carry their own step/execution model or observed screen model, with record evidence preferred. A refusal with an unplaced model holds only its own still-unplaced observed source; it is never promoted to a whole-pool wall. Distinct model spellings are not assumed to be aliases or distinct canonical models. General Claude windows and Codex retain their existing pool semantics. A destination uses its resolved provider/model policy; the current source uses its running record, falling back to its screen even when the check had no like seat. Detailed status and ledger label groups; operational held-seat text names the applicable group or own refusal without usage percentages.

Event scope is stored in `wall_scopes`, keyed by the unchanged `wall_events` source/event pair and bound to its retained pool, time/reset and refusal identity. Identical observations perform no scope write. Conflicting scope evidence stays unknown. Read-only books without the side table leave Google event scope unknown and keep legacy provider behavior; an older writer can still use its positional `wall_events` insert. A downgrade ignores scope and restores the old whole-pool Google decisions while that code runs. The approved native discovery stage must first look for a documented membership surface. If none exists, this machinery can land with the real fact tables empty: each unplaced Argon seat runs until its own provider refusal holds that model, at the cost of one refused turn per such seat. A successful installed check and an honest spent-versus-open proof remain distinct evidence; a check after reset is not equivalent to the required spent-window comparison. This staged source supplies neither a proven mark nor a public availability claim.

One rule decides whether a recorded refusal holds a seat: the paying program's `quota_scope(event, model)`. Its default is the ship's general rule: a refusal with no model group, as `wall_events.group_name` or its bound `wall_scopes` row gives it, holds every model, and one with a group holds the models its window would (`usage_scope`), so Claude's refused 5h and 7d hold every family and a refused Sonnet week holds Sonnet only. Antigravity overrides it with the stricter rule above: a Google refusal holds every model only by an explicit all-model statement, its own group's proved members otherwise, and its observed model or execution where the group is unknown. A window-only predicate from an older caller reads a refusal's group the same way. On the status line a held Google seat is named with its limit's scope alone, the group or what is known of it, such as `worker (Gemini 4 Argon) held at limit`; the full reason stays in `qd status`, `qd watch` and the door, so the line keeps the seat's name within its budget.

Every subscription adapter that reads usage names its headline windows: Claude selects 5h, falling back to 7d when a good read carries no five-hour figure, since the provider reports none for some accounts: the headline then says the provider reports no 5h window rather than unknown, 5h returns when a good read carries it again, and a failed read still reads as unknown; Google shows each returned group and bucket separately, retaining the historical Argon weekly `7d` storage identity; Codex selects both 5h and 7d, with an absent expected window explicitly unknown. Status and watch show those cached windows even without a live seat; unsupported adapters, key pools and endpoint pools gain no invented subscription reading. The text status line carries operational alerts. It names an up seat held at its current limit only when none of its declared destinations has proved room in the recorded evidence. Routing and status use the same cached eligibility predicate and later-then-earlier candidate ordering. Lifecycle guards can defer a move with an eligible destination without creating a held alert. The service keeps its ordinary paced foreground read before a move and re-evaluates that predicate after recording the result. Status commands make no provider request, so an unread destination supplies no proved room until the service reads it. An unreadable ledger makes held-seat evidence unknown. Detailed status, ledger and JSON line facts retain walls, windows, reading dates, age and failure reasons. The line uses the existing 160-character presentation budget for alert names, then counts every affected operational category and points to qd status. The all-category count fallback can exceed that budget. Grant-expiry alerts retain their dates.

Codex 0.166.0 supplies subscription observations in `event_msg` / `token_count` / `rate_limits` in its own record. The `codex` limit id identifies the allowance, not an account. `window_minutes` identifies 300-minute and 10080-minute windows regardless of primary/secondary slot; `used_percent` is provider-reported utilization, and `resets_at` is UTC Unix seconds. The event timestamp dates the observation, never the service's read time. Each minute the service selects the newest eligible snapshot across current joined Codex records whose saved launch names the pool, excluding entries before that launch. It does not scan historical or personal sessions, query credentials, or assemble windows from different snapshots. A newer partial/failed snapshot goes through the existing retention errors rather than selecting an older complete one. An older observation cannot replace a newer retained tuple; an observation at or before the latest failed attempt cannot clear that failure. Missing, unreadable, untimed, future or conflicting evidence cannot certify a current measurement. A restart without a post-launch snapshot therefore leaves dated retained values or unknown; repeated reads do not renew their age. A current supplied blocking window can establish a wall before a request fails, but an absent expected sibling cannot establish a fully known/open destination for automatic failover. Binding relies on the saved paying pool: these record events do not identify the account. No store or schema is added.

An endpoint pool may state `[pools.<name>.price]` with `currency = "USD"`, `unit = "million_tokens"` and all four numeric rates: `input`, `output`, `cache_read`, `cache_write`. Rates must be finite and nonnegative; booleans, incomplete declarations and other units/currencies are refused with the pool name. Zero explicitly states a zero price. Omission means unknown. Adapters map these rates into their program's supported model configuration; unknown rates are omitted, never written as null or zero. Pool rates override selected-model template rates so the ship declaration remains the price authority. The effective rates and model are saved with the actual launch and owned-record launch journal. Only an explicit matching step model and an unambiguous turn interval can use them; edits to current pool settings never price earlier turns.

Pi and OpenCode default omitted model rates to zero internally, so a zero cost in their records alone does not prove free usage. Their readers retain that recorded value separately and require stated launch evidence to establish zero cost. Measured nonzero step costs remain usable even beside unresolved siblings. Each endpoint step retains its recorded amount, tokens and explicit model; the display model is never price evidence. Known step amounts form a partial numeric turn cost, while `unpriced_steps` marks missing/invalid costs or uncertified zeros. Rollups count every such turn as unpriced even when a supported partial amount is present. A late source refresh can resolve or introduce uncertainty; preserving historical cost never overrides new step evidence. The Ledger keeps `recorded_cost` and `cost_basis` in a separate `turn_costs` table without rewriting historical numeric values. An old zero with no basis remains uncertified, neither declared free nor called fabricated; an owned-record refresh can establish its meaning only with available source/launch evidence. Missing old records or missing launch evidence cannot be repaired by today's pool settings. Historical nonzero record costs are retained on a later incomplete read. Rollups expose `cost` and `unpriced` independently in JSON: all unpriced is null, genuine measured zero is zero, and a partial numeric text total carries `+`.

Compatibility: the preceding service keeps the original 22-column `turns` and four-column `record_launches` layouts, so its reads and writes still work after the new service. `turn_costs` and `launch_prices` hold the added evidence. Ingestion names the stored turn and tool columns for both reads and writes; source-row names do not change the tuple-based public queries or the on-disk layouts. Insert/update triggers invalidate cost evidence when an older writer refreshes a turn; the next owned-source read can establish it again. Raw evidence is retained while invalid; it cannot certify current cost. Old numeric nonzero costs without side evidence remain recorded costs, while old zeros without evidence remain uncertified. Older readings cannot display these new uncertainty semantics.

`launch.json` and endpoint `model.json` retain their preceding keys. Adjacent `launch-price.json` and `model-price.json` bind price evidence to the file's publication (inode, size, modification/change times and content digest); a rewrite by the previous version, or a missing/malformed side file, leaves price unknown. Copying those files to different inodes also fails closed; the durable owned-record launch journal preserves previously established historical prices. Pool price declarations and extra fields in the record launch journal are ignored safely by the preceding version; generated program price fields use the programs' existing supported configuration.

Turns: a row per ended turn, from the record. Tokens in as many classes as the provider bills, four for Anthropic: read cached, read uncached, cache written, written; cost where the program states it; the tool calls made, by tool, each with its duration and whether it failed; the turn's duration; and the turns of any subagents the seat spawned, charged to the seat. The three headline measures, read cached, read uncached and written, stay the display; the rest is a column away.

What a record did not hold is counted and marked, never guessed and never hidden. A token class a provider never reports is zero within an actual measurement; an absent, malformed or unrecognized whole measurement is unmeasured. Explicit measured zero is complete. The common validation lives beside `Tokens`; each adapter identifies its format's measurement presence, including proto3's present message with omitted zero scalars. Measured sibling steps remain in the total, with missing steps counted. A step whose usage the record does not hold, a turn whose duration the record did not state, a tool call without a verdict, a record that would not read: each is counted where it belongs, and every figure built on such turns carries a trailing `+`, meaning at least this much; the tables say so in a line. The book has one writer, the service. `qd status`, `qd watch` and `qd ledger` open it read-only, so a reading never writes, and a newer `qd` never moves the schema under an older service.

Machine: the service samples each seat's process tree every tick and charges the turn with the CPU seconds it used, its peak memory, the most processes it had running at once, and the bytes it wrote to disk, read from the processes' own I/O counters. Tokens say what a seat cost the provider; this says what it cost the machine, which is the shared thing on a box where five seats running a test suite at once have frozen the desktop, and where disk has filled more than once with nobody able to say which seat was writing. The status line shows the free space on every filesystem the ship writes to, the runtime's, the workspace's and the system's temporary space, and when one runs low it names the seat that wrote most in the last hour, so the question "who is filling the disk" has an answer before the disk is full.

Seats and orders: the same rows, rolled up by seat and by the order each turn was charged to.

Order attribution is cached in `turn_attribution`, keyed by record and turn, beside the unchanged 22-column turn and five-column tool layouts. The legacy `order_id` remains for preceding readers/writers; replay never updates turn rows, cost evidence, tools, usage or launch provenance merely to change attribution. The side row records verified message ids/times, the seat/turn bounds they belonged to, verdict, roots and evidence routes. Every insert/update, from either version, leaves attribution pending until full service replay; ingestion never certifies the narrower evidence in `turn.input`. Existing side evidence is preserved while invalidated, and a new key without a verdict also forces replay even when source fingerprints and posts are unchanged. New readings display pending/legacy until service replay; the preceding version ignores the side table and retains its older attribution behavior.

The service revisits every stored turn on startup, changed post evidence, changed source evidence or invalidated verdicts, including retired seats and records whose files have not changed. Saved reader bindings choose the adapter; unknown bindings are never guessed from record content. Missing records do not delete measurements or established provenance. Previously verified incoming evidence may be retained only for unchanged seat and turn bounds, and is marked retained, not a fresh source read. Changed bounds require fresh evidence. Reconciliation is idempotent. Status, watch and ledger readings open the book read-only, never migrate it or run replay.

A successful stable replay may save a per-record certificate in `attribution_records` inside the same record transaction. It binds that harness's reader source hash plus the attribution engine source hash, reader bindings, record/WAL fingerprint, all turn identities and intervals for the affected seats (including cross-record overlap), and relevant post evidence. That post scope includes messages to/from those seats through the record's last ended turn, their reply ancestors and identity variants, relevant closing reports, and envelope-header candidates that can affect incoming-message ambiguity. Digests retain the existing relative post order. Unrelated posts and ordinary later posts leave historical certificates valid; new related ancestors or identity/header collisions require reconciliation. A match with valid stored verdicts skips that record's input parsing and verdict replay across restarts. Unknown readers, missing/unreadable or unstable sources, and retained error evidence receive no certificate. Verdict writes invalidate certificates, including older writers' invalidations. Changed inputs still use the existing replay and evidence rules. Standalone replay without a framework stamp keeps its existing behavior.

Replay checks source fingerprints, complete post values and pending verdicts before rebuilding the thread graph. An unchanged successful pass skips that construction; a failed source read is retried, and only a completed replay advances the remembered post snapshot. New turn keys and measurement-only refreshes still force full reconciliation through the existing invalidation triggers.

Attribution replay excludes source paths outside its runtime before any fingerprint, stat or read. A legacy reader/path/launch binding without a saved fingerprint supplies no authority to read that external source. Those stored turns remain counted and unassociated with the reason `legacy binding outside the runtime, no saved fingerprint`, including when outgoing posts or claims could otherwise provide a fallback. This attribution-only boundary leaves ordinary harness accounting and receipt paths as they were.

`qd ledger` prints the pools; `qd ledger --by seat` and `--by order` print the rollups, with tokens, cost, tool calls, minutes, machine load and bytes written side by side. The Ledger is one SQLite file in the runtime; ingestion is idempotent, so a turn read twice is counted once.
