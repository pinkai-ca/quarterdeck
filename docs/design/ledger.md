# Quarterdeck design: Ledger

A page of [the design](../DESIGN.md).

## 9. Ledger

The Ledger accounts for ended turns, provider allowances and machine use by pool, seat and order. Native records supply measurements; missing evidence is counted and marked rather than guessed. One SQLite file lives in runtime. The service is its only writer; status, watch and ledger commands open it read-only and never migrate it or replay history. Idempotent ingestion counts each turn once.

### Measurements and cost

Each turn stores tokens by reported billing class, program-stated cost, tool calls/durations/verdicts, elapsed time and charged subagent turns. The headline separates cached reads, uncached reads and writes. An unreported token class inside an actual measurement is zero; an absent or malformed whole measurement is unknown. Measured siblings still contribute, and incomplete totals carry `+` meaning at least this much. Explicit measured zero is complete.

A record past its raw read bound or one of Claude's projection limits leaves an unread span (law: every-turn-accounted). The projection limits cover physical lines, retained bytes per row, retained bytes for the whole projection, and retained memory. The ledger keeps the owned record, its seat and pool, its raw size in bytes, the first observation (`passed_at`), the last change in those figures (`seen_at`), and the count of turns already accounted for. Turns since then are unknown. A repeated observation of the same figures writes nothing. A complete, stable read of the same owned record clears the span. A fresh conversation has its own record, and an unread span for an older record remains until the older record can be read.

Raw bounds stay in `unread_spans` and are displayed in MiB. The additive `unread_projection_spans` table stores the exhausted resource and its exact limit in lines or bytes. Earlier readers can still read the raw bounds. If a retry runs past a projection limit, any existing raw-bound evidence remains part of the same unread span. `qd ledger` names each span in its notes and counts it on each pool it touches. The unread record's note also marks its seat's figures with `+`. Accounting continues to store guarded Claude projection counts and exhaustion in `record_projection_usage` for status and growth forecasts. The forecast uses current observations for exhaustion and can use older density estimates after the same inode grows. Compatibility forecasts require evidence of a per-row or shape refusal. An older compatibility flag alone is ambiguous and gives no compatibility forecast until accounting refreshes it. These scalar readings contain no record text.

When a guarded per-row refusal identifies the limiting value, the ledger stores its schema path and encoded byte count, including when a whole compatibility read succeeds. New observations also show the reader layout and a fixed refusal code, with a schema-known block or media type where available. For `not-a-user-row` and `unknown-block-type`, the ledger also shows the row type, message role, enclosing message block type and whether message content is a list. A row type matching `^[a-z][a-z_-]{0,31}$` is shown as written, and an absent key is shown as `missing`. Other labels and field names come from fixed schema lists. A `?` replaces values outside their allowed forms, and array indices are omitted. The diagnostic belongs to the exact guarded file observation, so a later append, rewrite or replacement hides it until read again.

A guarded Claude compatibility read or a per-row projection refusal makes 128 MiB the first warning bound, with a size alert at 96 MiB and the growth forecast using 128 MiB. That evidence follows growth of the same file until another guarded read updates it. A record beyond the compatibility bound is shown as unknown. For an operator-owned seat, the growth report goes to the desk and stages no handoff.

Giant native Claude user rows can stream base64 image data in typed input and tool results while keeping the block metadata and payload size. Typed text stays whole for receipts and attribution. The reader hashes a typed image row's complete canonical content through the same guarded descriptor so its compaction identity stays exact in both newline and Unicode splitlines layouts. Changed records in the splitlines layout still read from the beginning. A recognized long user tool-result text can use the same bounded projection when it cannot carry watch evidence. A native user result envelope also permits projection of oversized strings in its top-level `toolUseResult` mirror. The reader keeps the mirror's containers and scalar types, checks base64 image data, and retains task and agent evidence fields whole.

Claude can stream verified base64 image data from direct image blocks or from a supported tool-result content list in a user or assistant message envelope, including when the top-level row type is absent or unfamiliar. Outside native user rows, text and mirror strings stay exact and count toward the retained-row limit. Each reader still interprets the original row type. The record digest covers all raw bytes, and a compact boundary or queued input keeps its exact full-row identity for the compaction frontier. Values that exceed the retained-row limit without a supported projection use the usual refusal or bounded compatibility path.

Endpoint pools may declare all four finite nonnegative USD-per-million rates: input, output, cache_read and cache_write. Zero explicitly states free; omission is unknown. Pool prices override selected-model template rates. Effective model/rates bind the actual launch and owned-record launch journal, and price only matching step models within unambiguous turn intervals. Today's settings never price past work.

Pi/OpenCode native zero cost alone does not prove free usage because omitted model rates default to zero. Readers keep recorded amount, tokens and explicit step model separately from stated price evidence. Known step amounts form a partial cost; `unpriced_steps` counts unresolved siblings. JSON exposes `cost` and `unpriced` independently: all unknown is null, measured zero is zero and a partial text total carries `+`. A later source reading can change uncertainty without erasing established historical nonzero measurements.

`turn_costs` and `launch_prices` hold added evidence beside the stable turn/launch layouts. Triggers invalidate evidence when any writer refreshes a turn. Raw retained evidence cannot certify current costs while invalid. `launch-price.json`/`model-price.json` bind price evidence to inode, size, timestamps and digest of their adjacent launch/model files. Missing, copied, malformed or replaced evidence leaves price unknown; historical owned-record launch prices remain available. Old readers cannot display these uncertainty semantics.

Each tick samples seat process trees for CPU seconds, peak memory, process count and bytes written. Disk alerts cover runtime, workspace and temporary filesystems and name the largest recent writer. Tokens measure provider use; process counters measure pressure on the shared machine.

### Accounting passes and recovery

Operational duties, including deliveries, precede accounting and usage refresh. A low-priority child reads records one at a time into bounded private plans, making no provider call or operational Ledger write. The service applies ready groups within a two-second cooperative slice and commits before returning. Whole-record checkpoints resume catch-up after a slice/restart. A checkpoint is keyed on the launches joined to that record, so a seat that is down or relaunched onto another record does not invalidate finished records of older launches. A launch or price joined to a record invalidates that record. Reader changes invalidate that harness's records. The catch-up epoch uses all native reader and attribution-engine keys, independent of the installation path and unrelated package changes; only a changed reader key reopens a finished catch-up at startup. An unreadable reader or attribution dependency cannot certify completion. Heartbeat refresh continues independently through long accounting steps and apply loops. Historical/key-spend figures remain explicitly last-known during catch-up; watch totals stay unknown rather than reparsing history. Only budgets dependent on unfinished spend wait for history; independently fresh subscription windows retain their own validity.

A planning job validates each record's seat identities before applying its groups and validates the job's observed identities again before committing catch-up completion. If an identity changed, accepted work for other seats stays committed. Only affected seats are recollected and replayed, clearing only their speculative reader caches; unrelated identity changes do not invalidate that scoped retry. Completion stays pending until the retry finishes, so retirement cannot race unfinished catch-up. Identity churn never forces a new global epoch. The child retains the post graph while the Store's validated message listing stays identical; a changed listing rebuilds it. Each job logs its start, end, elapsed seconds, record and packet/write counts, and a scoped reset naming changed seats. The planning child writes framed results to an anonymous temporary file inside the runtime, rather than a pipe that can fill while the service is busy. The parent reads bounded chunks at its own offset and applies ready groups without waiting for more input in a 20ms cooperative slice before a pass, between duties and during idle waits. The ordinary accounting duty alone starts jobs. A finished job truncates the shared plan only before the next job begins; close or process exit removes its anonymous file. Every200completed record contexts emits an accounting-job-progress line after commit, with record/packet counts, elapsed time and plan bytes. A long individual duty may delay application, but cannot block the child for want of an output reader.

A lazy `Ledger.record_pass` owns record writes with `commit=False`: one commit if data changes, no transaction/DML for an unchanged pass. Program record/screen reads precede it; provider requests stay outside it. Writer connections require `synchronous=OFF`, verifying SQLite value 0, and DELETE journaling. Process interruptions retain transaction rollback; an operating-system crash or power cut can lose writes or corrupt the database, requiring reconstruction, as [SQLite documents](https://www.sqlite.org/pragma.html#pragma_synchronous). Read-only connections set no pragma and cross-process readers continue to see committed data. WAL is not chosen on this host’s SQLite 3.46.1-9ubuntu0.3 without evidence of the [WAL-reset fix](https://www.sqlite.org/wal.html#walreset) backport. Memory-backed write counts are a proxy for drive traffic, not measured drive writes.

Fingerprints, reader/launch caches, meters and attribution progress publish only after commit. Exceptions discard speculative progress. Stable complete reads save `record_accounting` in the same transaction, binding reader, seat, record/WAL metadata, the launches joined to that record and reader-source hash. Changed, growing, missing or malformed sources cannot reuse a checkpoint. Changed records still read their whole history; equal turns write nothing. Failed known-reader sources retry at most once a minute without repeating unchanged logs. A source read whole whose turn state is unknown keeps the incomplete note and is not read again until it changes, with one exception: where its reader says the unknown lasts only for a time, as Claude's does for the grace after the program's own notice, the service reads the unchanged source again once that time has passed on the reader's own clock, then checkpoints it as any complete read. A hold is read once: the read it brings sets a new hold or none. Where the grace ends between the pass's read and the reading that asks for the deadline, that reading finds the window already passed and still gives the hold, due at once, so the next pass reads the source again. The service gets the deadline from the exact snapshot of Claude's guarded reader (`harness/held_reading.py`, the service's alone and imported by no reader, so no reader's stamp moves with it).

The accounting duty reuses a private input certificate only after a complete full job with matching observations before and after its committed output. The observation before is taken before the job collects its seats and sources, so a change made while collecting is newer than the certificate and starts the next job; a record first found while collecting joins that observation only when its metadata is older than it by the filesystem tick, and otherwise its first job cannot certify it. It watches known in-runtime records and their WAL files, launch/price/join/ownership/pool metadata, the declaration and resolved settings, reader/attribution hashes, and the ledger connection revision plus database identity. Post store/import/forward/address folders use identity and times under the immutable-message contract. Metadata newer than the two-second filesystem tick, unreadable observations and reversed wall time grant no reuse. Intervening ledger writes invalidate completion; only this driver’s own committed writes are excluded. A new service, a failed/partial job and targeted retries certify nothing. Retries still run immediately. A due hold is a reason of its own: the child reports each hold it leaves by its seat alone, and once one is due on its reader's clock the gate starts a job for that seat, though nothing it watches has changed; a job that reads the seat takes its holds, and the child reports what it leaves again. Otherwise an unchanged duty starts no child job until its monotonic ten-minute backstop, which revisits newly discoverable paths, metadata-invisible rewrites and screen/process-only evidence. Usage refresh continues independently. No certificate is persisted, and scheduling changes neither native reader stamps nor the attribution epoch. The ordinary accounting duty alone begins a job; a drain only continues one already begun. The first valid full job with no retry after the service starts, or after a catch-up begins, logs `accounting-caught-up` once, whether or not it wrote, and says whether it did. The health file is written at once when what it shows changes, or a job ends or fails; otherwise once a pass, however many drains step a running job.

Each actual job start adds one `accounting-gate-start` event containing only its numeric job counter and class/count evidence: changed record, WAL, launch metadata, post folder, settings or hashes; tick-young/unreadable observations; retry, no completed certificate or backstop; a due hold (`held-reading`, a count); and SQL revision. SQL evidence separates the driver's credited writes from other same-connection changes, external `data_version` changes, and connection/database replacement indicators. `data_version` is a revision delta, not a count of external transactions. One previous job's begin/end validity, input classes and SQL accounting explains rejected certification without retaining a growing history. No path, seat, record identity, hash value or exception text enters this event. Quiet waits add no event; the existing minute `service-timing` summary counts them in `duties.accounting_waits.calls` only when nonzero. That count-only row uses zero timing placeholders; its elapsed time is already included in the accounting duty. These diagnostics do not change eligibility or certification.

After a completed full job, record and WAL observations are partitioned by proven seat ownership. A changed record selects that seat's entire owned inventory and all its historical attribution. The post graph and the seat's closed intervals remain complete, so cross-record overlap is reconsidered. Launch and registry files of a seat the partitions do not know, ownership, declaration/settings, reader hashes and other-writer SQL are global barriers: uncertainty or a change requires a full job. A scoped job rechecks every barrier and every outside-seat input before starting and before advancing its observations. A young record remains dirty and cannot be certified; it can keep its seat active without reopening every other seat. A scoped seat whose guarded read failed was not read: it keeps its owners as they stood, nothing of it is marked, and a retry that failed to read its seat certifies nothing of it. Unknown or ambiguous ownership forces full work.

The post is no global barrier: it is narrowed seat by seat, by the engine's own rule. Each job's child sends, for every seat, the digest of `Threads.scope(seat, SCOPE_END)` at the post its replay read (`accounting_slices.post_scopes`). That is the attribution engine's own closure: sender and recipient, every reply ancestor, an order's closing report, envelope-header candidates and identity variants. `order_attribution.py` is unchanged, so no reader stamp moves. The unbounded end holds every message any of the seat's verdicts can see: a superset of what a turn's attribution reads, which may dirty a seat more often than its turns need, never less. A seat read whole is certified at its digest, and every seat whose digest differs from its certified one is dirty and read by a scoped job (`Partitions.record_scopes`). A certificate's post stands only at the post folders' stamps read before the child built its graph: a message that lands later keeps the post due (`Partitions.post_due`) until a job takes every seat's scope again. With nothing else to read, that job reads no seat, and its child builds the graph off the service's own process. A young post folder in that reading stands for no post and keeps it due. A message file that leaves the post, or whose identity (device, inode) or size changes under its name, breaks its contract: nothing is certified, and the next job is full. An addressee the closure cannot expand, such as the ship or a group, forces nothing: the gate takes the engine's own closure, which the agreement test proves equal, and forcing a full job there would force one on every report to the ship. The service's numeric timing counts, for each duty, the ledger rows it wrote (`ledger_writes`), as counts only. Those counts named the one other writer: the usage refresh, which writes pools, usage_samples and usage_reads alone, none of them read by the accounting job. Its rows are counted apart (`Service.NON_ACCOUNTING_DUTIES`, `non_accounting_writes`), each gate reading carries the count (`Reading.foreign`), and the other-writers barrier compares the rows written less those (`accounting_scope.written`). Any other uncounted write by this service, and another process's write to the ledger, stay global barriers.

A known seat's own launch files (its trusted folder's launch record, price, pool, record pointer and both registries, and its home's conversations.owned) are no global barrier either: they are judged seat by seat. Each seat is certified at their stamps in the reading its last whole read began from (`Partitions.record_meta`). A seat whose files have moved since is dirty, and so is every owner of a record a moved registry names (`Partitions.meta_dirty`). The registries are append-only: under the same file, with the digest of its first old-size bytes unchanged, the lines after the old size name what moved. A registry rewritten in place (that digest changed, even where the file grew), shrunk or replaced reaches every record it names now and named then. A record so named whose owner the partitions do not know forces full. A young launch file leaves its seat dirty, read again alone. A retry whose read of its seat failed certifies nothing of that seat, which stays dirty and is read again alone.

The initial job and catch-up are full. Scoped work never moves the independent 600-second full-scan deadline; the driver preempts a still-running record scope when full work becomes due. Record jobs cannot emit or apply the global catch-up completion. The existing identity retry is structurally different: the parent retains the completion of the full generation it continues, and accepts that completion only after the remaining affected seats pass validation in that same generation. A new full generation invalidates that continuation. A retry that is itself reset re-queues every seat still in the continuation, not only the seats that moved again: its slices are discarded for every seat it read, so none is stranded and the continuation empties after one more read. A record-triggered job naming exactly those seats acquires no such completion. Failure and rejected observations grant no reusable partition certificate.

A full job reset by moved seats certifies, with its identity retries, what it read whole, seat by seat (`Partitions.stitch`). When the continuation empties, every seat has been read whole once: by the full job, or by the retry that re-read it. Each record is marked unchanged only where its readings in the job that read it are equal and settled. A record no seat lists is the full job's. Every other record goes dirty, and the next decision is a scoped job for the dirty seats, not another full one. Nothing that moved is certified. A moved seat's slices from the full job are discarded at its reset, its retry reads it once, and the completion is applied once, when the continuation empties. The global barriers hold across the whole span, from the full job's begin to the last retry's end, with every job's own ledger changes counted: the post folder, settings, the declarations, every other seat's launch metadata, and every other writer's ledger rows. A moved seat's own launch metadata, its identity, which moved, is judged instead within the retry that re-read it: it must be equal and settled there. Any break gives no certificate, and the next job is full; the refusal is logged as `accounting-stitch-refused` with the barrier classes alone (post folder, launch metadata, settings, declarations, hashes, epoch, ledger identity, other writers, a retried seat that moved again), never a path or a seat. A reset retry's own ledger writes count as the job's. The 600-second backstop runs from the stitch, as a completed full job's runs from its end, so a span longer than the backstop still gives a certificate that holds. These private scheduling observations do not change a reader stamp or the attribution epoch.

`harness/reader_stamp.py` hashes relative reader/shared module names and bytes plus Python version, independently of installation path. Reader changes invalidate affected harnesses; attribution changes invalidate verdicts separately. Attribution's message dependency is `post_message.py`: immutable message identity, JSON and exact delivered envelopes. Store listing, publication and transport changes do not reopen a completed catch-up; message interpretation changes do. Missing files grant no reuse. Reader and attribution imports must be explicitly assigned or documented launch/control-only.

The checkpoint test walks declared reader and attribution modules by AST, including imports inside functions. It checks `import`/`from` statements and literal-name calls to `import_module`, `importlib.import_module` and `__import__` against the same reader and launch/control sets. Relative `import_module` names resolve only with a literal package or the module's `__package__`. An unresolved computed name or package fails with the importing module, line and expression unless that exact call and enclosing scope have a nonempty reason in the harness's `COMPUTED_IMPORTS` table or `ATTRIBUTION_COMPUTED_IMPORTS` beside its dependency set. The existing adapter factory is classified because the fixed adapter registry selects the program whose reader set already names its adapter and delegated readers. Classification is a reviewed source fact, not static proof of every possible computed target; the walker does not execute imports or resolve arbitrary aliases, reflection or generated code.

An unknown/ambiguous reader never gets guessed from filenames or content. A present empty record without WAL accounts as no turns. Other unknown-reader records receive a fingerprint-bound settled note and `+`; unchanged notes neither reparse nor relog across restarts. New bytes, reason or reader evidence permits a new attempt. Unreadable ownership is transient, retried once a minute. Established reader evidence permits ingestion and clears the note in that pass.

`launch_harnesses` records explicit program provenance beside stable `record_launches`. Missing/conflicting metadata stays unknown, never filled from pool provider or current seat preference. Table-change triggers invalidate it; read-only old books project unknown. Reader-registry observations are shared only within one account invocation, with metadata revalidation. Registration of a missing exact row rereads under its existing exclusive lock before appending. No cache or lock spans future passes or native reading.

SQLite itself may sync a hot rollback journal and database while recovering at open after a process crash, before `synchronous=OFF` takes effect. This recovery-only exception is not a steady-state write barrier. SQLite 3.46.1 marks the pragma [NeedSchema](https://github.com/sqlite/sqlite/blob/version-3.46.1/src/pragma.h#L552), [loads schema before applying it](https://github.com/sqlite/sqlite/blob/version-3.46.1/src/pragma.c#L478), and [syncs hot-journal recovery](https://github.com/sqlite/sqlite/blob/version-3.46.1/src/pager.c#L5053). The two hot-journal fixtures observed four native `fdatasync` calls.

### Malformed database recovery

Every writer open, including service construction, runs SQLite's read-only table-valued `quick_check` before schema setup, checking data pages as well as the header. Ordinary status, watch and ledger readers do not scan or move files; a `SQLITE_CORRUPT` or `SQLITE_NOTADB` they actually encounter reports the remedy to stop the service and run `qd ledger --recover`. Busy, locked, full, generic read-only and I/O errors are not corruption verdicts.

A positively malformed ledger and its `-journal`, `-wal` and `-shm` sidecars move unchanged into a dated `runtime/evidence/ledger-corrupt-.../` folder. A directory flock serializes writer initialization; recovery also takes the service lifetime lock before any move. Sidecars move before the database. Each rename preserves a whole file, including across an interrupted archive. The replacement uses ordinary fresh-ledger schema and owned-record catch-up. A status-line alarm names the evidence folder until `qd ledger --clear-recovery` writes an acknowledgment; acknowledgment deletes no evidence. Explicit recovery refuses a running service.

On the specific `SQLITE_READONLY_ROLLBACK` result, the writer first copies the database and all sidecars byte-identically into a fresh dated folder under those locks, then permits SQLite's normal rollback and runs `quick_check`. Healthy recovery removes only that provisional copy. Corrupt recovery keeps both the pre-rollback bytes and the files as they stand afterward, with the evidence alarm. Generic READONLY and I/O errors never enter this branch.

The only persistent framework SQLite file is `runtime/ledger.sqlite`. The accounting planner uses `:memory:`. Native OpenCode and Antigravity databases are snapshotted read-only into memory; unreadable native records are reported without moving or repairing program-owned originals (`one-folder`). An OpenCode database is snapshotted once per change: its snapshot, and the rows read from it, are kept in memory by the identity of the database and its `-wal` (device, inode, size, nanosecond modification and change times of each, and the log's absence), and reused only while that identity holds and was older than the post's two-second filesystem tick when the kept read began. A young, changed or unreadable database is read afresh, a gone path drops its entry, and the kept snapshots are bounded together (256 MiB, 64 databases, least recently used first), each counted with the one set of rows read from it, the latest: the length of their text and blob values. Nothing is kept across a service restart. Antigravity and the ledger's own snapshot are read afresh each time.

### Usage transaction ownership

Each actual usage attempt owns an independent atomic transaction containing cache, pacing attempt and any persisted hold. All service paths converge through `quota.record_read`/`Ledger.record_usage`; preparation checks ownership before credential/provider work. Record-derived usage uses that same owner without a provider request.

Incomplete intended DML rolls back. The standalone writer stores a unique receipt in the same transaction as the cache and pacing rows before it calls COMMIT. A raised COMMIT with an open transaction keeps its owner and retries that COMMIT. Once SQLite closes the transaction, the receipt proves whether the attempt committed or rolled back. A proved rollback clears the owner and fails that pass so the next usage attempt can write on the same connection. A failed receipt read keeps the owner and the next pass checks again. Older pacing rows and rows still visible inside an open transaction give no proof. Both usage entry points and record accounting settle the owner before they start another write. Unknown partial transactions and nested owners still refuse.

Three consecutive accounting preparation or transaction failures, including unreadable usage receipts and mixed causes, raise `accounting failing since <time>: <cause>`. The sliced duty checks pending usage ownership even when its idle certificate would skip accounting. A successful record pass clears record failures. Confirmed usage rollbacks have a separate streak. A duty pass with any confirmed rollback counts once, even if another pool commits or a deferred rollback is settled during record preparation. A pass that commits usage without a rollback clears the usage streak. A pass with no usage outcome leaves it as it was. The onset log includes an allowlisted exception type and a fixed message, with recognized SQLite or OS diagnostics where available. The status uses fixed causes. Per-record incomplete measurements and post-commit or usage errors retain their separate visibility.

Until records have been checked, status shows `accounting health unknown` below the usage alarm bound. A bounded usage alarm is visible even while the snapshot still records the check as pending. A bounded record alarm takes precedence over a usage alarm.

`accounting_health.py` publishes a disposable process-bound `runtime/accounting-health.json` beside heartbeat. Independent readers require live lock, fresh matching heartbeat, pid/start identity, fresh observation and valid shape. Invalid evidence is health unknown while the service runs, never healthy or an old process's alarm. Reads do not repair it. Status-cache reuse rechecks that fresh health fact; changed facts force collection. This snapshot authorizes no accounting or transport.

### Allowances and limits

A subscription window stores fraction, reset, burn and dated/stale evidence. A pool is spent for a model only when a relevant meter reports used >= 1.0 or the adapter proves a refusal at that limit. Near-limit/severity warnings never move a seat. A spent reading survives failed/stale reads until its reset or a newer valid reading with room. Key budgets use measured spend, with unknown spend counted separately; endpoint pools have no quota wall.

Usage attempts are paced from stored attempt times across service restarts. Claude's shared login is read at most every five minutes, with the pool's own sign-in, on the service's tick whether or not a seat sits on the pool (`idle_usage`), so an idle declared pool's figure is never days old; a live seat's read and the idle read share one clock, so the pool is read once per interval whichever made it, and never on a reading's demand. A failed call with no Retry-After of its own waits twice as long each time, from ten minutes to the hour, until a good read ends the wait; the failure is kept as the pool's latest read and shown with its reason. Retry-After holds last at least the interval and at most an hour, in memory. Call failures log safe status/retry/timeout/network/JSON categories, never tokens, headers or bodies. No-call states log only reason changes. Grok's declared background reader uses an owned billing home and the selected native ACP billing client, with a twenty-second deadline and conservative thirty-minute cadence; no new HTTP client is introduced. Credential refresh reconciliation surrounds private-home native reads.

Claude general 5h/7d and named family windows come from one response. Fable, Sonnet, Opus and Haiku remain distinct. Null optional windows are absent. A family list row needs its model scope, numeric percent, severity, reset and active flag; inactive does not cancel a full meter. Duplicate named/list representations agree only with equal fraction/error/uncertainty and resets within two seconds, retaining the later reset and either warning. Conflicts retain a complete spent representation whole; without one room is unknown. Fields from disagreeing readings are never spliced.

In Claude Code 2.1.317, exact kind `weekly_scoped` proves 7d; rendering group alone proves no period. Otherwise exactly one general reset within two seconds identifies the period. Unknown/ambiguous periods retain fraction/reset under a stable unknown-period name, with room unknown. Diagnostics retain key/type shapes and only bounded ASCII kind/group words, never account/header/body values. `pools.exhausted` stores bound warning evidence, exposed as `reading.warning`; severity alone is never a wall. A fresh uniquely matching known-period replacement may retire an absent old unknown-period cache row through adapter-declared `Window.replaces` and its two-second reset continuity. Failed, stale or ambiguous replacements preserve old evidence and historical measurements.

Native refusals live in `wall_events` with pool, reset and group; `wall_scopes` binds additional scope to the retained event identity. Conflicts stay unknown. Supported refusal forms are:

| Program | Evidence that establishes a wall |
| --- | --- |
| Claude Code 2.1.317 | API-error usage_limit_reached, rate_limit/rejected, future integer reset and known five_hour, seven_day, seven_day_sonnet or seven_day_opus type. Other rate errors/credits/overage remain unknown. |
| Antigravity 1.5.x | Individual quota reached with its stated reset; other errors remain unknown. |
| Codex 0.166.0 | Meter only; usage_limit_exceeded lacks a window/reset. |
| Grok 1.0.77 | Meter only; retrying rate_limited lacks a window/reset. |

The paying adapter's `quota_scope(event, model)` decides applicability. General Claude windows/refusals constrain all models, named families only proved members. Google requires explicit model/group relations or all-model statements; its unestablished membership tables supply no guessed room/wall. An unplaced Google refusal holds its own observed model/execution, never the whole pool. Record model evidence precedes screen evidence. Downgrades that ignore saved Google scope restore their older whole-pool policy while running.

Automatic destinations need all relevant current windows, including supplied matching-family rows, to prove room. An unknown unrelated family does not block; an absent optional family adds no invented constraint. A known relevant stale/malformed row cannot prove room. Explicit selection permits unknown usage but refuses a proved applicable wall. Source scope uses running record-first settings; destination scope uses its resolved choice. Unknown source family cannot prove a scoped wall, and unknown destination family with scoped rows cannot prove room. [Seats](seats.md) owns move admission and retained conversations.

Codex record token-count rate-limit events identify the allowance, not account. Window durations 300/10080 minutes identify 5h/7d regardless of slot. The service selects one newest eligible snapshot across current joined records saved to that paying pool, excluding pre-launch rows. It does not scan personal/history sessions or assemble siblings across snapshots. Event time dates the reading; rereads never renew it. Partial/newer failures retain uncertainty rather than falling back to an older complete observation. A supplied blocking window may prove spent; a missing expected sibling cannot prove room.

Detailed status/ledger retain window fractions, dates, groups, errors and resets. Headline windows are adapter-owned: Claude prefers 5h with a named 7d fallback when absent; Codex expects both; Google shows each returned group/bucket. Operational held-seat alerts use the same cached destination eligibility as routing. Lifecycle deferral with an eligible destination creates no held-limit alert. Unreadable Ledger evidence remains unknown.

Weekly spending forecasts retain accepted blocking `7d` readings (including named-family ` / 7d` windows) in `usage_samples`, in the same transaction as the latest tuple and attempt. Only the pool/window, observation time, fraction, reset and measurement scope/bucket are stored; no provider account data or extra provider request is needed. Duplicate observations do not create samples; conflicting values at one observation time make that point unusable. New reads prune samples older than a day for that pool. Existing books gain the table only through the service writer; read-only older books have no forecast, and missing history is not reconstructed from token counts.

The rate is the measured fraction increase divided by elapsed hours, using endpoints of at most three hours of contiguous same-reset/scope/bucket history. Two resets are the same when they lie within a minute: a provider's reset time jitters below the second from read to read, while a real reset moves by a week (`usage_forecast.same_reset`). This window reacts within a shift, including one that spends a week in roughly six hours, while averaging short bursts. At least three distinct observations spanning an hour are required. A gap over an hour, decreasing meter, identity/reset change or invalid observation ends that segment. Failed, future or hour-old latest readings, flat rates and already-spent meters produce no forecast. The exhaustion time starts from the actual last observation, not the time a status command runs. A prediction already in the past is suppressed rather than repeated as a future warning.

One weekly exhaustion forecast per declared subscription pool, the earliest among its windows that warn (the earliest overall when none warns, so a window that runs out only after its own earlier reset cannot hide another's warning), appears with rate, span and sample count in `qd ledger`. Before reset, the status line shows the pool and its projected local exhaustion time while the pool has room. Crowded status lines can group forecasts by count. The service saves fixed immutable report intents to declared systems recipients once per pool/reset (the same tolerance: a jittering reset is one week), before publication; restart, a changed estimate and a temporary clear do not rearm that week's notification. A later week can notify again. These are warnings only: they establish no wall, move no seat and change no destination eligibility. No forecast is emitted for unknown or insufficient history.

The regression fixtures include ordinary synthetic steady, bursty, flat, discontinuous and scoped series. A Grok ramp is explicitly a steady reconstruction from two retained readings, not a claim that intermediate observations survived. It contains only fractions and relative elapsed/reset times, shifted to an invented epoch; interpolated points test the estimator without introducing account data or claiming that the forecast actually ran that night.

### Attribution

Turns roll up by seat and order. `turn_attribution` stores verified message/time/bound evidence, roots and verdict beside stable turn/tool tables. Ingestion marks attribution pending; it cannot certify from `turn.input` alone. Replay never rewrites measurements, tools, prices or launch provenance merely to change attribution. Older readers retain their older attribution behavior.

Startup, changed post/source evidence and invalidated verdicts revisit stored turns, including retired seats. Saved bindings select readers. Missing records preserve measurements and established provenance; previously verified incoming evidence is retained only for unchanged seat/turn bounds and marked retained. Changed bounds require fresh evidence. Sources outside runtime without saved authority remain counted and unassociated, without even fingerprinting the external file. Their fixed reason is `legacy binding outside the runtime, no saved fingerprint`.

A stable successful replay may transactionally save `attribution_records`, binding reader/engine hashes, record/WAL, bindings, this record's own turn rows and relevant post ancestry/closing/header identities in their relative order. Other records contribute only whether more than one closed turn of the same seat contains a posted-message timestamp inside this record's turns. The key and verdict share an inclusive interval index: open, unknown and reversed intervals contain no timestamp. Each job prepares that index, the post-overlap vector and record keys once per participating seat; record visits only look up keys. The immutable post graph retains its post-time index and at most 8192 pure seat/time scope results across jobs; a changed graph retains neither. Closed intervals and ledger-derived keys are rebuilt every job. A disjoint later turn preserves historical certificates; a turn that closes over an old post, an overlap added/removed at that post, or changed own-record bounds invalidates the affected record. Incoming-envelope ambiguity still depends on all turns within its own record. Unrelated/later posts preserve historical certificates; related ancestors or ambiguity collisions invalidate them. Unknown readers, failed/unstable sources and pending verdicts grant no reuse. Invalidations from any writer force reconciliation. Failed reads retry; only completed replay advances the remembered snapshot. Changing this key changes the attribution engine stamp once, reopening attribution catch-up; native reader identities and committed native-record accounting checkpoints stay unchanged.

`qd ledger`, `--by seat` and `--by order` show tokens, cost, tools, minutes and machine use. These readings never write certificates or repair the book.

Hand conversations older than seven days may be retired, never deleted, after catch-up and its planning job finish. The service checks an exact committed `record_accounting` checkpoint, a closed native conversation, an earlier owning launch, old file modification times and the absence of open same-user process descriptors. A process whose descriptors cannot be listed holds the move when it bears one of the adapter's process names, except one whose every task (`/proc/<pid>/task`) has exited, Z, X or x: a zombie refuses its listing but holds no descriptor, while a thread-group leader reads Z as its other threads still run and hold the files, so it ends only when every task has. Every guard that keeps a record names itself, to a caller that asks (`run(..., declined=[])`) and once per record and guard in the log (`hand-transcript-held`). Current, unknown and unaccounted records stay. Without a ledger the duty returns before reading runtime state. Each adapter declares its native retirement bundle and process names; shared modules know only the framework's retained-home mapping. A bounded duty moves one record per pass under its seat lifecycle claim. Pi moves one JSONL file; OpenCode moves its per-launch `opencode` directory atomically, with DB/WAL/SHM and the native `log`, `repos`, `snapshot` and `tool-output` folders together (`tool-output` holds a large tool result of that launch). Unknown ancillary files hold the move. A record the pull-request screen lists as written by a screening launch (`runtime/pr-screen/records/<hand>.json`) holds an outsider's text, so it goes first: every hand's listed records in one walk before any ordinary one, outside the one-a-pass limit, at every service pass rather than every five minutes, and through a catch-up (never while an accounting job is open). It is moved without the week's wait, and even before the hand's next launch has a record; it waits only for its own accounting checkpoint and the other checks. While such a record is still in the home, no launch of that hand resumes (a restart, a relaunch's finish or a failover starts it fresh).

Retained bytes live at `runtime/retired/hand-transcripts/<seat>/home/<original relative path>`, outside the seat folder. `record_location.resolve` preserves original logical ledger keys and routes record fingerprints (including provenance), native JSON/SQLite reads, ownership reads and accounting input observations to those bytes. Native discovery includes retained paths, preserving replay and OpenCode launch numbering even after rebuilding the ledger. Attribution, receipt and native history readers share the same parsers; post threads and inboxes continue reading their immutable post files. Retired records are excluded from joins; native resume and a pinned retired record refuse plainly and direct a fresh conversation. No native source or stored measurement is rewritten by retirement.
