# Quarterdeck design: Harness adapters

A page of [the design](../DESIGN.md).

## 5. Harness adapters

An adapter owns every fact about one terminal program: launch, home, credentials, records, screen, controls, usage and dialogs. Code outside `harness/` uses that interface rather than naming programs. The base implements common record joining, state/turn reading and declared control lookup. The adapter's card teaches its program; fixtures capture its supported native forms. Unknown evidence stays unknown and grants no action.

### Interface

`Harness` in `harness/base.py` groups these responsibilities:

| Members | Contract |
| --- | --- |
| `name`, `program`, `home_variable` | Registry identity, selected executable and native home variable. |
| `build_home`, `launch`, `owns_launch` | Build a private home from ship files and credential links; produce argv/environment and recognize the saved launch. |
| `preflight`, `workspace_notice` | Read-only readiness and optional workspace information. Preflight performs no native/provider call or write; omitted context never implies the operator's home or cwd. Notices prove no activation or permission. |
| `records`, `first_timestamp`, `session_id`, `reader` | Find records, establish native launch time and resume identity, read state and ended turns. Joining uses the first post-launch record; ambiguity is reported, never guessed. |
| `inputs`, `record_time_resolution` | Accepted/queued/consumed input evidence for the shared exact receipt matcher. Positive timestamp resolution floors only its comparison boundary, never the saved attempt. |
| `recorded_paste`, `paste_ignored` | Only measured native transformations of a typed payload; defaults preserve it. |
| `attribution_inputs` | Additional structured watch-consumption evidence for accounting, never a delivery receipt. Complete post envelopes must still match the immutable store. |
| `screen`, `styled_screen`, `box`, `box_columns` | Composer, work state, dialogs and layout. Styled capture carries current pane identity. Unknown work/layout stays unknown; a boxless dialog-free startup frame waits within `start_seconds` (default 60). |
| `queued_input`, `queued_waiting` | Prove a newly visible native queue after a matched paste and its continued wait. Visibility never replaces an exact record receipt. |
| `paste_clear_rules`, `paste_clear_keys`, `keys` | Versioned cleanup descriptors and proved submit/interrupt gestures. No descriptor means no automatic cleanup. |
| `controls`, `interruptions`, `answer_seconds` | Supported launch/session controls, resulting-state confirmation and recognized dialogs; default answer observation bound is five seconds. |
| `queues_while_working`, `opening_prompt_turn` | Whether work accepts queued input and whether an opening brief starts a native turn. |
| `human_wake_box_margin`, `waking_inapplicability` | Explicit waking-row layout proof or named inapplicability; default unknown never authorizes a wake. |
| `check_tool_evidence` | Check-only bounded reading of the temporary seat's last eight call/result pairs, at most 32 KiB; no receipt/activity authority. |
| `native_provider`, `accepts` | Company identity and pool compatibility. `EndpointHarness` supplies endpoint home/readiness behavior. |
| `credential_file`, `freshness`, grant/renewal readers | Credential location, generation and known fixed/self-renewing/unknown grant facts, read only through declared native fields. |
| Usage readers, `headline_windows`, `shared_usage_key` | Subscription windows, cadence, shared readings and optional background/private-home work. Missing capability leaves usage unknown; key pools use spend. |
| `model_scoped_usage`, `usage_scope` | True/false/unknown model applicability. Running source settings are record-first; destinations use their resolved choices. |
| `quota_wall`, `screen_walls` | Only measured screen quota evidence and resets. |
| `remote_control`, `wrap_slack`, `drill_settings` | Remote access, layout margins and synthetic-only settings. |

JSON-lines adapters supply `take`/`end` on `JsonLinesReader`, optionally `identifies` for a different native envelope. Grok identifies ACP method/update markers without rewriting rows and retains physical line numbers. A database holding all sessions gets a data directory per launch, keeping one-record identity exact.

### Homes, trust and permissions

Adapters pass ship-owned files and launch overrides without editing the operator's configuration, instructions or repository. Operator HOME material stays outside seat homes. Frontier programs trust the declared working folder as their maker intends; program-specific restrictions require the ship's authorization. Generated prompt suggestions and self-update are disabled where supported. A program is selected through PATH or the declaration, without pinning an executable path/hash.

Programs run without native approval prompts. A seat requests a jail with `sandbox = true`; endpoint seats default to jailed unless explicitly false. A jail starts from an empty environment (`jail_environment`): bwrap's `--clearenv`, behind a launcher that itself execs with PATH alone, then only an allowlist named in one place: PATH, HOME, USER and LOGNAME, TMPDIR, XDG_RUNTIME_DIR, QD_SHIP, QD_SEAT, this ship's qd function for the seat's shells, the git identity, the pane's TERM, LANG, TZ and LC_*, and the variables the seat's harness declares for its program. Nothing whose name looks secret passes, whatever names it: a word of the name ending in KEY, TOKEN, SECRET, PASS, PASSWORD, PASSWD, PASSPHRASE, CREDENTIAL, CREDS, AUTH, COOKIE or JWT (with their plurals), or one of AUTHORIZATION, BEARER, PRIVATE, SIGNATURE and SALT; TOKEN before a word of counting (MAX, MIN, LIMIT, COUNT, BUDGET) is a number of tokens. A declared name that looks secret, such as a keyed endpoint's QD_ENDPOINT_KEY, refuses the launch. Unjailed seats and the service start from declared lists too, never the caller's whole environment, which may be a seat's pane (its QD_SEAT) or the desktop's shell (its secrets). The ship's own tmux server starts, and each new session is made, from the unjailed panes' list (`jail_environment.UNJAILED`): the framework's names the jail also has, the pane's TERM, LANG, TZ and LC_*, and the desktop session's DISPLAY, WAYLAND_DISPLAY, XDG_SESSION_*, XDG_CURRENT_DESKTOP, DBUS_SESSION_BUS_ADDRESS, SSH_AUTH_SOCK and XAUTHORITY, which a jail never receives; XAUTHORITY is the X cookie's path, which with DISPLAY lets an X program reach the desktop through XWayland, and an unjailed seat can read the file anyway. It stays in the operator's login session, so polkit prompts reach the screen. SUDO_ASKPASS reaches no seat, jailed or not, nor the ship's server nor the service: every list passes through one refusal beside `looks_secret` (`jail_environment.refused`), which drops it even where a list, a pool key or a harness names it, and every launch unsets it by name, so a seat can never raise a sudo prompt on the operator's screen; root beyond the security door goes only through pkexec. A seat's environment is not the only way in: an unjailed seat inherits the operator's HOME, and a program that runs its commands from a login shell reads that HOME's `~/.profile`, which on this machine exports SUDO_ASKPASS again and defines a `sudo()` function that asks for the password through it. Codex did so for every command, and kept the result in a shell snapshot in the seat's home that it sources before each. Its harness therefore writes `allow_login_shell = false` and `features.shell_snapshot = false` into the seat's config, at the top and in every profile, whatever a template or the seat's settings say; HOME stays the operator's, and his files are never written. Measured on Codex 0.166.0 through qd's own throwaway path, with a decoy HOME whose `.profile` exports a secret-looking name and defines `sudo()` (`tests/measure_codex_login_shell.py`, run by hand where Codex is signed in): before, the name, SUDO_ASKPASS and `sudo()` were in the snapshot and the name and SUDO_ASKPASS in the command's environment; after, no snapshot is written, neither reaches the command, `type sudo` names `/usr/bin/sudo`, and qd, git and python3 are still found. A session the service makes holds the desktop names DISPLAY and SSH_AUTH_SOCK only if whoever started the service had them, since tmux marks them removed in a new session when the creating client lacks them; so a ship raised at boot by its unit, or by a timer, makes sessions without them, as it does today. The service starts from its own list (`SERVICE`), named exactly with no prefix but the unjailed list's: the unjailed panes' list, what it needs to run (a test namespace's TMUX_TMPDIR, certificates and proxies), QD_SHIP and QD_DEFAULT_SHIP, and git's identity names; never a pool's key, whatever `api_key` a pool declares, since no seat runs on a key until the routed key isolation lands and an unjailed seat of the same user could read one in the service's `/proc/<pid>/environ`; never QD_SEAT, nor GIT_DIR, GIT_WORK_TREE, GIT_INDEX_FILE, GIT_OBJECT_DIRECTORY or GIT_SSH*, and QD_SHIP set to its own ship. QD_TMUX_SOCKET passes only where it is declared, a test's or the drill's private namespace; the ship file declares none. A running server keeps the environment it started with and gives it to every new window, so at each start the service unsets in the ship's own running server's global environment every name the unjailed list would not keep, and logs the names (`server-environment-cleaned`), never the values; the operator's default server and a test's are never touched. The plan refuses a jail that would show the operator's `~/.ssh`: one that leads outside the home, or whose real path is, holds or lies inside any path the jail's command binds. Those paths are read from the very places the command takes its binds from (`sandbox.shown`), so a bind added later is checked too. An unjailed seat is not contained: it keeps the desktop's D-Bus and the ssh agent, and reaches whatever they reach. It runs in a transient systemd scope of its own, `qd-service-<ship>-<random>.scope` (`systemd-run --user --scope --expand-environment=no`, which execs it as the same pid), so a stop of the caller's scope leaves it running; where systemd-run is absent or the user's manager cannot be reached, it starts as before and its proof line says why. Both lists are filtered by `looks_secret`, and an unjailed seat's program refuses a secret-looking name too, with one exception: the one variable its own pool's declared key fills. A key pool's key is the one secret a seat holds, because it is the seat's own credential, needed to run; a jail refuses even that. For now no seat runs on a key at all: until the routed key isolation lands, every launch on a pool paid by a key, jailed or not, is refused before anything of it is made (`ship.key_refusal`, see the ship file's pools). `sandbox.py` builds one recorded bubblewrap launch: read-only root, private capped tmp, empty operator home, required program/interpreter/PATH folders bound back read-only, writable workspace and own seat home, read-only ship with other seats hidden, and only that seat's own drop folder writable under a read-only `runtime/post`, so `qd post` writes a drop and the service files it; and that seat's own check proof folder writable, never another seat's. The ship's tmux socket is hidden and `QD_TMUX_SOCKET` absent. The runtime is fenced like the fleet: inside, `runtime/` is an empty folder, read-only once its mounts are in place, and only what a seat needs is shown read-only (`RUNTIME_SHOWN`: its git fence, the seat's own view of the post in the post's place (see the post's design), the seat's own brief (never the folder, which holds every seat's), the ship's own qd in `bin`, `venv`, `venv.prev` and `installed.json`, and the service's heartbeat, by its folder `heartbeat/`, so a running jail sees every beat), with the seat's own folder, drop and check proof folder writable. Everything else there is absent: the ledger, which a read-only reader holding a read could keep every writer from (and which holds every seat's usage); the logs and evidence; the usage readers' homes and the parked sign-ins, which a jail running as the same user could otherwise read; and any folder the runtime grows later. Among them is `runtime/trusted`, every seat's trusted folder (`trusted_files`): what the service writes for a seat and then decides from, its launch record and `launch.sh` among them, which is also an empty private tmpfs inside, as the locks are, so no jail can read or write it, its own seat's included (see the seats' design). A jailed cascade orchestrator therefore reads no ring state, and its `qd thread` shows a cascade's final without the ring's context. Every tmpfs inside is bounded: `/tmp` at 256 MiB, the hidden home at 16 MiB, and every fence and hidden folder (fleet, runtime, tmux, locks, trusted) at 1 MiB, so a jailed seat cannot fill the machine's memory. A jailed seat that declares a `cwd` of its own works in a folder of its own, compared by real path with links resolved: the plan refuses that folder when it is the framework's checkout or holds it, when it lies inside the checkout anywhere but `work/hands/<name>` or below, or, for the office's own seats such as its jailed desk, `office/work/<name>` or below with the office a real folder (the code, its history and hooks, the workers' worktrees and the captain's queue are what unjailed seats read and run), or when it is another declared seat's working directory, holds one or lies inside one, naming both seats and the folder, since the jail binds it writable. A declared cwd below the ship's own `work/` (the office desk's `work/desk`), or below the `work/` of the workspace the ship declares (a hand's `work/hands/<name>` in the framework's folder), is also walked at every launch as the declaration writes it, with `lstat` from the ship folder, or the workspace, down (`sandbox.check_own_work`): every step a real folder of this user, never a link, the folder itself set to 0700 under the ship's own `work/` and refused unless 0700 under the workspace's, since qd changes nothing outside its project folder, and a missing one refused, since only qd init makes one, and only under the ship's own `work/`; a cwd elsewhere that reaches either `work/` through a link is refused too. A ship whose common workspace is its own `work/` or a folder below it (the forum's `workspace = "work"`), or a seat whose cwd is `work/` itself, has that folder walked the same way, from the ship folder down, before a jailed seat working there is launched: no link at any step, a real folder of this user, set to 0700, and refused when the ship found it elsewhere when it was read; a workspace written elsewhere that reaches the ship's own `work/` through a link is refused. In the office, qd init makes such a folder as it makes `work/desk`, and the office's repository then ignores `work/`, since nothing a jailed seat writes there is the office's (`setup.jailed_work_folders`); a jailed seat at `work/` itself works alone there, since the plan refuses one whose folder holds another seat's. An unjailed seat is not checked. Loading a ship resolves a cwd, and a relative workspace, so the declaration's own paths are kept beside them (`declared_cwd`, `declared_workspace`) for this walk. A hand works in `work/hands/<name>`. A seat at the ship's common workspace, and qd check's seats there, are not bound by it, nor counted as another seat; nor is a declared cwd that is the common workspace or holds it, such as a seat's `~/dev` above the project, for a jailed cwd inside the common workspace by real path, since lying inside it there is lying inside the common workspace, which the checkout rule rules; a jailed cwd under such a folder but outside the common workspace lies inside that seat's own folder and is refused, naming both seats and the folder. Jailed readings explain their limited visibility.

A seat's program record lies in its home, which its jail can write, and every reader opens it the same way (`record_file`): the folders from the seat folder down are opened one by one with `O_NOFOLLOW`, so a folder the jail swapped for a link (into another seat's home, or the operator's files, where the owner and inode checks would pass) is refused; the name itself is checked with `lstat` and opened with `O_NOFOLLOW|O_NONBLOCK`, so a link, a fifo, a socket or a device is never read and a fifo can never hold the service's read; and the open descriptor's `fstat` must show this user's own regular file, the one the name showed, with no other name (`st_nlink` 1). One read takes at most a bound: 128 MiB for a JSON-lines record and 512 MiB for a SQLite record (OpenCode's, Antigravity's) with its log. On 15 November the largest were a Codex rollout of 74.1 MiB and a Claude conversation of 61.0 MiB, and an OpenCode database of 198.6 MiB with a 4.0 MiB log; a JSON-lines read cost about 7.4 ms and 11.6 MB of memory per MiB (a 74.1 MiB parse 0.55 s and 864 MB at its peak), a SQLite copy about 3.1 times the file. A record past its bound, by its `fstat` or by what the read finds as it grows, is not read at all: the reading is unknown and says `record past the read bound (<size>, bound <bound>); not read`, never a state taken from part of it, and the accounting's failure for it is `record past the read bound`. Its turns cannot be counted, so they are reported, never guessed: from three quarters of the bound the status line says `<seat>: record <size> of its <bound> read bound; start it fresh at a natural break`, and past it `<seat>: record past the read bound (<size>, bound <bound>); not read; start it fresh`, measured by the read's own walk from the seat folder and never read, so a link on the way gives no figure rather than a followed one; a fresh start begins a new record. A seat the operator owns, the desk or an office seat, is named from its owned record pointer, never by reading its conversation: those are the longest conversations on the ship, and so the likeliest to reach the bound first. A read larger than 32 MiB waits for any other such read in the process, so the service never holds two near the bound at once. The ship's own ledger goes through the same SQLite snapshot for the accounting's planning book, opened the same way but with no bound, since it is not a seat's; it held 92 MiB on 15 November.

The folders a jail writes on the disk are bounded by the service's write-bound alarm (`write_bound`), which needs no daemon and no root: the seat's own folder at 4 GiB, its workspace at 2 GiB, and its drop, check proof folder and an endpoint seat's relay folder at 64 MiB together. A hand's seat folder held 101 to 642 MiB on 15 November, its transcripts most of it. The alarm finds each jail by its process, the outermost `bwrap` of this user that binds a declared seat's own folder writable in a pid namespace of its own, and measures exactly the folders that process binds writable (`--bind`, `--bind-try`), so a seat's launch record, which its jail can write, is never trusted for a pid or a folder. The alarm never reads a jail's pid from the seat's `launch.json`, which lies in the seat folder the jail writes, so a forged pid there can never aim the kill at another process of the operator. Each folder is walked by descriptors, `openat` with `O_NOFOLLOW` from the held descriptor of its parent and `fstatat` without following, so no path is longer than one name and no link is followed; it stays on the folder's device, counts each inode once in its group by its blocks on the disk, and adds the regular files the jail's processes hold open after unlinking them (from `/proc/<pid>/fd`), which no walk can see, to the largest bound on their device. A walk that passes 200,000 entries, 512 folders deep or 2 s of the alarm thread's own CPU time (`time.thread_time`) reads as over, so a jail cannot hide behind a costly tree; it drives that CPU time only through what it builds, which the entry bound caps. The walk is bounded on the clock too, at 10 s, but the clock measures how busy the service and the machine are, not the jail: on 15 November a hand's 47-entry home passed a 2 s clock bound at load 12 to 16, its alarm thread starved by the busy service, and the hand was killed with 531 MB of its 4 GB. So a walk cut short by the clock reads as unmeasured: the seat stays up, the status line says `<seat>: write bound unmeasured, <n> of 3 passes in a row (<why>); retried each pass, stopped at 3`, and the next pass retries with the same bounds. What the cut walk reached still counts, and if it already passes a bound the seat is over at once. A jail can load the machine on purpose, so unmeasured is no free window: three unmeasured passes in a row stop the seat as a measured over does, about 30 s at most, and a measured pass, a stop, or no jail left running ends the count (`runtime/post/write-bound/unmeasured/<seat>.json`, which no jail is shown); a count that is there but cannot be read starts again at one, and the service says so in one log line, once while it stays so. One look over every jail has 10 s on the clock: a walk once started runs to its own bounds, the seats the look did not reach are measured first on the next look, so no seat waits behind another's slow walk for more than one look. The processes' open files are read first and the small folders walked first, so a walk the clock cuts short has most often read whole every device but the one it was cut on. A backstop no walk can be starved out of ends each look: one `statvfs` for each device a jail writes, its free space as a user's write sees it (`f_bavail`). Under its floor, the smaller of 50 GiB and 5% of the device (`FLOOR_BYTES`, `FLOOR_SHARE`, counted as `f_bavail`), or fallen more than 20 GiB since the last look, the device stops every jailed seat that went unmeasured there this look or whose bytes there grew since its last whole measure; a seat measured whole there and not grown stays up, and its first measure is its baseline, so a restarted service stops nobody for a disk that was already low. A device whose `statvfs` fails is logged and skipped for that look, so its floor fails open while the walks still stand; when it fails two looks running the status line says `write bound: free space unread on <folder>, <n> looks running (<error>); its floor is not watched there` (`runtime/post/write-bound/floor/unread.json`, which no jail is shown), until a reading succeeds again. Its hold says why, the status line says `<seat>: stopped by its disk's free-space floor (<folder>: <free> free, under its floor of <floor>; this seat went unmeasured there); held: qd up <seat> lifts it`, and the service tells the desk and the systems seats at once, by the alarm road a held seat's selection takes. The larger of the two was under both disks of this machine on 15 November: / held 369.3 GiB free of 7389 GiB, 5% being 369.5 GiB, and `/tmp` is 44.9 GiB in all. An endpoint seat's relay folder on `/tmp` is in the 64 MiB group, so its walk catches a jail there long before any floor; the floor is the backstop for the disk. Over a bound the alarm places the seat's hold first, `runtime/post/write-bound/<seat>.json`, which no jail is shown, and clears the seat's relaunch intent; then it stops the jail's whole process tree with SIGSTOP and kills it with SIGKILL, an endpoint seat's relay included, signalling a process only while its pid still has the start it was found with. The hold registers in `relaunch_intent.HOLDS`, every launch refuses while it stands, a whole ship's `qd up` leaves the seat down and says so, and every ship session's status line names it: `<seat>: stopped at its write bound (<group> <held> of <bound>); held: qd up <seat> lifts it`. Only a word for that seat lifts it: `qd up`, `qd fresh` or `qd restart` with the seat named, logged with who gave it; a hold that cannot be read still holds. The service runs the alarm in a thread of its own every second, so a pass that hangs never delays it. The same thread, at most once a minute after a look, sweeps a stray sandbox (see the seats' design, "The sweep of a stray sandbox"). The overshoot is the write rate times the period: measured, a writer at full speed was stopped 0.08 GiB past a 2 GiB bound at a 1 s look, and 1.97 GiB past it at 5 s. A look over the four hands' jails took about 50 ms. Beside it the jail's launcher caps any one file at 1 GiB (`RLIMIT_FSIZE`, soft and hard, from `jail_environment.FILE_BYTES`) and gives `SIGXFSZ` its default action, which Python ignores: a write past the cap fails with EFBIG in Python, Node and Bun, which handle the signal themselves, and ends a program such as `dd`.

An endpoint seat's relay runs its jail as its child and is a subreaper (`PR_SET_CHILD_SUBREAPER`), so a jail's inner `bwrap` orphaned by its outer one's death comes to the relay rather than to the user's manager. Before the relay exits, at its jail's end or at its pane's hangup, which it forwards to the jail, it ends everything left under it through the write bound's own kill, confirms it gone and reaps it, for at most 5 s; its exit status stays its jail's. What still runs then is the seat's stop's to hold (seats' design, "A sandbox ends whole"). Each launch's relay has a folder of its own, named by the seat and a token the plan draws for that launch (`Jail.launch`); the launch record's argv holds that name. A relay removes only its own folder, so an older relay that exits after a relaunch leaves the new launch's folder and its way to the model whole. A folder whose relay died without cleaning stays as it is: a dead socket and a copy of the hosts file, mode 0700, read by no later launch, and cleared with /tmp at boot. No sweep removes it, since a sweep could only guess that its relay is gone, and removing a live relay's folder is the very fault this rule ends.

The program's home is the seat home. The empty-home mount is depth ordered after ancestors and before allowed descendants. A workspace equal to home or any bind-back that exposes home or an ancestor refuses by path. A fleet folder, `ships/` or `office/`, that is the home or contains it refuses the same way. Inside, `ships/` and `office/` are empty read-only folders, with only the seat's own ship and the peer declarations found at launch bound back. A program or PATH folder that would be bound back is judged by its real path as well as the path it is named by, since bubblewrap follows a link: it is dropped where either is, or lies inside, this ship's folder, a fleet folder or another ship's runtime, and where a path through a link leads to a folder holding the fleet or this ship's folder, which the fences cover only at their own paths. The fence is a mount at the folder's own path, which bubblewrap can make only where the jail can write: a fleet folder missing at launch, under a parent seen read-only inside (the root for a project outside the home, or a folder bound back, such as the framework's own checkout that `qd` runs from), would get no fence, and a ship raised there later would show. So the launch makes a missing fleet folder, empty, in the project first, and refuses by path one it cannot make or one that is a link or a file. A workspace inside `ships/` or `office/` refuses by path, since the fence would leave it absent inside, with one exception: the seat's own ship's `work` folder, as the forum's reviewer has it, is mounted writable after the ship's own read-only folder. No other folder of the ship may be a jailed workspace: `homes/` holds settings and code that unjailed seats load, `.git` runs hooks when qd commits the declaration, and `roles/` and `orders.md` go into unjailed seats' briefs, so writing there would escape the jail. A jailed OpenCode hand's finder starts in the folder it works in, which the seat gives its adapter by one rule (`Seat.adapter_spec`, `ship.cwd_of`) at its launch and at every resume's preflight alike: its declared `cwd`, or the ship's workspace when it declares none, so a resume is checked against the folder its launch worked in. `QD_WORKSPACE` names that folder. The adapter's own fallback to the seat's runtime work folder, for a seat given no `cwd` at all, is reached by no seat. Resume requires the saved session directory to match that same folder; a mismatch names the recorded and expected directories and refuses before closing the old program. Fresh start retains the old record and carries open work.

### Versions, checks and controls

Adapters apply their newest known facts to later versions as best effort; an unproven version alone does not hold launch. Status separates running, installed and proven versions. `qd check <harness>` uses a throwaway seat to prove launch, readiness, full folded paste verification, exact receipt, a task/file and closing report, join and ended record. Fixtures separately cover record shapes, usage, controls and dialogs. A changed unrecognized form withholds rather than guesses.

Optional check `--model ID` affects only that seat. Requested identity must be confirmed record-first, with startup screen fallback and an owned-record model at completion. An explicit contradictory screen model prevents success; an absent screen model does not negate a confirming record. Proof names requested, launched and recorded models.

`version(home=None)` normally runs the selected program's version command. Only explicit `private_version_home` adapters receive an empty temporary home under an existing fenced runtime; no context creates a runtime just to inspect a version and no executed call retries without context. Grok uses `env -i`, controlled native ENV, selected PATH and that home for HOME/GROK_HOME. Context-free Grok executes nothing and parses only a recognized selected binary basename; otherwise version is unknown.

Launch controls apply when starting. In-session controls leave their visible command in the native log and avoid a restart. Launch-only changes require a stated restart. Confirmation needs resulting native state, never command echo. A pending control owns its dialog continuation, saved once claim and original thirty-second deadline. Only its requested-value-matched option, proved focus and unchanged command binding allow an answer. Uncertain gestures are observed or expire, never repeated. A person's independent `/model` dialog remains obstructed.

Claude Code 2.1.317's model answer is Enter on the highlighted, exact-display Yes option, at the measured 120×40 styled frame with hidden composer/cursor. Expected display comes from the fresh exact home catalog, without picker overrides. Confirmation requires the linked caveat, exact command and successful result after the saved complete-row byte boundary in the same unchanged-prefix record. Display alone, old results, unsupported geometry/style or missing command linkage cannot confirm it. The synthetic adapter uses its own linked command/result form; an initially unjoined synthetic control may observe a joined result but grants no dialog key. On any other Claude Code version the model control answers nothing, so a change to a seat's model holds untyped, its request waiting on the status line. Measure the model control on a new version, and admit it in the adapter, before the crew runs that version.

### Selections and explicit defaults

`harness/capabilities.py` owns pure effort/default metadata. Capabilities distinguish levels, none, unknown and synthetic unrestricted text; complete vocabulary and exact-version measurement are separate. Pi's complete vocabulary is off/minimal/low/medium/high/xhigh, measured on 0.74.2; OpenCode has no seat effort control. Other CLI vocabularies remain unmeasured until established. Catalog/model support cannot be inferred from a level.

Pure ship loading rejects concrete effort on a no-effort harness or outside a universally complete vocabulary. Doctor, launch and running controls reuse their appropriate installed/running version observation. An unmeasured version passes with an explicit unchecked note; missing evidence is never invented. Cascade validates each effective choice. `qd controls --harness NAME` exposes the same metadata without ship lookup, tmux or native probes; it conflicts with an explicit seat.

Independent `model_mode`/`effort_mode` values are named or program-default. Named requires its string; explicit default requires it absent. Omitted modes retain legacy strings, including literal `default`. String pool choices inherit modes; inline choices own/reset theirs.
