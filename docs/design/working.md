# Quarterdeck design: Working on the framework from a ship

A page of [the design](../DESIGN.md).

## 15. Working on the framework from a ship

Sync refuses links along the runtime, staging and live resource paths before mutation. Every installation phase, including venv creation, pip, resources, version, laws, durable state and startup, belongs to the same failure boundary. Failure restores the earlier directory to the canonical live path and restarts its service if it had been running; a first failed install removes the incomplete environment and starts no seats. A storage, stop, restore, restart or cleanup failure keeps the operation visible rather than claiming completion.

**Target resources.** The explicit per-file `[tool.setuptools.data-files]` declaration in the target commit's `pyproject.toml` is the one authority for packaged laws, cards and templates. Wheel and source distributions use those same source files; there is no second resource tree or recursive ship inventory. Even an unchanged incumbent with an older literal copy list already pip-installs the target, so that original call bootstraps new templates after one sync across this fix. The first declaration retains every root the supported old incumbents copy: their subsequent old copy step rewrites target-identical files and does not remove newly packaged roots. This covers the historical standing-orders/drydock incumbent and the later forum/cascade incumbents; it cannot change an old caller's behavior if a future target removes a root that caller requires.

Updated sync code reads the archived target's declaration before installation, then replaces the managed `share/quarterdeck` tree with exactly those files after pip, including on rollback. It first builds the complete replacement in a temporary sibling. Read and diagnostic commands never synchronize or repair resources. For targets before the declaration, `resources.py` reads at most 1 MiB and 20,000 AST nodes of the target's installer without importing or executing it. It recognizes one direct literal copy tuple with the historical remove/copy statements and optional simple absent-template skip, then inventories only those declared roots. There is no inferred historical root catalog. Missing, dynamic, ambiguous or otherwise unsupported legacy shapes do not prevent emergency rollback: after pip, the explicitly authorized baseline fallback copies only the target's `standing-orders` and `ships/drydock` roots, each only if present, and runs ordinary installed laws proof. Other share contents are left as pip left them; one output line warns that extra templates may remain. This named fallback is separate from the authoritative packaging declaration. Only when the target has no standing orders at all does proof use `--help` instead, with an explicit laws/cards-unavailable line that does not promise usable seat briefs. Ordinary service restart, re-brief and seat lifecycle keep their existing behavior after successful proof.

The real live directory is always `runtime/venv`, and the copy before it is the real `runtime/venv.prev`. Before touching live code, sync journals the operation, stops the service, captures its brief/launch baseline and runs `cp -a` of the live copy to `runtime/venv.backup`, a destination that must be absent. Copied files and directory entries reach durable storage before live mutation is permitted. The backup's shebangs still name the canonical live path; no command or proof runs at the backup path. `venv.prev` is not touched until the new copy is active: only then does cleanup remove it and journal the rename of the backup into its place. A sync that fails at any phase therefore leaves `venv`, `venv.prev` and their recorded facts as they were, and `--back` still returns afterwards: a failed install removes failed live code and journals the rename of the complete backup back to the live path; a failed copy removes the partial backup. A journal written before the backup had its own role kept the backup at `venv.prev`; recovery still restores from there and keeps no previous copy, as that code did. An older framework that recovers a journal with `venv.backup` holds it pending once live code was changed, finding no backup at `venv.prev`; before that it undoes the operation its own way, consuming `venv.prev` as it always did and leaving the partial `venv.backup`, which the next sync refuses by name until it is removed. Peak disk use during a sync is three copies. `venv.swap` is a temporary rename role during back, never a retained copy.

`installed.json` contains current/previous facts, a bounded pending journal and the last fixed failure, with the old `commit/ref/at/previous` projection for historical readers. The journal precedes each rename; runtime directory fsync follows it. Directory identities distinguish the two roles even for same-commit force installs. Recovery can settle a rename cut on either side, undo incomplete changes, or finish cleanup after durable activation. Reads never perform recovery. Normal sync and normal up recover under the install lock before new work or any seat. Service bootstrap does so before constructing Service, opening its ledger or taking its service lock, and execs restored code whenever recovery could have replaced loaded modules. A stopped ship may remain stopped until its next normal up; no unattended restart is promised.

A live parent holds the install lock through startup. A token tied to its process identity allows only its target-ready or restored child bootstrap to proceed without trying to take that same lock. After its own service lock, the child acknowledges the copy identity captured at module load, its source digest, process identity and startup token; parent confirmation is bounded to 30 seconds. Missing or mismatching evidence is unknown, not a successful target startup. The target's own literal `COPY_SAFETY` declaration states whether it implements this contract. Historical handlers keep their old in-place behavior and receive an explicit warning; no feature marker is fabricated in their source. A valid historical success record is simply the current copy, with no migration, alias or extra proof at adoption. Back is unavailable until a real sync creates a recorded previous copy.

`--back` needs no checkout, Git, archive, pip or build. It journals and fsyncs exactly three forward renames: live to swap, previous to live, swap to previous. It then runs the same canonical-path package/prefix/resource, version and ordinary laws proof as sync. On failure it journals inverse renames, restores the original current copy and restarts it where it had run; only once that restoration is safe is the failed candidate removed. Interrupted inverse renames are recoverable too. Back again can return to the other recorded copy after success. A stable same-commit sync without `--force` is a true no-op: no backup, install, proof, state write, rebrief or restart. Force uses the same two real paths.

Both proofs use the live executable, remove inherited ship/source redirects and omit `--ship`, so a handoff cannot prove a different copy. Version return status is checked. Proof records contain disposition and command kinds, not native output. The historical resource fallback below remains explicit; a target lacking standing orders can answer help without promising usable seat briefs. Persisted proof is not a claim to detect arbitrary later disk tampering.

This also supplies the resource packaging mechanism for ordinary installs. Fresh installed laws/fake-drill acceptance and the installed-package omission inventory remain separate acceptance work; this sync change does not establish those proofs.

The most common work a ship does is work on Quarterdeck itself, so the loop has to be short and safe. Three facts shape it. The checkout a running ship uses is live: the seats run its `qd` on every post, so a half-edited file there breaks every seat at once. The service runs the code it loaded at its start, so a change to the service's own modules reaches it only by a restart, which the seats do not notice. And a worktree on a temporary filesystem loses uncommitted work at a reboot.

So: work on the framework happens in worktrees under `work/`, inside the project folder and ignored by its repository, never in the checkout itself; each worktree gets its own venv and its own test run, one suite at a time. A change is reviewed at its tip, once, by the captain, who reproduces what it doubts and writes down what it only suspects; its commit is its record, and no manifest or backup stands beside it. The desk lands it: a fast-forward of the checkout the ship runs, then the service restarted by `qd up`, which leaves the seats as they are; a seat picks up the new `qd` at its next command and a new adapter at its next restart. A landing may not move the schema under a running service, which is why the service alone writes the Ledger and every reading opens it read-only.

**The test tool.** `python3 -I tests/testrun.py` is the one way a seat runs the suite and cleans up after a change. It is the repository's own tool, standard library only, shipped with the tests and imported by nothing in `src/`; the framework neither depends on it nor installs it. Its durable results and control records live under the project's ignored `.testruns/`, whose project is the parent of the Git common directory, the same from every worktree. Working files prefer an owned project-specific folder in memory; committed author worktrees stay on disk.

- `run [--fast|--whole|targets] [--target PATH] [--ci-layout] [-n N] [--timeout S] [--wait S]` tests the committed HEAD of the worktree Git resolves from `--target` or the current directory, never from where the tool's own file lives, so a worktree older than the tool is run by the main checkout's copy with `--target`. A worktree with uncommitted changes refuses; a WIP commit makes the result name exactly what ran. The run holds a complete set from four eight-worker project slots (four lock files, with the original `slot.lock` retained as the first): fast takes two, whole or named targets one; each fast run defaults to 16 workers (at most 16), while whole and named-target runs default to eight (at most eight). With no targets the selection is `fast`: whichever of `tests/unit` and `tests/contract` exist in the resolved target, in that order. `--fast` makes that choice explicit. A project with neither falls back to its original whole-project pytest discovery with no positional targets, eight default workers and one slot; its first line and recorded reason say `no tests/unit or tests/contract`. Selection and worker defaults resolve only after the target project is known, so constructing a runner for its bound/alarm helpers does not read selection fields. A signing run chooses `--whole`, which passes the complete `tests` directory to pytest; named targets cannot be combined with a lane flag and are labeled separately, even when a named path is `tests`. The first line names the actual fast directories (`fast: unit, contract` when both exist), `whole` with any fallback reason, or the named targets, and the result/report retain the selected name, exact targets and worker count. Older results without this field remain unrecorded rather than inferred to be a signing selection. A run without enough free slots refuses at once with the holder notes or waits as long as `--wait` says; two fast runs, or one fast plus two whole runs, fill the four slots. Acquisition releases any incomplete nonblocking attempt before waiting, so a fast run never waits holding just one slot. Once admitted it checks the commit out detached in its own scratch, makes a venv on the ordinary `python3` with the system's read-only test tools and, by one plain `.pth` path line resolved from that interpreter before HOME is replaced, its user site (where `pip --user` tools such as pytest-xdist live; the line adds the directory only, so no `.pth` file or finder inside it is processed; the tools' bytecode there must already be current, the user site's bytecode folders are stamped before and after, and a change holds the run's cleanup), installs the checkout editable with no index, proves every package imports from that checkout, compiles the run's own code and makes its package folders read-only before any reader starts, and runs pytest in its own session with an evidence plugin of public hooks. HOME, the XDG folders, TMPDIR, pip's cache and the build all lie in the scratch; PATH is the caller's own; variables that would redirect Python, pip, pytest or git are removed and only their names recorded. Every interpreter of the run, pytest's, its xdist workers' and any child a test starts, runs with `PYTHONNOUSERSITE=1`, recorded among the fixed settings, so none processes a user site's `.pth` files or startup hooks and the user site is seen only through that path line, its base carried for a run started inside a run under the tool's own `TESTRUNS_USERBASE`, never as `PYTHONUSERBASE`. A run's time has two bounds, each named by what it covers. Setup, from the tool's start to pytest's, has its own fixed 600 s, the wait for a slot not counted; when it runs out the run ends as a timeout, exit 3, its line `time limit of setup, 600 s`. `--timeout` bounds pytest alone, counted from pytest's start (default 3600 s), and ends it as a timeout, exit 3, its line `time limit of S s`. The wait for a slot is outside both and governed by `--wait` alone, so a run's whole time is at most `--wait` plus 600 s plus `--timeout`.
- Every ending, pass, failure, error, timeout, interruption or a runner that died and was recovered, leaves exactly `results/<run>/result.json`, `report.md` and `failures/NNN.txt`, one complete file per failing test, once cleanup proves its recorded paths gone. Recovery ownership records persist there only while scratch or recorded sessions are kept, held or interrupted; a clean ending removes those records too. The result names the target's commit and tree, the runner's own files by hash, the exact command, tool versions and safe settings, the exits of the wrapper, pytest, a signal and the cleanup as separate numbers, and the source manifests before and after. Each run folder carries a random owner token written when it is made, so a folder recreated in its place, even one that reuses the inode number, is refused at removal. Counts are stated only when every expected item, the xdist workers' collection included, reached a terminal report and the session finished in agreement; otherwise they are unknown, and what is known, a collection error or a failure, stays. A run stopped before pytest's collection completed states no expected count either: what it would have run is unknown, not empty, and its report says whether it stopped in setup or during collection. pytest reports a collection it was interrupted in as if finished, so the evidence plugin marks one that completed, errors included; an unmarked collection is partial, and the tests it names that never reached a terminal report are kept as at least these. Every recorded process counts, each xdist worker the controller knows of or whose recorder started, and each must have marked its own collection. Evidence of the plugin's first version, which has no mark, is read as before only when every process reports that version, and the report says so; versions that differ or are missing leave the collection unverified. The report holds the complete console. Nothing is retried.
- `clean --change BRANCH [--drop --reason TEXT]` retires a change the tool registered at its first run: its worktree by an unforced `git worktree remove` and its branch, once the branch is merged into main, or by a drop recorded first with its reason and bound to the branch's tip. It refuses main, an unregistered change, a worktree replaced since registration, in use by one of this user's processes, or holding anything Git reports, ignored files included, since the tool recorded none of them; results, reports and failures stay. A journal makes an interrupted clean resumable.
- `run --jail` runs every step that executes the target's code, the venv, its install, the import proof, compiling and pytest, inside bubblewrap, built by listing what goes in: `--unshare-all` (no network but loopback, private processes), a cleared environment refilled from an allowlist of the run's own names, a read-only `/usr` and a listed few files of `/etc`, a private `/tmp`, bubblewrap's minimal `/dev`, the run's scratch writable, and read-only the user site that supplies the test tools and the project's Git folder, with the run checkout's own admin entry writable. Nothing else of /home or /run/user is inside: not the ssh agent, the desktop's bus or the live tmux folder. The checkout is made with hooks off. The jail comes from the invoked tool; a tool lying inside its own target is refused. Since the project's Git folder is inside, read-only, `--jail` also refuses, naming the key and file but never the value, when the project's Git config, its worktree configs or any file they include, conditionally or not, holds a credential helper, an http extraheader, or a URL with user info (any password, or any user on http, https or ftp); an ssh login such as `git@host:path` is no credential. The run's `--timeout` and per-process `--memory-mib` hold inside it, and the result's `jail` and the report's `jailed` line state the jail and the tool commit that built it. A crew run stays unjailed unless asked.
- `keep RUN --reason TEXT` keeps one run's scratch past its end and its change's clean, recorded with its reason.
- The detached checkout is `checkout-<run>` under the run's recorded working storage, replacing the old fixed basename `checkout`. Before `git worktree add` starts, both scratch state and retained ownership record that path and the intended `.git/worktrees/checkout-<run>` entry. The entry must be absent before add and must match Git's actual admin path afterwards. Cleanup validates its backlink to this checkout, removes only that recorded entry and verifies its absence; a stop during checkout cannot silently leave an entry while claiming complete. An incomplete or mismatching entry, or a failed removal that leaves it present, holds cleanup with the reason. Older recorded runs retain their original checkout path.
- Start-event tool versions and plugin names are type-checked before their summaries are built. Malformed fields become named causes of incomplete evidence, with counts unknown and observed reports retained, rather than aborting finalization. Optional absent tool versions remain null.
- `retire RUN [--wait S]` retries retirement of exactly one recorded crashed run in this project; RUN is an exact run identifier, never a filesystem path, branch, age or name pattern. It holds one of the four slots and an exclusive guard on that exact result directory, and requires the run lock to be free, retains keep notes, and holds while the recorded runner or its groups are live or uncertain. It does not signal arbitrary processes. Its one shutdown action is an explicitly addressed, ownership-proved private tmux server. The first terminal result, report and failure output stay unchanged; the command's separate result at `.testruns/retirements/<run>.json` records cleanup without rewriting the first result, report or failure bytes. Successful retirement removes its temporary recovery records from `results/<run>/` too. `ownership.json` persists the scratch identity, owner token and recorded checkout outside the scratch before removal, so a partially removed state file does not erase recovery authority. Older runs need their own intact state and owner token; missing or unreadable ownership is held, never inferred. Absent already-retired paths are an idempotent success.
- Scratch retirement shares one 45-second monotonic budget and 2,000,000 traversal checks across validation, removal and writer-race retries. Vanished children are tolerated inside the verified tree; a directory that fills again is retried within the same budget. An ordinary cleanup error or expiry reports the exact remaining path and preserves the test outcome. Partial removal keeps the root owner token for retry. The finalization alarm remains 60 seconds with a five-second emergency report; explicit `retire` uses those same outer limits after slot acquisition, preserving the first result on timeout and writing a separate timeout notice when possible. An interruption between the final marker unlink and directory removal can leave ownership unprovable, which is held rather than adopted.
- The tool gives its pytest the separate short `.testruns/r` socket anchor, so its outer fixtures do not appear in direct pytest’s shared `.testruns/s`. Each tool-run session fixture records its exact newly created socket container, anchor, identity and owner token under `results/<run>/sessions/` before use. Records without an anchor retain the original `s` meaning. Child pytest using another project or a nested fixture keeps its ordinary local cleanup and does not register that container as a direct child of the outer anchor. Cleanup considers only these records, never whether the shared `.testruns/s` is globally empty. Private server births are recorded with the socket, namespace and lock identities, process ID/start, boot and random server owner before use. Stop and retire address only those servers, with explicit `tmux -S <recorded-socket> -N`; a guarded shutdown verifies the server ID and birth owner. A dead socket is unlinked only after that process has ended and the endpoint refuses a connection; a process has ended when /proc no longer shows it, or shows it exited, as a zombie (Z) or in the instant of its reaping (X, x before Linux 4.14), and the tool's process-group and session reads exclude the same states, then its recorded lock and empty namespace are removed. A legacy server additionally needs the matching recorded session identity/token, qd namespace header and its own process environment naming this run; that proof is persisted before shutdown. Unprovable, replaced or live-listener endpoints remain held with their reason. Only empty recorded containers and empty native socket subdirectories are removed; no namespace is recursively erased. Other runs and unrecorded legacy sessions are neither inventoried nor removed. These ownership records remain for explicit retirement after an interrupted or held run, and disappear once every recorded container is proved gone. Unrecorded peers never make a completed run retain its own metadata.
- On interruption or timeout, the step's whole recorded session is signalled and waited on through interrupt, terminate and kill, even after its shell exits; child process groups in that session are included. Detached private tmux servers are ended separately through their recorded endpoints. No systemd scope is created.
- Four run-slot locks are held through setup, pytest and finalization; disk fallback keeps its slot. Slot selection never holds the memory reservation mutex. Memory admission/release separately takes the brief project-directory lock described below; a run holds its selected slot before memory admission. Each slot represents eight workers: a fast run holds two slots together and a whole or named-target run one, so the admitted total never exceeds 32 workers. A smaller explicit `-n` does not reduce its lane’s slot reservation. There is no machine override or load-based admission rule. The comparison of four simultaneous 16-worker fast runs against two is a private measurement-only override, never a shipped option. Memory reservation and per-process bounds are unchanged. `tests.testrunner.layout.all_slots(root, wait=...)` is a public context for the nonsharing part of a live proof: it takes all four or releases partial acquisitions while waiting, then returns all four on leaving the context.
- Registration updates serialize briefly on the changes directory, so concurrent runs of one change do not lose each other's registrations. Cleaning holds that same registry lock and refuses a registered active run even before scratch exists. Each active run guards its retained result directory before publishing a memory reservation; recovery/retire use that exact directory guard before inspecting or removing anything. Different runs do not share that guard. The existing process, scratch identity and private-server ownership proofs remain required and unchanged.
- A run recovers only its own change's abandoned runs, after printing their scope, and only once its lock is free and its own process groups are empty; another change's leftovers are reported and left. The forced removal of a run's Git admin entry reaches only that run's own checkout: a recorded state naming any other checkout path, or an admin entry not directly under the project's `.git/worktrees`, holds the cleanup and removes nothing. Control state and results are versioned JSON, written atomically; a newer format refuses.

Working storage is selected in order from TMPDIR, /dev/shm and /tmp, accepting only a writable executable filesystem proved by statfs to be tmpfs or ramfs. Admission holds a flock on the verified project root across selection, a fresh free-space measurement and publication of each run’s durable reservation. Available bytes must cover the new 4 GiB bound, a fixed 8 GiB margin and the full bounds of this project’s outstanding reservations on the same memory device. Full-bound charging is conservative: bytes already written also reduce the filesystem’s measured free space. Several runs may reserve memory concurrently; when capacity is unavailable the tool emits its one disk-fallback line. This lock coordinates runs of this project, not independent projects or unrelated filesystem writers. The owned root is `qd-<uid>-<project-path-hash>` under that base, opened as a private directory without following links. The run's durable `results/<run>/storage.json` records the base, root name and root identity; the existing run identity, owner token, process locks and retirement checks still apply. Old disk scratch remains recoverable. Insufficient space falls back to disk with one line; unavailable roots or invalid storage records are named and held rather than publishing an unverifiable reservation. During a memory run a one-second sampling interval measures working bytes (hard-linked contents counted once, plus a conservative 4 KiB inode/dentry allowance per entry so empty files are charged); crossing 4 GiB or a measurement error stops its process group and records a refusal. The report retains the sampled peak, allocated file bytes, device diskstats delta (machine-wide, including other writers) and process I/O counters. Metadata memory and writes between samples are not an exact byte quota. Each recorded memory run, kept or crashed included, retains its own reservation until its exact retirement releases it under the same admission lock. Admission never declares a run dead or changes another run’s reservation. Recovery and retirement retain their existing per-run ownership checks; kept reservations have no release command, and a changed filesystem must regain its original memory mount before retirement can proceed. A reboot removes memory contents at the latest, while durable ownership records allow the remaining Git administration to be retired; before a reboot every recorded process must be proved gone, and a missing project root in the same boot holds. The fixed short socket anchors stay on disk.

Pytest originally used `.testruns/t` to keep disposable products in one project-owned place and share the short socket anchor. Direct pytest now uses the same owned memory root's `t` folder, retaining only failing tmp_path folders from at most three failed sessions (`tmp_path_retention_policy = "failed"`, count 3); `.testruns/t` remains its disk fallback and the cache provider stays off. Each test sets TMPDIR to its own tmp_path so a synthetic tool run stays inside that test’s retained lifetime, rather than leaving kept or emergency scratch beside unrelated sessions. This per-test TMPDIR applies inside tool runs too. After test patches and process fixtures have unwound, teardown discovers the test's temporary synthetic project folders, derives each memory root with `scratch.project_name`, and removes only that exact private directory under its candidate bases, holding and checking its directory identity through removal. A shared base must still be tmpfs or ramfs. A base inside the test's own tmp_path stands in for memory: where it is memory it opens through the tool's own memory_root, and where the basetemp is on disk, as on a runner without a large tmpfs, it opens the same way without the mount check. The owner, mode, link and identity checks are the same for both. Kept or crashed synthetic products have the same teardown lifetime. The controller records a shared-memory census and, after workers return their checked paths, fails if a root belonging to a synthetic project seen by this session remains; the final check only reports, and never removes roots. Other concurrent suites' synthetic projects are outside that check. Gates in `tests/unit/test_synthetic_memory_teardown_gates.py` prove it on real roots under the test's own TMPDIR candidate, never /dev/shm itself: a root of another owner at the derived name is left and named; a symlink there is neither followed nor removed; a root swapped for another directory before or after it is opened is not removed, nor is the original; a root that is not mode 0700 is refused; a root of another session's project under the same base is left alone; and the end check fails naming a leftover root of this session's own project, and removes nothing. Its controller samples this shared folder against 4 GiB and interrupts the session on excess or a measurement refusal. Authors choose a unique basetemp on a writable memory filesystem as well as TMPDIR, for example `env -u TMUX -u TMUX_PANE -u QD_TMUX_SOCKET OPENBLAS_NUM_THREADS=1 TMPDIR=/tmp timeout --kill-after=15s 1200s python3 -m pytest --basetemp=/tmp/<unique-author-folder> -n 2`; /tmp must first be proved tmpfs or ramfs on that machine.

The shared test-only `tests/testrunner/resources.py` policy lowers both soft and hard `RLIMIT_AS` to 8 GiB per pytest process, or a tighter inherited limit. The tool establishes it before executing pytest, even for an older target without the shared conftest; direct pytest establishes it in the shared configuration hook, before collection. Controllers, xdist workers and their forked, executed or spawned children inherit the hard bound even if their environment is cleared. `--memory-mib` on the tool, or `TESTRUNS_MEMORY_MIB` for direct pytest, may request a smaller positive integer limit, never a larger one. The tool records its declaration, pytest prints the effective limit and a test raising `MemoryError` names the bound. This is an address-space limit on one runaway process, not an aggregate resident-memory allowance. The ordinary plugin set includes Zarr's pytest plugin, which imports NumPy/OpenBLAS: on the 32-core test machine its thread-buffer reservations produce about 4.4 GiB of legitimate virtual address space with about 80 MiB resident at startup. The 8 GiB bound leaves room for that reservation while limiting one process to less than a tenth of the machine's 89 GiB. The runner fixes `OPENBLAS_NUM_THREADS=1` in its child environment before starting pytest or its plugins, retaining the installed plugins and user site unchanged. Direct authors set it in their command before Python starts. The shared conftest reports the value it observed at import and explicitly cannot attest that earlier plugin imports saw it; a missing or different value is reported with the required early setting, never silently repaired after import. No production program configures these limits; the suite's service and program processes are synthetic.

The tool's `--timeout` is finite and positive (3600 seconds by default), covers preflight, setup and pytest with one monotonic deadline, and uses a main-thread alarm to interrupt synchronous setup too. An interrupted step's own session gets the existing bounded stop grace: at most three 15-second signal waits and two 5-second survivor waits. Finalization, including evidence and cleanup, has a separate 60-second budget. The stated maximum is the requested setup/test timeout plus 120 seconds of termination, finalization and emergency grace; normal test failure exits 1 and a setup/test timeout exits 3. If it expires, the tool makes no cleanup retry: the first result, report, failures and remaining scratch stay, an additional `emergency.json` is attempted within five seconds, and the command exits 7 with an explicit finalization-timeout notice and the evidence path. That notice takes precedence over a first result whose cleanup was still pending. Signal handlers and earlier timers are restored in `finally`. Authors running pytest directly supply an external wall bound as well, for example `env -u TMUX -u TMUX_PANE OPENBLAS_NUM_THREADS=1 timeout --kill-after=15s 1200s prlimit --as=8589934592 .venv/bin/python -m pytest -n 2`, with their own basetemp and fresh short private socket anchor.

**Shared test installs.** `tests/shared_install.py` supplies opt-in session fixtures registered once as a pytest plugin by the three ordinary consumer modules; the global `tests/conftest.py` is unchanged. Each xdist worker builds its own current wheel, current installed prefix and (only where requested) historical installed prefix under its own `tmp_path_factory` directory; nothing is cached across runs. Wheel build source and build venv are removed before the artifact is used. Shared artifacts/prefixes are read-only and fingerprinted through session teardown. Upgrade cases receive writable copies with entry-script prefixes and RECORD hashes rebound, while their synthetic source repositories and installation records remain per-test. The plain installed-layout cases still create a new venv and run real pip for each layout; the genuine first-install-failure and wheel/sdist-build cases retain fresh construction. The statusline footer case reads the shared pristine install. Its display-only runtime/write/foreground-wait case is unchanged.

**Opt-in CI layout.** `run --ci-layout --whole -n 8` selects every test in an owned independent repository, rather than a linked worktree, with the target's exact HEAD/tree and complete real reachable history. The tool initializes the repository with no template hooks, fetches only that exact commit's reachable ancestry from the local source (no network, remote configuration, hardlinked objects or borrowed alternates), and verifies its own plain `.git`, history count and ancestry hash. Its run-specific checkout basename and intent/identity are recorded before setup and after creation. Default linked-worktree bookkeeping, current ownership records, the two-slot fast/one-slot whole rule, memory reservation accounting and all setup/pytest/finalization bounds remain in force. CI mode requires a real memory reservation and refuses before setup if none is available; it never falls back to physical disk.

The CI flag is orthogonal to selection: without `--whole`, a project with unit/contract directories retains the author's fast selection and sixteen workers, and is not a full workflow reproduction. Named targets and worker overrides are also recorded as focused unless a whole selection at eight workers was requested. `ci_full_invocation` records that request, not a passing result. The report records mode, selection, exact argv, repository/common-directory/history, effective environment, source origins and session observations. A shallow source refuses. Preflight requires every project import under checkout/src and the admitted regular/namespace/absent tests form; these are the established CI implementation's source rules, not a substituted fixture.

**The installed copy.** With no `[ship] code` line, a ship owns its installed framework copy. The only explicit mode is `code = "checkout"`, which follows the checkout and never builds a copy; any other type or value fails pure load, before provider or pool work. The default template leaves code absent. Drydock and both production drill factories explicitly choose checkout. Every test/fixture factory chooses checkout; a test of the installed copy opts in explicitly. Synthetic gates, suite timing and instrumented absence of attempted real ship venv creation complete acceptance. A failed copy operation keeps its fixed category in last_failure.reason and its known proof command or install phase in last_failure.step. Its message names both, for example proof command failed at --version, only when that step ran. Doctor displays only those allowlisted values, never exception or native output. A ship never tried passes doctor’s framework check with the note no copy yet; qd up makes one only when the installer finds its source repository. Without that repository doctor fails and says to run sync or upgrade from a Quarterdeck checkout. Missing or broken copies with installed evidence still fail.

At launch and copy activation, the ship prepares `runtime/bin` with only `qd` (and `qd-fakeharness` for synthetic launches), puts it first on the seat’s PATH, and leaves the framework venv’s interpreter and pip out of that PATH, so ordinary Python commands use the machine’s tools.

The generated seat brief gives the shell-quoted absolute `runtime/bin/qd` command and uses it in its command examples, including replies and human inbox watches. It tells the seat to use that command for every `qd` invocation in orders, cards and messages. The final launch `env`, after the bootstrap shell, also exports `BASH_FUNC_qd%%` as a Bash function that calls that absolute command with its arguments.
