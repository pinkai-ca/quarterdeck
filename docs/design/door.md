# Quarterdeck design: The door

A page of [the design](../DESIGN.md). The door is how a message is typed into a seat, including a person's own session and the waking line. What a seat is, and how it is launched, is [Seats](seats.md). The message itself, and the store, is [Post](post.md).

## The door

Everything typed into a seat goes through one path. It clears what it knows how to clear, refuses what it does not, types once into an empty box, checks the box as the program shows it, submits, and confirms by the record. Where it cannot confirm, it looks once more, record first. What it still cannot settle it holds, and never types again by itself.

**The box shows the paste.** After its one paste the door waits for its event, the box showing the message by the adapter's own matcher, never for a guess at how fast a program draws: under load a program's box may take seconds to draw. It only reads while it waits; nothing is typed, resent or cleared. It stops early on a box that cannot become the message, one that is not empty and whose visible characters, whitespace set aside, are the start neither of the message's nor of its fold placeholder's (a fold is read by its literal head, its words before any count, so a fold drawn half way is waited for), read so twice in a row so that a capture torn mid-redraw does not stop it (the matchers compare whole drawings and cannot say "a prefix of it", so this test is the door's own). It stops for safety at 20 s (`PASTE_SHOWN_SECONDS`), below the service loop's 30 s busy line, since one seat's wait holds the loop. A wait past 2 s is logged (`box-wait`, with the seat, its program, its length and how it ended), so a program's slow draws are seen. What it does once the wait ends is as before.

A message reaches its addressee by one of two paths, chosen by the session the seat sits in.

On the Bridge and in the Crew, where the human reads but does not type, the service types the message in full into the seat's pane through the door, under a one-line header and over a one-line footer:

```
qd > order from desk · ord-7f3a · Codex profile of the fake harness
Build the Codex profile of the fake harness. Report when its contract tests pass.
qd > reply: qd post report --re ord-7f3a
```

The pane is where the human reads, by scrolling up, so the whole message goes there and not a pointer to a file. Both programs show a sent paste in full in their transcript. Messages arriving together are typed one paste each, and each is confirmed on its own. New due messages go before previously withheld messages, in order within each group, so a failed item never becomes part of another item's payload. A pre-paste refusal can leave the door usable for the next item; a foreign draft, unknown dialog, unverified paste or uncertain submission holds the door. There is no unconditional progress through an occupied or uncertain box. A message has no length limit.

**A person's own session.** In a human session, the Office, messages arrive through the seat's own `qd inbox --wait` background watch. It blocks until something new is addressed to that seat, prints the new messages in full and exits; the program hands the output to the agent as a notification. The brief tells the seat to arm it again as the last act of every turn. Into a session the human owns it types only when a message waits there, no watch is armed and the box is empty. The exception is only the fixed waking line, never a control. On a seat in a human session, every control goes by restart with resume at turn end; the human at that keyboard may type the slash command by hand. Nothing is pressed or typed into a seat in a session marked human, whoever asks. A human box is never cleared, a notice never dismissed, and no interrupt or control key is authorized by waking.

**The waking line.** When an undelivered message waits and the watch is proved absent or dead, the service may send exactly this fixed line: `qd > ship: messages are waiting. Run qd inbox --wait now to read them.` Before reserving the wake, and again at the final pre-paste capture, the line must fit one composer row using the adapter's explicit `human_wake_box_margin`. A legacy default `box_columns` is not that margin. Unknown margin or pane width holds. A narrow pane holds as `human wake held: pane too narrow for the waking line (N columns needed)`, with no reservation and no paste. The margin includes the prompt, insets and cursor reserve: Codex 3, pi 1, OpenCode 7 and Grok 10 (only at pane widths of at least 14). Claude Code declares 8. Antigravity is unknown. The fake declares its known two-column prefix and supports only the one-row case. No message payload is pasted as a wake. No waiting message means no waking input, including after up, restart, fresh or failover. A human seat that is not up receives no wake. An unavailable pane, a changed launch or a failed ownership read stays a named unknown, not a down fact. An up seat with the service down still shows that it is awaiting the service.

With a joined record, all three of these must be proved: `turn_open is False`, `pending_tools == ()`, and a known empty queue with no queue error. Unknown dimensions hold as `human wake held: record activity unknown (<which>)`. The no-record-yet case still needs a positive empty, non-starting screen. A whitespace draft is nonempty. Unknown boxes, notices, account-holder questions and unreadable watch evidence receive no input.

`human_wake.py` reserves the fixed line in `runtime/seats/NAME/human-wake.json` before any paste, and does not mark the waiting post delivered: only the ordinary watch does that. An uncertain phase that might have typed is never repeated on that launch. A genuinely changed saved launch releases that episode: the original bytes are kept under `runtime/seats/NAME/human-wake-history/<sha256>.json`, then a cancelled release marker is written. A missing or replaced pane alone is not a new launch. Because the text is fixed, the receipt matcher must find no already-qualifying input before reservation and again at the last pre-paste boundary, using the original saved time. A coarse timestamp shared with an old fixed line holds and types nothing. Only phases that could have pasted or submitted use receipt recovery. Prepared-but-unsent reservations are cancelled, never labelled uncertain.

Once the record proves the turn ended, absence of a later watch registration raises **human wake confirmed but watch not armed; person must intervene**, rather than typing again. Each real watch registration writes a saved random `watch-generation` beside the PID and time, under the same seat admission lock, shared with the inbox-watch proof. A confirmed wake followed by a new generation releases the episode. A missing current generation, when the episode saved one, holds. An uncertain wake is not released by a new registration alone; its original receipt must be found first. Only person-must-act end states produce immutable reports: an ended confirmed wake without rearm, possible-input receipt uncertainty, or unreadable operational evidence. The status line carries only those action-required states. Wake scheduling reads the owned record; automatic status reads the operational wake observation and these markers, never conversation bodies. A watch retires only its own registration. The service alone schedules the wake; `qd check` uses that same function on a throwaway human-owned session. Antigravity's waking step is **not applicable: Google pool reading** and starts no human-session seat. There is no second typing implementation.

Each human seat's wake pass and alarm reading are isolated: a failure in one never stops the delivery pass of any other seat, crew seats included. Only a fixed phase and category is logged, once per seat and reason while the service runs, never exception text, input, payload or subject. The seat's `human-wake-status.json` keeps a failure flag bound to its launch; it is shown in detailed `qd status` and `qd watch` and gives no new action-required alarm or report, and facts proved independently still come first. Only a later successful observation of the same launch clears it. A failure to publish the observation is logged and not published again.

**The person's quiet time.** In a human session the ship never restarts the seat, so the seat starts itself fresh, and it needs to know when the person has stopped. Each tick the service reads the newest input the person typed from the seat's owned current record and keeps it in `runtime/seats/NAME/person-quiet.json`, bound to the launch: the time, or unknown with a reason from a fixed list, never record text. Every input counts as the person's except two kinds. The first is the program's own notices, which the adapter declares: Claude Code's are a background task's end (`origin.kind` of `task-notification`), a queued command in that mode, or a compaction summary. The second is the ship's own fixed waking line (`human_wake.LINE`), compared whole. An adapter that declares no notices reads unknown, and so does a record with no joined file, an unreadable or undated input, no person input, or a time ahead of the clock. Nothing reads as quiet for lack of evidence. A queued input counts when it was typed and again when it was taken in, so an unclassified row can only make the person look more recent. `qd watch` shows "person quiet for 23m" or "person's quiet time unknown: reason" from that file alone, and `qd status --json` carries the same reading for each human seat.

Only the desk is woken. Any other human-session seat waits for the person to run `qd fresh`. When the compaction journal says a desk is ready for a manual fresh start, the desk is idle by the ship's one idle proof (`idle.check`: a closed, recorded turn, a known empty queue and no pending tool but its own proved, current inbox watch) and the person has been quiet for twenty minutes (`person_quiet.QUIET`, a framework constant, with no ship-file key), the service posts the desk one order from the ship: "The person has been quiet for twenty minutes and you are ready: post your handoff if you have not, then run qd fresh now." It posts once per readiness, which is the launch and the journal's generation. `runtime/seats/NAME/person-quiet-wake.json` names the order before it is published. A busy, unknown or unreadable reading changes nothing. Nothing here types or restarts: the order arrives through the seat's watch, or through the waking line, and the seat's own `qd fresh` starts it.

**Pending input.** A submitted payload on the same pane, process and launch, still showing its exact verified display, reads as `waiting to be taken`; an empty box reads as `waiting for record confirmation`, never delivered. The bound is 600 seconds from the attempt's time; polls, retries and service restarts cannot move it. It is an intervention policy, not a claim about normal queue delay. Past it the delivery is uncertain, is never resent, and its box and record need inspection.

**The door's one look.** Where the door cannot confirm a delivery (its journal reads as needing a human: blind, uncertain, or past its 600-second wait), the service's `looks` step, just before deliveries, looks once more by itself at a crew seat's current launch, record first, then the screen, and settles only three cases: the record shows the message in either typed form (`post.delivered_forms`), so it counts as delivered; its exact text still sits in the box, so the door submits and the record confirms it as usual; the box is empty, the seat idle by the one idle proof (`idle.reading`) and the record lacks it, so the door types it once more, with the same id under the second-delivery line. Anything else stays held. The look is written into the delivery journal (`look`: time, outcome, what it saw) before it acts, a second delivery's journal is marked as one, and the door never types that message again by itself. The look's candidates come from the attempts the pass's reconcile already loaded: a message whose latest attempt at the seat is one the door could not confirm (unfinished, `pending`, `typed`, `blind` or `queued`). Only the journals those attempts name are opened, and whether the look already typed a message once more is read from that message's own attempts and journals, so a pass with nothing unconfirmed opens no journal, and the settled history is never walked a second time beside reconcile's. A batch, a seat in a human's session, a thinking recovery, a receipt refresh and an owned paste cleanup are left to their own paths. `qd submit <seat>` presses the seat's submit key only when the box holds exactly one of the seat's pending messages, confirms by the record, and prints its proof line; otherwise it refuses, naming what the box shows. For the look's exact text and for `qd submit`, a held box counts as holding a pending message when it equals the message's exact text once two things alone are taken out of it: trailing spaces at row ends, up to the pane's width, and soft wraps at the text area's edge as read with that screen (`harness.types.held_box_matches`). A soft wrap is a break where the row, its painted spaces included, reaches that edge: a word broken at a full row of text, or a wrap at the message's own spaces before a word that would not have fit on the row. A newline the message carries must be a line break. Any other break, a missing newline or any other changed character is refused. Neither types anything; the door still presses submit on what is there and confirms by the record. A held reading in `qd watch` and the status line adds `; qd submit <seat> sends it` when that same read-only check matches. A human session never gets this hint.

**Systems' acts.** A screen the door does not know stays held and named; the door never guesses. A systems seat may answer it, through the same path in the service (`acts.py`): `qd press <seat> "<choice>"` presses a named choice of the dialog as the screen shows it, and `qd type <seat> "<line>"` types one line into a stalled seat's empty box and submits it. Only a caller whose `QD_SEAT` the ship file declares with the role `systems` may act. Each refusal names why. A choice is found by its text exactly once on the screen of the seat's own launch, or refused. It is pressed by the key its own label names (`[0] Skip`, `1. Yes`, `(2) No`, `3) Later`), only where the dialog stands in place of the box, since a key into a drawn box would be typed; otherwise by one click at its middle where the program has asked for SGR mouse reports; otherwise nothing is pressed. A box holding text refuses a press. A line is one line of plain text, at most 2000 characters, into a box read empty; the box must show the line before it is submitted, once; the record confirms it where the program records it. Both act only on a frame read twice, unchanged.

`qd press` presses only a choice whose own text, its pointer, label and a trailing key hint set aside, is on a short benign list: Continue, OK, Dismiss, Skip, Later, Wait, No, Not now, Close. `qd type` never types a line whose first non-space character is `/ ! # $ & @ \` or a backtick. Then the path refuses, by the screen's measured form (an adapter's own interruption: a control question, a question whose answer the orders fix, or one whose name reads as below), by the choice or the line itself, and by the dialog's words, anything that reads as granting a permission, trusting a path or folder, widening a sandbox, allowing a command always, or answering an account holder's, money, data or terms question. Words are matched on normalised text (NFKC, straight quotes, one space), so a wrapped phrase or a curly apostrophe still matches. The dialog's words are read from its nearest top frame above the act (the choice's row, or for a line the last row) to the screen's end, else from the whole screen. A program's own composer frame is never taken for a dialog's: where the adapter's screen reader names it (Grok's rounded composer, `grok_screen.composer_rows`), its top is passed over and the frame above it, or else the whole screen, is read; its rows are left out of the words only where the reader read them as the composer, so they hold the program's own box and status. Passing that top over only moves the start up, so no row outside the program's own frame is read less, and a dialog drawn in a frame of the composer's own form above it is still read from its own frame. Such a screen is the desk's, never a systems seat's. A screen it cannot classify is refused too. A refusal only sends a screen to the desk. The service posts one report from `ship` to each declared desk seat, naming the seat, the caller and the act, the guard's reason and the screen's last 20 lines (2000 characters at most), once per seat and screen (`runtime/seats/<seat>/acts-notices.jsonl`). A refusal for authority tells nobody. Before any key is sent, the act is appended to `runtime/seats/<seat>/acts.jsonl`: the act's id, the verb, the choice or line, the caller, the time, the launch's pane, process and start, and the screen as shown (its last 60 lines, 6000 characters at most). A second line with the same id records the outcome. Where the first line cannot be written, nothing is sent. `qd watch <seat>` prints the seat's last act and its outcome.

**Setting one journal aside.** A delivery journal the door cannot settle holds its seat's door. `qd set-aside <seat> <journal>` moves that one named journal, unchanged and never deleted, into the runtime's fixed archive, `runtime/evidence/journals-set-aside/<seat>/`, through the same service path, with the same authority as the screen acts: a systems seat, never into a session the human owns. The name is one plain `*.json` file name of the seat's pending folder: no path, no `..`, no leading dot, and the file a regular file, never a link. It is moved only when it is provably stuck, read with the seat's post admission and lifecycle claim held without waiting, so no delivery or transition starts meanwhile (either held: refused, the door is active): every delivery attempt to the seat reads and none is still open (an open one is a live delivery); and the journal, where it reads, is not terminal (it holds nothing) and not mid-recovery. A journal that cannot be read is set aside only because the attempts prove nothing live, and the proof line says its message could not be identified. Anything unread refuses. The act is written to `acts.jsonl` before the move, nothing moves when it cannot be; the move is a link into the archive and the journal's unlink, checked byte for byte; the proof line names the journal, its size and sha256, the destination and why, and the service log keeps it. The message stays held by its attempt's result, so the door never types it again; every other delivery to the seat is freed. Where that result is one the service holds (`post.HELD`), the act also marks the message, by an attempt of its own closed `abandoned` with the set-aside's detail, and tells its sender once, as a refused message's sender is told, in words that say what happened and that the message may not have reached its addressee, so the sender can send it again if it matters: one report from `ship`, `re` the message, its id fixed in the act's record before the journal moves, so a later act on the same message or any pass republishes the same notice and never a second. The service's set-aside step completes, each pass, a mark or a notice that a cut left after the move. A sender that is no seat is not told; a message never typed (the door may still deliver it) is neither marked nor told; an unidentified one gets neither, and the act's record names it. Nothing else reaches the status line: the mark is not one the unsettled count reads.

**Reaching a seat mid-turn.** A turn can run half an hour. Both first-round programs take a message typed during a turn and queue it, so a message is typed when it arrives and read at the turn's next stop. Two faster speeds exist where the program has the key: `qd post --now` types the message and presses the program's send-now chord, so the model reads it at its next step without losing the tool call in flight; `qd post --interrupt` presses the program's interrupt key first, which stops the turn, then delivers. `qd stop <seat>` is the interrupt alone. The adapter declares the keys, or their absence. A `qd stop`, like every request a `qd` command files for the service (a stop, a control, a resend, a relaunch, a selection), is answered alone, in name order: a refusal is its answer, written to the request's `.done`; an unexpected error keeps the request under `requests/failed/`, logs the trace and answers the asker that it failed, and the request is never retried, since an act that may have half happened is never repeated unconfirmed. A rebrief, which persists its intent and posts each notice once, stays to be tried on the next tick. None keeps a later request waiting.

Request files are published by a temporary beside the final name, so the client sees a complete `.done` or keeps waiting. Before dispatch the service saves the original bytes beside the request as `.claimed`. Completion removes the active request before removing that replay guard. A claim left by a failed answer stays visible and prevents replay. Rebrief is the exception: its persisted intent and deterministic notice ids make retry safe.

**Unsubmitted paste checks.** On verification failure, the door may clear only its current in-process, positively owned unsubmitted paste. It requires a prepared empty-box reservation followed by the same journal in `pasting`, the exact pane, PID and launch, an unchanged record binding and no receipt, unchanged attached-client activity, and a fresh whole visible payload. Human, unknown, edited, foreign, folded, submitted or changed-cursor input is untouched. Codex has a measured line-clear path: with the cursor proved at the payload's end, `C-a C-k BSpace` once per logical input line. Each adapter declares its own `PasteClearRule` (rule identifier, measured version, per-line keys). A failed key guard or a missing empty-box confirmation stays uncertain. Other adapters have no clearing authority unless they declare one.

Before the clear, optional `paste_clear` format 1 records the owner, cursor and geometry, the line-clear rule and the stage (`clearing`, then `checking_empty`). Only a confirmed empty cleanup (`empty_confirmed`) retires the journal as terminal `withheld`, with its failed `shown` evidence and the reason kept. The attempt stays withheld, never delivered. Another message may then use the empty door. An unchanged explicit resend returns that refusal before any key. A changed payload, version, launch, geometry, frame or record is reevaluated. A missing or unknown first frame holds immediately, with no second capture used to authorize a clear or a resend.

Codex paints an extra editor row when a logical line ends exactly at the composer's right edge. The adapter reconstructs each logical line and requires that one derived editor row. Explicit blank lines consume their own rows. The measured composer is the pane width minus three. Folded pastes keep their counted-placeholder confirmation.

Codex 0.166.0 and Grok 1.0.77 wrap with textwrap 0.16.2 and unicode-linebreak 0.1.5, first fit. Beside ASCII and Latin letters, the box comparison knows three ship-authored symbols: U+00B7 and U+2192 resolve to alphabetic, and U+2026 is inseparable, allowing only its source-established following breaks. That classifies no other punctuation and establishes no unknown grapheme or control layout.

**Scrolled input.** An adapter may declare a third visual form with `BoxScroll`: an exact native scroll mark, its first or last row, its gutter or dedicated-row position, and a top or bottom anchor. After the whole/fold comparison, the door can compare that one contiguous anchored window of the payload's established wrapped rows. It searches for no substring. A dedicated-row mark may also carry the exact count of hidden visual rows. Unknown wrapping or an undeclared adapter supplies no partial comparison. The raw screen box remains unchanged, and submission and exact record confirmation use the ordinary path.

Codex 0.166.0 declares a bottom window with `↑` in the first visible row, immediately outside its pane-width-minus-three text area. A private open measurement used one submitted 22-line/839-character turn, confirmed exactly once in its owned record. Further unsent synthetic pastes measured both horizontal wrapping and vertical scrolling: the wrapped 22-line payload has 29 visual rows, of which the last 24 were visible at 112×42 and the last 14 at 112×28. A plain 22-line payload was whole at 112×42 and showed its last 14/12 rows at heights 28/24. The native viewport row count can vary with layout; the observed window must still equal the declared end of the complete derived layout. Synthetic fixtures contain no account, workspace or post data. The private composer was cleared and its server stopped after measurement.

**Short panes.** A failed whole-paste comparison can carry a reason-only geometry reading: `pane too short: at least N rows needed for the unfolded message (H available); enlarge the pane`. Only adapters with an established text-column declaration opt in. Printable ASCII and LF supply a conservative lower bound: spaces and empty lines are ignored because rendering can discard separators; unsupported layout or undeclared columns stays unknown and keeps the generic mismatch. The bound makes no assumption about UI chrome or a program's folding threshold. Accepted folded placeholders never acquire the diagnostic.

The failed-paste journal retains its observed geometry. Its owner then atomically publishes one marker of at most 4096 bytes, `.pane-obstruction`, beside that journal, naming only that journal, its identity, geometry and paste time. A reading opens that marker and, only if it is valid, the one journal it names. It enumerates no journal or attempt history. Journal phase, identity, payload and geometry remain the evidence; the marker grants no admission or receipt, and no human seat is annotated. Saved launch metadata and the reading's already owned frame bind the display without a pane query. Without such a frame, saved geometry is labelled `last failed paste`. A changed frame removes the current-geometry label without settling uncertainty or allowing a resend. The writer removes the marker when its journal leaves pasting or withheld, or a later paste is confirmed in the record (delivered or accepted queued input, not a screen-only queue hint). Invalid markers read as no diagnostic and reads never repair them. A link at a marker is the post folder's link hold and that hold alone: the door's reading takes it as no diagnostic and a journal save completes past it, the link left as it is, never followed or removed; the status line names it as the post folder names a link (`pane_obstruction.held_links`). Any other refusal there still raises. An open door can display a previous failed delivery's geometry without changing its admission decision. Native renderer behavior at short heights is unmeasured, so no unnumbered height diagnosis is inferred from an unknown box.

**An unread box.** Where the reader finds no box after a paste, outside a human's session, the failed-paste journal also keeps the screen it read as `paste_screen`: the reader's own reason, the screen's last 120 rows cut to 320 characters each and 24,000 in all, and the count of rows cut. Anything shaped like a credential is masked first. The blind reason names the reading and says the screen is kept. It is evidence for a person and nothing else: nothing reads it back to decide, clear or resend, and saving it can fail without changing the outcome.

**Stopping during a delivery.** SIGTERM exits immediately outside a delivery and outside a relaunch the service makes (that section is described in seats.md, under "A relaunch a stop waits out"). Initial door readings, admission/identity checks and the attempts-history scan remain interruptible before any attempt is opened. The service reuses its reader for that preflight scan and passes the history into journal preparation; the new attempt itself still participates in the earliest-attempt timestamp. Deferral begins immediately before the attempt write and spans the existing journal/submit boundary. `Attempts.open` publishes an owner-bound attempt pointer before it returns, so the write unit receives delivery grace even while its journal has not been prepared. Journal preparation replaces that early pointer with the ordinary journal-bound pointer. The early form grants grace only; after an interrupted process it leaves the attempt unchanged for ordinary receipt reconciliation. During that write unit it is deferred until the prepared journal is cancelled before paste, or the checked submission and its `submitted` journal are saved. Stop keeps its ordinary 3-second grace; an exact observed in-flight delivery extends the total to 30 seconds from SIGTERM, then at most 2 seconds for SIGKILL release. The stopper annotates only the matching journal after the old process is gone and one nonblocking claim proves the original lock inode, PID, start, generation and transaction token. The lock frees as the old process closes its files, a moment before the kernel marks it gone, so after the lock frees the stopper waits up to 2 seconds more for that event before it reads the owner as gone. Unknown identity leaves the journal unchanged. Forced `pasting` or `submitting` cuts remain uncertain until the door's one look settles them.

The same boundary recognizes the waking line's `human-wake.json` reservation. A stop before paste keeps that prepared reservation unchanged and unsent. The `paste_boundary = "prepared-before-paste-v1"` marker proves that no payload paste began, so the next service may cancel that reservation and deliver the open message once through the ordinary door. Ambiguous paste and submission keep their holds.

A message the door typed into a turn that ended in an error is not settled as received. Where the record proves no model output, the attempt and its journal read `unacted`: no tick types it again, and the next start carries it as unread. Where output is unknown they read `uncertain` and wait for a hand. Where the record shows output, its receipt stands. How a turn's error is classified, and what a provider refusal does to the seat, is [Seats](seats.md#6-seats). What the attempt file stores, and when a delivery counts, is [Post](post.md#7-post).

OpenCode 1.19.5 draws a centred, capped composer before its first turn and a
full-width composer afterwards. At pane widths 64/80/112, measured text widths
are 55/70/70 before and 55/71/103 after that turn. The door asks each adapter
for the text width of the screen already read; the default retains its ordinary
`box_columns` declaration. OpenCode reads its recognised bottom-rule span minus
five cells and retains its measured ASCII word/hyphen wrapping. For comparison
alone it excludes ASCII padding beyond the text area, bounded by the actual pane;
`Screen.box` remains the native observation. An unrecognised rule supplies no
measured width and falls back to the old declaration, never a guessed cap.
